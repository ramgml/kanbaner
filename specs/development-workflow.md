# Процесс разработки и релизов

- Статус: принят
- Дата: 2026-11-06

## 1. Назначение

Этот файл фиксирует модель веток, версионирование и выпуск релизов Kanbaner.

Правила:

- Продуктовые границы описаны в `product-mvp.md`.
- Архитектурные решения описаны в `architecture.md`.
- Технологии и версии зависимостей описаны в `technology-stack.md`.
- Процесс разработки не должен незаметно менять публичные контракты, схему данных или продуктовое поведение.
- Изменение модели веток, SemVer-политики или состава релизных артефактов требует явного решения пользователя и обновления этого файла.

## 2. Модель веток

Используется GitFlow с двумя постоянными ветками:

| Ветка | Назначение | Правила |
|---|---|---|
| `main` | Опубликованные стабильные релизы | Только merge из `release/*` и `hotfix/*`; каждый релиз помечается тегом |
| `dev` | Интеграция завершённых задач | Всегда рабочая; сюда вливаются `feat/*` и `fix/*` |

Временные ветки:

| Ветка | Создаётся от | Вливается в |
|---|---|---|
| `feat/<slug>` | `dev` | `dev` |
| `fix/<slug>` | `dev` | `dev` |
| `release/<version>` | `dev` | `main` и `dev` |
| `hotfix/<version>` | `main` | `main` и `dev` |

Правила:

- Код, миграции и изменения контрактов выполняются в отдельных ветках задач.
- Небольшие изменения спецификаций и документации допускаются напрямую в `dev`, если нет параллельной работы над теми же файлами.
- Прямые коммиты в `main` запрещены, кроме начальной истории репозитория.
- Перед интеграцией ветка перебазируется на актуальный `dev`.
- Интеграция выполняется через `merge --no-ff`, чтобы сохранить границу задачи.
- После rebase и каждого merge проверки должны оставаться зелёными.
- Force-push, `reset --hard` и переписывание опубликованной истории запрещены.
- Опубликованные теги не перемещаются и не удаляются.
- Ветки `release/*` и `hotfix/*` создаёт и интегрирует только оркестратор.
- Worker не выполняет merge, rebase, push и удаление чужих веток или worktree.
- Remote в MVP не обязателен. При появлении удалённого репозитория `main` и `dev` защищаются, а задачи могут проходить через pull request без изменения модели веток.

## 3. Коммиты

Формат:

```text
<type>(<scope>): <краткое описание>
```

Допустимые типы:

- `feat` — новая возможность;
- `fix` — исправление;
- `docs` — документация;
- `test` — тесты;
- `refactor` — изменение без нового поведения;
- `chore` — инфраструктура и релизные изменения.

Правила:

- Scope необязателен, но предпочтителен для доменных и инфраструктурных изменений.
- Один коммит не должен смешивать несвязанные задачи.
- Коммит worker-а содержит только файлы его задачи.
- В обычной одиночной задаче коммит выполняется только по явной просьбе пользователя.
- В режиме `parallel-worktrees` worker коммитит по протоколу skill.
- Release-коммит имеет вид `chore: release vX.Y.Z`.

## 4. Версионирование

Версионируются независимо:

| Объект | Схема | Источник |
|---|---|---|
| Приложение | SemVer | Корневой `package.json` |
| Plugin Contract | SemVer | `plugin-contract.md` |
| Плагин | SemVer | Манифест плагина |
| Миграции | Версия плагина и checksum | Журнал миграций |

Правила:

- Версия приложения не определяет версию Plugin Contract.
- Несовместимое изменение Plugin Contract требует нового major-контракта.
- Пакеты monorepo остаются `private` и не публикуются в npm в MVP.
- Встроенные плагины входят в релиз приложения и отображают версию приложения.
- Сторонние плагины версионируются независимо.
- Смена схемы SQLite не требует нового major приложения, если миграция автоматическая и проверена.
- Несовместимая миграция требует резервной копии, release notes и явной процедуры восстановления.
- Автоматический downgrade не поддерживается. Откат выполняется запуском предыдущей версии приложения с резервной копией в новом каталоге данных.

### Версии приложения

| Состояние | Версия |
|---|---|
| Разработка MVP | `0.1.0-dev.0` |
| Ветка `release/0.1.0` | `0.1.0` |
| Первый стабильный релиз | `0.1.0` |
| Разработка следующего minor | `0.2.0-dev.0` |
| Первый hotfix | `0.1.1` |
| Стабильный major | `1.0.0` |

Правила:

- Публичные релизы до завершения этапа 8 не выпускаются.
- `0.1.0` выпускается после выполнения Definition of Done MVP.
- До `1.0.0` minor-версия может содержать несовместимое изменение приложения только с release notes, миграцией и явным решением пользователя.
- Patch-версия не должна ломать совместимость данных и публичного поведения.
- `1.0.0` назначается после стабилизации обновлений, миграций, backup/restore и Plugin Contract.

## 5. Подготовка релиза

Релиз выпускается по готовности, а не по календарю.

### 5.1. Создание release-ветки

1. Все задачи релизного объёма находятся в `done`.
2. Definition of Done MVP или релизного этапа выполнен.
3. От актуального `dev` создаётся `release/<version>`.
4. Новые возможности в release-ветку не добавляются.
5. Допускаются только исправления, документация, обновление версии и changelog.

### 5.2. Обязательные проверки

- чистая установка на Linux и Windows;
- `pnpm install --frozen-lockfile --strict-peer-dependencies`;
- отсутствие deprecated-зависимостей и unmet peer dependencies;
- typecheck, линтер и unit-тесты;
- integration, contract и Storage Provider Conformance Suite;
- E2E-сценарии;
- production build;
- загрузка и работа нативного `better-sqlite3`;
- миграции на чистой базе и повторный запуск;
- обновление копии данных с предыдущего релизного тега;
- online backup через `.backup()` и restore в новый каталог;
- установка из архива исходников;
- проверка отсутствия секретов.

Для первого релиза проверка обновления с предыдущего тега заменяется проверкой чистой установки и восстановления backup.

### 5.3. Версия и changelog

1. В корневом `package.json` устанавливается релизная версия.
2. Версии встроенных плагинов синхронизируются с версией приложения.
3. `CHANGELOG.md` переводится из `Unreleased` в раздел релиза.
4. В release notes указываются миграции, backup, ограничения и порядок обновления.
5. Выполняется release-коммит `chore: release vX.Y.Z`.

### 5.4. Публикация

1. Release-ветка вливается в `main` через `merge --no-ff`.
2. На коммите `main` создаётся annotated tag `vX.Y.Z`.
3. Release-ветка вливается обратно в `dev`.
4. В `dev` устанавливается следующая development-версия.
5. Release-ветка удаляется после успешной интеграции.
6. Публикуется архив исходников с `pnpm-lock.yaml`, документацией и changelog.
7. Готовые бинарные сборки в MVP не публикуются.

Ошибка после публикации исправляется новым patch-релизом. Существующий тег не перемещается.

## 6. Hotfix

1. Hotfix создаётся от тега последнего стабильного релиза или от `main`.
2. Ветка называется `hotfix/<version>`.
3. В релиз входят только исправление, regression-тест, patch-версия и changelog.
4. Выполняются релевантные релизные проверки.
5. Ветка вливается в `main`, создаётся новый annotated tag.
6. Исправление вливается в `dev`.
7. При наличии активной `release/*` hotfix переносится и в неё.

Поддерживается только последняя minor-версия. Долгоживущие ветки поддержки старых minor в MVP не создаются.

## 7. Changelog

`CHANGELOG.md` ведётся вручную в формате Keep a Changelog.

Разделы:

- `Added`;
- `Changed`;
- `Deprecated`;
- `Removed`;
- `Fixed`;
- `Security`;
- `Migrations`.

Правила:

- Feature-ветки и worker-ы не редактируют `CHANGELOG.md`.
- Релизные изменения фиксируются в `tasks/reports/KAN-NNN.md`.
- Оркестратор переносит значимые изменения в `Unreleased`.
- В release-ветке changelog редактируется окончательно.
- Автоматические генераторы changelog в MVP не используются.
- Запись `Migrations` обязательна, если релиз меняет схему данных или требует backup.

## 8. Границы процесса

- Release-please, Changesets и автоматический changelog не входят в MVP.
- Готовые установщики, MSI, AppImage, deb и автообновление не входят в MVP.
- Публикация пакетов в npm не входит в MVP.
- Docker-образы не публикуются.
- Подпись тегов и артефактов может быть добавлена отдельным решением.
- Модель веток не отменяет правила задач, ownership файлов и проверки из `AGENTS.md`.
