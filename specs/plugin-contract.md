# Контракт плагинов Kanbaner v1

- Статус: принят как основа MVP
- Версия: 1
- Дата: 2026-11-06

## 1. Назначение

Контракт определяет, как ядро и плагины взаимодействуют без импорта внутренней реализации друг друга.

Контракт охватывает:

- манифест и жизненный цикл плагина;
- команды и запросы;
- события;
- универсальные ссылки на ресурсы;
- UI-вклады;
- хранение и миграции;
- экспорт в HTTP API и MCP;
- версионирование и совместимость.

Это не сетевой протокол MVP. Внутри процесса используется типизированный SDK. Логические сообщения контракта сериализуемы и могут быть позже перенесены через RPC.

## 2. Границы доверия

- Плагины являются доверенным локальным кодом.
- Они работают в процессе приложения.
- `permissions` описывают намерения и используются для диагностики и UI.
- `permissions` не являются песочницей.
- Плагинам запрещено импортировать внутренние модули ядра и других плагинов.
- Взаимодействие выполняется только через `@kanbaner/plugin-sdk` и публичные контракты.

## 3. Идентификаторы

### 3.1. Plugin ID

Формат:

```text
<namespace>.<plugin>
```

Примеры:

```text
kanbaner.tasks
kanbaner.projects
kanbaner.notes
acme.calendar
```

Plugin ID:

- глобально уникален;
- неизменяем после публикации;
- используется в командах, событиях, namespace данных и ссылках;
- не должен зависеть от отображаемого названия.

### 3.2. Версия плагина

Используется SemVer:

```text
major.minor.patch
```

### 3.3. ID команды и запроса

Формат:

```text
<plugin-id>.<action>
```

Примеры:

```text
kanbaner.tasks.create
kanbaner.tasks.move
kanbaner.tasks.list
kanbaner.notes.create
kanbaner.search.query
```

ID глобально уникален. Регистрация занятого ID завершается ошибкой активации.

### 3.4. Тип события

Формат:

```text
<plugin-id>.<resource>.<past-tense-action>
```

Примеры:

```text
kanbaner.tasks.task.created
kanbaner.tasks.task.updated
kanbaner.tasks.task.deleted
kanbaner.notes.note.updated
```

## 4. Манифест плагина

Пример:

```json
{
  "id": "kanbaner.projects",
  "name": "Kanban",
  "version": "1.0.0",
  "hostApi": "^1.0.0",
  "entrypoints": {
    "server": "./dist/server.js",
    "client": "./dist/client.js"
  },
  "requires": {
    "kanbaner.tasks": "^1.0.0"
  },
  "consumes": [
    "kanbaner.tasks.commands.v1",
    "kanbaner.tasks.queries.v1",
    "kanbaner.tasks.events.v1"
  ],
  "provides": [
    "kanbaner.projects.ui.v1"
  ],
  "permissions": [
    "commands",
    "events",
    "ui",
    "storage"
  ],
  "migrations": "./migrations"
}
```

Обязательные поля:

| Поле | Назначение |
|---|---|
| `id` | Уникальный идентификатор |
| `name` | Отображаемое название |
| `version` | Версия плагина |
| `hostApi` | Совместимый диапазон API ядра |
| `entrypoints` | Точки входа server и/или client |
| `requires` | Обязательные плагины и диапазоны версий |
| `consumes` | Потребляемые контракты |
| `provides` | Предоставляемые контракты |
| `permissions` | Заявляемые возможности |
| `migrations` | Каталог миграций, если есть данные |

Манифест валидируется до выполнения кода плагина.

Конкретные команды, запросы, события и UI-вклады регистрируются через SDK во время активации. Ядро проверяет их метаданные и уникальность.

Контекст активации предоставляет публичные регистраторы команд, запросов, ресурсов и подписок на события, а также доступ к Storage Provider через Store-контракты. Плагин получает их от composition root и не импортирует внутренние реализации ядра. UI-вклады регистрируются через публичный UI API без доступа к чужому DOM.

## 5. Жизненный цикл

```text
discovered
  → manifest_validated
  → dependencies_resolved
  → migrated
  → server_activated
  → client_registered
  → active
```

Состояния ошибки:

```text
failed
disabled
incompatible
missing_dependency
safe_mode
```

Правила:

- зависимости активируются раньше зависимых плагинов;
- циклы запрещены;
- миграции выполняются до активации;
- при ошибке серверная активация откатывается;
- при ошибке клиентской регистрации серверный плагин деактивируется;
- отключение выполняется в обратном порядке;
- отключение не удаляет данные;
- ошибки публикуются в plugin manager;
- safe mode позволяет запустить ядро без проблемного плагина.

## 6. Команды

Команда — операция, которая может изменить состояние.

Пример метаданных:

```json
{
  "id": "kanbaner.tasks.create",
  "contract": "kanbaner.tasks.commands.v1",
  "version": 1,
  "kind": "mutation",
  "risk": "write",
  "idempotency": "supported",
  "exposure": {
    "ui": true,
    "http": true,
    "mcp": true
  },
  "inputSchema": {},
  "outputSchema": {}
}
```

Поля:

| Поле | Значение |
|---|---|
| `kind` | `mutation` |
| `risk` | `read`, `write`, `destructive` |
| `idempotency` | `none` или `supported` |
| `exposure` | Явные каналы публикации |
| `inputSchema` | JSON Schema аргументов |
| `outputSchema` | JSON Schema результата |
| `version` | Версия контракта команды |

### Правила

- Команда валидирует вход до изменения данных.
- Мутация выполняется в транзакции плагина.
- Частичный успех запрещён: результат либо успешен, либо операция откатывается.
- Массовая операция должна быть атомарной или явно разбитой клиентом.
- Команда не публикует событие до коммита.
- Разрушительная команда должна быть отдельной и иметь `risk = destructive`.
- Команда должна учитывать `expectedVersion`, если изменяет версионируемую сущность.
- Команда не должна молча перезаписывать конфликтующее изменение.

### Массовые операции домена задач

Домен `kanbaner.tasks` публикует две атомарные массовые команды:

```text
kanbaner.tasks.task.moveMany     risk = write
kanbaner.tasks.task.deleteMany   risk = destructive
```

Обе принимают `items` из 1…200 уникальных `{id, expectedVersion}` одного
проекта и не выполняют частичных изменений. Все проверки — размер,
уникальность, существование, один проект, точные версии и целевая колонка —
завершаются до первой записи. Дубликаты, чужая задача, отсутствующая задача,
устаревшая версия или чужой target дают ошибку без записи.

`task.moveMany` дополнительно принимает `columnId` и только дописывает задачи
в конец колонки в порядке входного массива. Source и target могут совпадать.
Результат — `{ tasks }` в порядке входа. Для каждой задачи публикуется
`kanbaner.tasks.task.moved`, для фактически сдвинутых соседей —
`kanbaner.tasks.task.updated`; поисковый индекс получает upsert перемещённых
задач и соседей.

`task.deleteMany` требует `confirm: true` и удаляет задачи вместе с
подзадачами. Parent и child в одном наборе не удаляются дважды: дескрипторы,
события и поисковые ссылки дедуплицируются. Успешный результат содержит
`deleted: true`, `deletedResourceRefs`, уникальные `deletedTasks` и `eventId`.
Если все задачи набора уже отсутствуют, возвращается `{ deleted: false }` без
событий и записи. Delete-событие публикуется для каждой уникальной задачи,
сдвинутые соседи получают `task.updated`, поисковый индекс очищает удалённые
ссылки.

Обе команды поддерживают `Idempotency-Key`: повтор с тем же ключом и payload
возвращает сохранённый результат без мутации, событий и повторной индексации.

### Цвета проекта и колонок

`Project` и `TaskColumn` могут содержать необязательное поле `color` со значением
из общей палитры:

```text
default | slate | blue | green | yellow | orange | red | purple
```

Отсутствие поля в существующем документе совместимо и означает стандартное
оформление. `project.create`, `project.update` и `column.create` принимают
необязательный `color`. В `column.update` поля `title` и `color` необязательны
по отдельности, но требуется хотя бы одно из них; color-only обновление не
меняет заголовок. Обычные правила `expectedVersion`, транзакции и событий после
коммита сохраняются. Произвольные CSS-значения в контракт не входят.

Цвет задачи отдельно не хранится: цветовой акцент карточки вычисляется
представлением из существующего `Task.priority`.

### Дерево и вложения заметок

`kanbaner.notes` публикует versioned CRUD/move/delete для страниц, отдельные
команды favorite/visit/link/attachment и queries get/list/search/links/export.
`note.move` принимает `parentId` и позицию среди siblings, запрещает циклы и
возвращает затронутые соседей. `note.delete` является destructive, принимает
`confirm: true` и атомарно удаляет всю ветку, activity и attachments.

`note.update` принимает partial title/contentMarkdown с `expectedVersion`.
Favorite/visit не меняют версию содержимого. Store-мутации с объявленной
поддержкой idempotency сохраняют результат ключа в той же транзакции, что и
изменение данных. UI invoker дополнительно принимает необязательный
`options.idempotencyKey` и передаёт его только mutation в OperationBus.

`note.subtree` возвращает свежий `noteCount` ветки, включая корень, и число
вложений. `note.delete` дополнительно принимает `expectedDescendants` с этим
значением и атомарно отклоняет удаление, если размер ветки изменился после
preview. Legacy-вызов без count остаётся поддерживаемым.

События и поисковые эффекты выполняются после коммита.

Attachment-create принимает base64 только поддерживаемого растрового формата;
домен проверяет размер и сигнатуру. Attachment URL в Markdown должен принадлежать
той же заметке. Поддерживаются inline `image` и `imageReference` через
`definition`. Query export является read-only и превращает локальные image URL в
data URL, не меняя сохранённый Markdown. Автоматическая очистка вложений во время
редактирования запрещена: удаление выполняется только явной командой после
подтверждения и проверки `ATTACHMENT_IN_USE`.

## 7. Запросы

Запрос не изменяет сохраняемое состояние.

Пример:

```json
{
  "id": "kanbaner.tasks.list",
  "contract": "kanbaner.tasks.queries.v1",
  "version": 1,
  "kind": "query",
  "risk": "read",
  "exposure": {
    "ui": true,
    "http": true,
    "mcp": true
  },
  "inputSchema": {},
  "outputSchema": {}
}
```

Правила:

- запрос не публикует доменные события;
- запрос не изменяет БД;
- внутренний кэш не должен менять наблюдаемое поведение;
- запрос обязан поддерживать пагинацию, если результат не ограничен;
- запрос возвращает только данные, доступные текущей установке.

## 8. Вызов команды или запроса

Логический конверт:

```json
{
  "contractVersion": 1,
  "requestId": "01K...",
  "operationId": "kanbaner.tasks.create",
  "operationVersion": 1,
  "idempotencyKey": "01K...",
  "source": {
    "type": "http",
    "id": "api"
  },
  "payload": {
    "projectId": "01J...",
    "title": "Подготовить релиз"
  }
}
```

`source.type` принимает:

```text
ui
http
mcp
plugin
system
```

`source.id` необязателен и уточняет клиента или плагин.

### Контекст выполнения

SDK передаёт обработчику:

```text
requestId
traceId
source
signal
deadline
idempotencyKey
logger
commands
queries
resources
storage
events
```

Контекст создаётся ядром. Плагин не подменяет источник вызова.

### Идемпотентность

- `requestId` нужен для трассировки, но не является ключом идемпотентности.
- `idempotencyKey` передаётся отдельно.
- Если команда поддерживает идемпотентность, повтор с тем же ключом и тем же payload возвращает исходный результат.
- Повтор с тем же ключом и другим payload возвращает `IDEMPOTENCY_CONFLICT`.
- Область действия ключа — команда и плагин.
- Время хранения ключей определяется плагином и документируется.

### Вложенные вызовы

Плагин может вызвать публичную команду другого плагина через `ctx.commands`.

- Вложенный вызов не разделяет транзакцию вызывающего плагина.
- Ядро ограничивает глубину вложенности.
- Циклическая цепочка команд завершается ошибкой.
- Для реакции на уже произошедшее изменение предпочтительны события.

## 9. Результат и ошибки

Успех:

```json
{
  "ok": true,
  "data": {
    "resource": "kanbaner.tasks:task:01J...",
    "version": 1
  },
  "meta": {
    "warnings": []
  }
}
```

Ошибка:

```json
{
  "ok": false,
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "Задача была изменена другой операцией",
    "retryable": false,
    "details": {
      "expectedVersion": 3,
      "actualVersion": 4
    }
  }
}
```

Базовые коды:

| Код | Значение |
|---|---|
| `VALIDATION_ERROR` | Неверные аргументы |
| `NOT_FOUND` | Ресурс не существует |
| `VERSION_CONFLICT` | Конфликт версий |
| `IDEMPOTENCY_CONFLICT` | Ключ повторно использован с другим payload |
| `PERMISSION_DENIED` | Операция запрещена |
| `DEPENDENCY_UNAVAILABLE` | Недоступен зависимый плагин или сервис |
| `PLUGIN_UNAVAILABLE` | Плагин не активирован |
| `CANCELLED` | Операция отменена |
| `TIMEOUT` | Истёк срок выполнения |
| `RATE_LIMITED` | Превышен лимит |
| `INTERNAL_ERROR` | Внутренняя ошибка плагина |

### Правила ошибок

- `message` предназначен для человека.
- `code` стабилен и используется программно.
- `details` не содержит секретов.
- Стек и внутренние пути не возвращаются внешнему клиенту.
- Ошибка плагина не раскрывает содержимое чужих данных.
- Ожидаемые ошибки обработчика выбрасываются как публичный SDK `PluginOperationError`; шина маппит их в стабильный конверт. Приватные kernel-конструкторы не используются.
- HTTP-статус вычисляется транспортом, а не плагином.

## 10. События

Пример:

```json
{
  "eventId": "01K...",
  "type": "kanbaner.tasks.task.updated",
  "contractVersion": 1,
  "source": "kanbaner.tasks",
  "occurredAt": "2026-11-06T12:00:00Z",
  "resource": "kanbaner.tasks:task:01J...",
  "resourceVersion": 4,
  "payload": {
    "changed": ["title", "status"]
  }
}
```

### Семантика доставки

- Событие публикуется после успешного коммита.
- Доставка в MVP асинхронная и best-effort.
- Гарантированный порядок между разными ресурсами отсутствует.
- Подписчик обрабатывает события идемпотентно.
- Ошибка подписчика не откатывает источник.
- Ошибка подписчика журналируется.
- Устаревшие события отбрасываются по `resourceVersion`, если это применимо.
- Плагины с собственным индексом должны поддерживать полную переиндексацию.

События не являются заменой транзакции и не должны быть единственным способом выполнения критичной операции.

### Содержимое

Предпочтителен минимальный payload:

- идентификатор ресурса;
- версия;
- список изменённых полей;
- идентификаторы связей, если это необходимо.

Полное состояние следует получать запросом, а не считать снимок события актуальным.

### Подписка

Плагин объявляет подписки через SDK:

```text
kanbaner.tasks.task.created
kanbaner.tasks.task.updated
kanbaner.tasks.task.deleted
kanbaner.*
```

Wildcard допустим только в конце сегментов. Неизвестный тип события не является ошибкой активации.

## 11. Ресурсы и связи

### 11.1. ResourceRef

Формат:

```text
<plugin-id>:<resource-type>:<opaque-id>
```

Пример:

```text
kanbaner.tasks:task:01J...
```

Правила:

- `plugin-id` должен совпадать с ID плагина-владельца;
- `resource-type` стабилен в пределах контракта;
- `opaque-id` не интерпретируется другими плагинами;
- ссылка сериализуема и может храниться в БД;
- ссылка не даёт права на чтение ресурса.

### 11.2. Регистрация типа ресурса

Плагин-владелец регистрирует адаптер:

```text
resolve(ref)      → заголовок, тип, состояние, метаданные
canOpen(ref)      → доступно ли представление
open(ref)         → открыть ресурс в UI
toSearchDocument(ref) → необязательное поисковое представление
```

`resolve` не должен изменять состояние. Для удалённого ресурса возвращается `NOT_FOUND`.

### 11.3. Связи

Связи создаются через сервис ядра:

```text
ctx.resources.link(sourceRef, targetRef, relation)
ctx.resources.unlink(sourceRef, targetRef, relation)
ctx.resources.list(ref, relation?)
```

`relation` должен быть стабильным и namespace-ированным:

```text
kanbaner.notes.references
```

Правила:

- связь не создаёт внешний ключ между данными плагинов;
- дубликат связи отклоняется или возвращается идемпотентно;
- при удалении ресурса связанные ссылки очищаются по событию;
- неизвестная ссылка отображается как удалённая, но не ломает страницу.

## 12. UI-контракт

UI-контракт v1 является внутрипроцессным.

Плагин может зарегистрировать:

- представление;
- маршрут;
- пункт навигации;
- пункт меню команд;
- панель в слоте;
- страницу настроек;
- обработчик открытия ресурса;
- диалог или уведомление через API ядра.

### Базовые слоты ядра

```text
app.sidebar
app.main
app.details
app.assistant
app.settings
app.overlays
```

### Правила

- Вклад имеет уникальный ID внутри слота.
- Порядок задаётся явным приоритетом.
- Плагин не манипулирует DOM другого плагина.
- Плагин не импортирует React-компоненты другого плагина напрямую.
- Для перехода к чужому ресурсу используется `ctx.resources.open`.
- Для собственных расширяемых областей плагин публикует именованный slot.
- Другие плагины могут заполнять только опубликованный slot.
- Удаление или переименование slot требует major-версии UI-контракта.
- UI-вклад не должен блокировать активацию остальных плагинов при ошибке рендера.
- Ошибка плагина показывается в границе ошибки, а не роняет весь интерфейс.
- `resource-opener` декларирует `resourceType` и `route`; необязательный
  `resourcePluginId` позволяет открывать ресурс другого плагина без его импорта.
  Клиентский `openResource(ref)` добавляет `resource=<encoded ResourceRef>` к
  маршруту активного opener и сообщает о недоступности без падения shell.
- Необязательное строковое поле `icon` задаёт идентификатор иконки
  navigation-вклада (`notebook-tabs`, `folder-kanban`). Значение непустое и
  содержит хотя бы один непробельный символ. Это совместимое расширение
  UI-контракта v1: SDK не зависит от React или Lucide, а shell сопоставляет
  строку со статическим allowlist компонентов. Вклад без `icon` или с
  неизвестным значением получает прежний fallback `Flag`.
- `renderSlot(slot, context)` рендерит публичный outlet через тот же UI registry.
  Контекст сериализуем; плагин-владелец outlet не импортирует вкладчика, а вклад
  получает только свои props и context.

Текущий UI-контракт не предназначен для загрузки недоверенного кода. Для будущей песочницы потребуется отдельный transport и renderer.

## 13. Хранение и миграции

### Правила хранения

- Плагин работает только через Store-контракты или `PluginDocumentStore`.
- Плагин не импортирует драйвер БД и не выполняет SQL напрямую.
- Плагин не читает и не изменяет данные другого плагина.
- Ядро не читает доменные таблицы плагинов.
- Доступ к хранилищу выполняется только через Storage Provider активного backend.
- Соединением с базой управляет только Storage Provider; доменный или UI-плагин не открывает собственное соединение.
- Конкретные имена таблиц, схем и SQL-диалект не входят в публичный контракт.
- Настройки плагина принадлежат плагину.
- Отключение сохраняет данные.
- Деинсталляция по умолчанию сохраняет данные.
- Удаление данных выполняется отдельной явной операцией.

### Store-контракты

- Доменный плагин объявляет собственный Store-контракт.
- Контракт описывает операции уровня домена, а не SQL-запросы.
- Контракт не содержит имён таблиц, типов драйвера и диалекта БД.
- Storage Provider реализует контракт для конкретного backend.
- Плагин получает реализацию через Storage Provider Registry.
- Плагин проверяет capabilities провайдера.
- Публичные операции Storage Provider и Store-контрактов асинхронны.
- `transactions` обязательна для любого провайдера; savepoints опциональны.
- Транзакция предоставляется через `withTransaction(async (tx) => ...)` и остаётся открытой до завершения callback.
- Транзакция монополизирует соединение; другие операции ждут и не выполняются внутри чужой транзакции.
- Rejected Promise откатывает транзакцию; вложенность без savepoint возвращает ошибку.
- ID генерируются приложением или доменным плагином до записи; autoincrement и rowid не являются публичным ID.
- Время передаётся в UTC; формат timestamp инкапсулирован Store-контрактом.
- Для простых данных используется `PluginDocumentStore`.
- При смене backend меняется провайдер, а не доменный плагин.
- Смена backend поддерживается для пустого хранилища; перенос существующих данных выполняется отдельным backend-neutral export/import и не входит в MVP.

### Миграции

- Применяются до активации новой версии.
- Выполняются атомарно в транзакции провайдера.
- `transactions` является обязательной capability провайдера.
- Уже применённая миграция не изменяется.
- История хранится в `core_plugin_migrations` с ключом `(backendId, pluginId, version, checksum)`.
- Миграция принадлежит конкретному backend и не применяется к другому провайдеру.
- Повторный запуск не применяет миграции заново.
- Порядок определяется версией и именем файла.
- Ошибка миграции переводит плагин в `failed`.
- Откат кода не откатывает данные автоматически; перед несовместимой миграцией нужна резервная копия.
- Миграция не должна напрямую менять таблицы другого плагина.

### Формат миграции

Конкретный инструмент выбирается при реализации. Контракт требует:

- уникального имени;
- монотонного порядка;
- транзакционности;
- журналирования результата;
- отсутствия зависимости от UI;
- возможности применить все миграции на пустой базе.

### Поисковый индекс и SearchProvider Registry

Поисковый индекс — инфраструктура активного Storage Provider. Его таблицы
`core_search_*` не принадлежат доменному плагину и не входят в публичный
контракт. Доменный плагин получает bound `ctx.search` и может:

```text
upsert(documents)   → записать документы своего ResourceRef
delete(ref)         → удалить свой документ
list()              → прочитать только свои документы
search(query)       → искать только в своём namespace
reindex(documents)  → транзакционно заменить только свои документы
```

Попытка записать или удалить чужой `ResourceRef` завершается
`PERMISSION_DENIED`. Документ содержит `ref`, `title`, `text`, необязательные
`kind`, `metadata` и `updatedAt`; секреты, вложения и служебные поля в
`metadata` запрещены. Провайдер обязан поддерживать `transactions` и
`fullTextSearch` либо использовать документированный fallback.

Для глобальной агрегации плагин регистрирует публичный `SearchProvider`:

```text
id             → обязан совпадать с Plugin ID владельца
kinds[]        → { id, title } типов ресурсов
filterFields[] → публичные поля metadata, которые провайдер умеет фильтровать
listFacets()   → facet-ы для UI
search(query)  → scoped-выдача своего namespace
reindex()      → идемпотентная полная переиндексация
```

- Реестр содержит только активных доверенных провайдеров.
- `registerProvider` проверяет `id`, непустые `kinds`, уникальность типов и
  фильтров; нарушение отклоняет активацию.
- Lifecycle вызывает `unregisterProviders()` при деактивации и при откате
  упавшей активации. Отключение сохраняет данные и индекс, но скрывает
  провайдера из выдачи и facet-ов.
- `reindex()` выполняется awaited при активации домена **до**
  `registerProvider`. Его ошибка прерывает активацию, runtime откатывает
  регистрации и уходит в safe mode; stale provider не остаётся доступным.
  Отдельной межплагинной reindex-команды с частичным успехом нет.
- Семантика JSON `metadata`-фильтров: `eq` — только точное совпадение
  строкового scalar; `contains` — подстрока строки или точный строковый
  элемент массива; object, number, boolean, null и отсутствующее поле не
  матчатся. SQLite и in-memory provider проверяются общим conformance-case.
- Реестр не читает namespace провайдера напрямую: только вызывает его
  объявленные методы.

Агрегатор `kanbaner.search`:

- принимает bounded `text`, `kinds`, `filters`, `limit`, `offset`;
- маршрутизирует запрос только к провайдерам с объявленными kind/filter;
- проверяет неизвестный kind и filter до раннего выхода без провайдеров:
  `VALIDATION_ERROR` не зависит от их наличия; обычный текст без провайдеров
  даёт пустую страницу;
- семантика metadata едина для SQLite и in-memory: `eq` — точное совпадение
  string scalar, `contains` — подстрока строки или точный строковый элемент
  массива; object/number/boolean/null/missing не матчатся;
- неизвестный kind, неизвестный filter и пустой текст дают `VALIDATION_ERROR`;
- дедуплицирует выдачу по `ResourceRef`, сортирует по `score` desc и `ref` asc,
  возвращает `hasMore`;
- не пропускает чужой `ResourceRef`, добавляя warning `foreign_ref`;
- при отказе одного провайдера возвращает остальную выдачу и warning
  `provider_failed`, при отказе всех — `DEPENDENCY_UNAVAILABLE`;
- при отсутствии активных провайдеров возвращает пустой результат без ошибки.

`kanbaner.search.query` экспортируется в UI/HTTP/MCP, `kanbaner.search.filters`
— только в UI/HTTP. Ручной OpenCode allowlist не строится из `exposure.mcp` и
не расширяется автоматически.

## 14. Экспорт в HTTP и MCP

По умолчанию команда и запрос не публикуются наружу.

Экспорт включается явно:

```json
{
  "exposure": {
    "ui": true,
    "http": true,
    "mcp": false
  }
}
```

### HTTP

- `http = true` означает доступность через общий command/query transport.
- Плагин не регистрирует собственные HTTP-маршруты в MVP.
- Аутентификация и лимиты выполняются ядром.
- Отдельный `/api/opencode/*` принадлежит composition root и является внутренним UI transport внешней интеграции, а не маршрутом плагина или command/query API. Он не экспортирует доменные операции, использует same-origin/client guard и не передаёт Bearer token в браузер.
- Схемы валидируются до вызова обработчика.

### MCP

- `mcp = true` означает автоматическое появление инструмента в `kanbaner-mcp`.
- Название инструмента строится детерминированно из command ID.
- Недопустимые символы заменяются, коллизии блокируют экспорт.
- Описание и JSON Schema берутся из метаданных.
- `risk = destructive` должен быть явно разрешён и помечен в описании.
- MCP не обходит ошибки, версии и идемпотентность контракта.
- `mcp = true` не даёт доступа к неэкспортированным командам и чужим данным.

Эти правила описывают универсальный discovery-driven `@kanbaner/mcp`. Ограниченный `kanbaner-mcp` из `@kanbaner/opencode` является отдельным ручным адаптером: его allowlist задаётся кодом интеграции, не строится из `exposure.mcp` и не меняется при добавлении новых доменных операций. Такая операция всё равно обязана иметь `exposure.http = true`; вызов идёт через общий `/api/v1` с теми же валидацией, версиями и идемпотентностью. Ручной allowlist не переиспользуется универсальным адаптером.

Метаданные ручного OpenCode allowlist содержат `name`, `operationId`, `risk` (`read` или `write`) и `requiresExpectedVersion`. Catalog `/api/opencode/catalog` отдаёт тот же список из 14 MCP tools вместе со стандартными built-in tools OpenCode, помеченными `source` (`builtin` или `mcp`); `operationId` и `requiresExpectedVersion` необязательны для built-ins. Панель показывает built-ins и Kanbaner MCP отдельными группами, поэтому UI не может разойтись с фактическим MCP tool list. Delete MCP tools в allowlist отсутствуют. По явному решению пользователя от 2026-11-20 built-in tools (`question`, `websearch`, `webfetch`, `read`, `glob`, `grep`, `edit`, `shell`, `subagent`, `skill`, `external_directory`) разрешены агенту `kanbaner` в `opencode.jsonc`; это не песочница и не расширяет ручной MCP allowlist. Сторонние MCP servers, Code Mode `execute` и wildcard allow для чужих tools не включаются.

### Запрещено

- экспортировать команду, которая обходит валидацию UI;
- создавать отдельную «серверную» реализацию операции для агентов;
- позволять MCP-адаптеру обращаться к базе данных;
- публиковать внутренние команды плагина без явного решения.

## 15. Версионирование и совместимость

### 15.1. Версии

| Объект | Формат |
|---|---|
| Plugin | SemVer |
| Host API | SemVer-диапазон |
| Contract | Идентификатор с major, например `.v1` |
| Command/query | Целое `version` |
| Event payload | Целое `contractVersion` |
| UI slot | Идентификатор контракта |

### 15.2. Совместимые изменения

- добавление необязательного поля;
- добавление новой команды;
- добавление нового события;
- добавление нового UI-вклада;
- добавление необязательного фильтра;
- ослабление ограничения без изменения смысла.

### 15.3. Несовместимые изменения

- удаление поля;
- изменение типа поля;
- изменение смысла существующего поля;
- новый обязательный аргумент;
- удаление команды или события;
- переименование resource type;
- изменение семантики `position`;
- удаление UI slot.

### 15.4. Правила

- Старые клиенты игнорируют неизвестные дополнительные поля.
- Плагин зависит от контракта, а не от точной версии чужой реализации.
- `requires` задаёт минимально необходимую реализацию, `consumes` — используемый контракт.
- Ядро поддерживает текущую major-версию Host API и документированный диапазон предыдущих.
- Устаревшие контракты получают срок поддержки и предупреждение в plugin manager.
- Plugin ID и command ID не переиспользуются после удаления.

## 16. Наблюдаемость

Каждая операция получает:

```text
requestId
traceId
source
pluginId
operationId
duration
result code
```

Правила:

- Вложенные вызовы сохраняют `traceId`.
- MCP-вызовы помечаются `source.type = mcp`.
- Ошибки плагинов содержат plugin ID и операцию.
- Содержимое заметок и секреты не пишутся в журнал.
- Plugin manager показывает последние ошибки активации и выполнения.

## 17. Тесты совместимости

Контракт считается реализованным, если проходят проверки:

1. Тестовый плагин регистрирует команду, запрос, событие, ресурс и UI-вклад.
2. Дублирующий command ID блокируется.
3. Плагин с отсутствующей зависимостью не активируется.
4. Циклическая зависимость блокируется.
5. Миграции применяются один раз и в правильном порядке.
6. Ошибка активации переводит плагин в safe mode.
7. Отключение плагина сохраняет данные.
8. Событие публикуется только после коммита.
9. Повторная обработка события не создаёт дубль.
10. Ссылка на удалённый ресурс корректно разрешается как отсутствующая.
11. HTTP-вызов неэкспортированной команды отклоняется.
12. MCP-адаптер видит только `mcp = true`.
13. Несовместимая версия контракта блокирует активацию.
14. Нарушение правил импорта обнаруживается автоматической проверкой.
15. Ошибка рендера одного UI-плагина не роняет shell.
16. Storage Provider Registry отклоняет дублирующий `backendId` и отдаёт capabilities.
17. Storage Provider Conformance Suite проходит на SQLite и in-memory provider.
18. Доменный код не содержит SQL и импорта драйвера БД.
19. Несовпадение checksum миграции блокирует активацию.
20. Асинхронный provider с задержками проходит conformance suite и не выявляет синхронных предположений в доменном коде.
21. Транзакция коммитится после завершения async callback и откатывается при rejected Promise.
22. Параллельные write-транзакции сериализуются и не перемешиваются.
23. Публичные ID генерируются до записи, а UTC-время сохраняется без сдвига.
