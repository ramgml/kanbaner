# План реализации

- Статус: принят
- Дата: 2026-11-06

План построен вокруг вертикальных срезов. Каждый этап заканчивается проверяемым результатом и не требует временного обхода контракта плагинов.

## Этап 0. Спецификации

**Результат:** зафиксированы продукт, архитектура, контракт, технологический стек, процесс разработки и порядок работ.

**Готово, когда:**

- решения не противоречат друг другу;
- границы MVP перечислены явно;
- критерии готовности проверяемы;
- модель веток, версионирование и release-процесс зафиксированы;
- отложенные решения не влияют на архитектурные границы.

## Этап 1. Ядро и SDK

**Цель:** доказать plugin-модель на минимальном приложении.

### Deliverables

- каркас TypeScript-приложения и рабочий процесс разработки согласно `technology-stack.md`;
- application composition root в `apps/web` без доменной логики;
- package `@kanbaner/plugin-sdk`;
- package `@kanbaner/kernel`;
- манифесты и валидация;
- разрешение зависимостей и проверка циклов;
- реестр команд и запросов;
- контекст вызова;
- шина событий после коммита;
- `ResourceRef` и сервис связей;
- асинхронный Storage Provider Registry, доменные Store-контракты, capabilities и bootstrap-порядок;
- SQLite Storage Provider, кроссплатформенный data directory и singleton;
- runner миграций и таблицы состояния плагинов;
- UI shell с базовыми слотами;
- минимальный plugin manager;
- safe mode;
- тестовый плагин, использующий все основные точки расширения.

### Готово, когда

- ядро запускается с одним тестовым плагином;
- тестовый плагин добавляет представление, команду, запрос, событие и поисковый провайдер;
- дублирующий ID блокируется;
- отсутствующая зависимость блокирует только зависимый плагин;
- ошибка активации не мешает запуску ядра;
- миграции не применяются повторно;
- Storage Provider открывается и проходит health check до миграций плагинов;
- публичные операции хранилища асинхронны;
- транзакция монополизирует соединение, а rejected Promise приводит к rollback;
- ID генерируются до записи, время хранится в UTC;
- SQLite работает без внешней СУБД и Docker на Linux и Windows;
- чистая установка не содержит deprecated-зависимостей и unmet peer dependencies;
- `better-sqlite3` устанавливается и открывает базу на обеих ОС;
- Storage Provider Conformance Suite проходит на SQLite и in-memory provider, включая provider с асинхронными задержками;
- автоматический тест запрещает импорт внутренностей ядра и чужих плагинов.

## Этап 2. Домен задач и список

**Цель:** получить повседневно используемый набор задач.

### Deliverables

- плагин `kanbaner.tasks`;
- проекты, задачи, подзадачи, приоритеты, сроки и теги;
- версии задач и обработка конфликтов;
- команды создания, изменения, завершения и удаления;
- запросы списка и деталей;
- события задач;
- представление списка в едином UI-плагине `kanbaner.projects`;
- фильтры и сортировка;
- формы создания и редактирования;
- боковая панель деталей задачи.

### Готово, когда

- задача проходит полный жизненный цикл;
- подзадачи ограничены одним уровнем;
- конфликт версий не перезаписывает изменение;
- список обновляется после команд;
- отключение списка не влияет на `tasks`;
- доменные тесты покрывают валидацию и переходы статусов.

## Этап 3. Канбан

**Цель:** добавить основное визуальное представление задач.

### Deliverables

- представление канбана в том же UI-плагине `kanbaner.projects`;
- пользовательские колонки проекта из домена `tasks`: создание, переименование,
  reorder и удаление с переносом задач;
- три default-колонки нового проекта и legacy-набор из четырёх колонок с
  Backlog для существующих проектов;
- ленивая материализация отсутствующей legacy-колонки при явном `status`
  старого клиента, чтобы fixed UI из четырёх статусных колонок продолжал
  работать до динамического рендера пользовательских колонок;
- перемещение между колонками через `columnId` при сохранении совместимости
  старых клиентов по `status`;
- изменение порядка карточек в области `(projectId, columnId)`;
- несколько открытых и несколько Done-колонок;
- оптимистичное обновление с обработкой конфликтов;
- доступная альтернатива drag-and-drop;
- мобильная горизонтальная прокрутка.

### Готово, когда

- порядок карточек и колонок сохраняется после перезапуска;
- перемещение выполняется через публичную команду `tasks`;
- ошибка перемещения возвращает карточку в корректное состояние;
- удаление колонки переносит задачи атомарно и не теряет данные;
- отключение канбана не влияет на `tasks`, список и API;
- канбан не импортирует внутренние модули `tasks`.

## Этап 4. Заметки и связи

**Цель:** связать знания с рабочими задачами.

### Deliverables

- плагин `kanbaner.notes`;
- визуальный CommonMark/GFM-редактор и автосохранение с конфликтом версий;
- самостоятельные заметки и дерево вложенных страниц с move/reorder;
- избранное, недавние страницы и полнотекстовый поиск;
- локальные растровые изображения и экспорт самодостаточного Markdown;
- связь заметки с задачей, проектом и другими ресурсами;
- переход по `ResourceRef` через generic resource opener;
- обработка удалённых ресурсов;
- публичный слот связанных заметок в деталях задачи;
- удаление и восстановление связей.

### Готово, когда

- заметка связывается с несколькими задачами;
- заметка открывается из связанной задачи;
- удаление задачи не оставляет рабочую ссылку;
- `notes` работает без активного `tasks`;
- заметки не обращаются к таблицам задач.

## Этап 5. Поиск

**Цель:** находить задачи и заметки по содержимому.

### Deliverables

- плагин `kanbaner.search`;
- регистрация поисковых провайдеров;
- полнотекстовый поиск FTS5 с `unicode61`;
- проверка кириллицы, регистра, фраз и prefix-запросов на Linux и Windows;
- обновление индекса по событиям;
- полная переиндексация;
- фильтры по типу, проекту, статусу и тегам;
- переход к найденному ресурсу.

### Готово, когда

- поиск находит задачу и заметку по тексту;
- отключённый доменный плагин не попадает в результаты;
- пропущенное событие исправляется переиндексацией;
- поиск не требует embeddings и внешнего сервиса;
- новый тестовый плагин добавляет поисковый провайдер без правок ядра.

## Этап 6. HTTP API

**Цель:** предоставить стабильный машинный интерфейс.

### Deliverables

- `/api/v1/health`;
- `/api/v1/discovery`;
- command/query transport;
- разрешение `ResourceRef`;
- `Authorization: Bearer`;
- `X-Request-Id`;
- `Idempotency-Key`;
- JSON Schema-валидация;
- структурированные ошибки;
- ограничение доступа к неэкспортированным операциям;
- привязка сервера к localhost по умолчанию;
- пакет `@kanbaner/cli` с универсальными и доменными командами для агентов;
- JSON-вывод, input из файла/stdin, idempotency и стабильные коды выхода CLI;
- интеграционные тесты API и CLI.

### Готово, когда

- валидный токен выполняет экспортированную команду;
- запрос без токена отклоняется;
- неэкспортированная команда недоступна;
- повтор с тем же idempotency key не создаёт дубль;
- конфликт версий возвращает `VERSION_CONFLICT`;
- discovery показывает совместимые операции и схемы;
- CLI выполняет универсальную и доменную операцию через HTTP без доступа к базе.

## Этап 7. MCP-адаптер

**Цель:** подключить внешних агентов без доступа к базе.

### Deliverables

- отдельный package `@kanbaner/mcp`;
- stdio-транспорт;
- чтение discovery;
- генерация инструментов из `exposure.mcp`;
- валидация входа и выхода;
- конфигурация URL и токена;
- понятные ошибки недоступного API;
- защита от коллизий имён;
- документация подключения;
- отдельный `@kanbaner/opencode` с глобальной панелью, catalog моделей текущего Service и NDJSON streaming;
- ограниченный `kanbaner-mcp` без delete/shell/filesystem, с `expectedVersion` и `Idempotency-Key`.

### Готово, когда

- MCP-клиент получает список задач;
- MCP-клиент создаёт задачу и заметку;
- неэкспортированные команды не видны;
- адаптер не подключается к базе данных;
- остановка MCP не влияет на приложение;
- интеграционный тест покрывает успешный вызов и недоступный API;
- OpenCode panel работает на desktop/mobile, stream завершается и отменяется, catalog и ошибки не раскрывают секреты;
- ограниченный MCP создаёт и обновляет ресурсы через HTTP API без доступа к базе.

## Этап 8. Плагин-менеджер и стабилизация

**Цель:** сделать plugin-модель пригодной для повседневной эксплуатации.

### Deliverables

- полноценный экран управления плагинами;
- установка из локального каталога;
- включение и отключение;
- отображение версий, зависимостей и ошибок;
- safe mode с диагностикой;
- защита UI границами ошибок;
- резервное копирование SQLite через online `.backup()` и восстановление;
- документация по установке и запуску на Linux и Windows;
- проверка доступности;
- end-to-end сценарии;
- профилирование основных запросов;
- исправление найденных дефектов;
- подготовка релиза `0.1.0` по `development-workflow.md`;

### Готово, когда

- новые плагины ставятся без изменения ядра;

- резервная копия восстанавливается на чистой базе;

## Предложения по OpenCode UI/UX после MVP

Дата фиксации: 2026-11-22. Это кандидаты для отдельных задач, а не новый объём
`v0.1.0` или `v0.1.0-rc.0`. Существующая кнопка `+` для нового задания и новой
OpenCode-сессии сохраняется без изменений.

Приоритет реализации:

1. **Статусы и ошибки конкретного prompt.** Показывать понятные этапы
   `Подключаемся → Выполняется → Завершаем → Готово`; при неподтверждённом
   результате предлагать «Проверить статус», а не автоматически повторять prompt.
   Ошибка и retry должны относиться к конкретному ходу и не доминировать над уже
   полученным ответом.
2. **Компактное представление tool calls.** По умолчанию показывать только
   иконку, название, состояние и длительность; вход, вывод и технические детали
   раскрываются по требованию. Последовательные вызовы одного этапа можно
   группировать, не превращая чат в серверный лог.
3. **Прокрутка без потери позиции чтения.** Автоматически следовать за новым
   ответом только когда пользователь уже находится внизу. Если он читает выше,
   сохранять позицию и показывать кнопку «К новому сообщению».
4. **Работа с кодом и черновиками.** Добавить копирование code blocks и
   сохранение черновика composer отдельно для каждой OpenCode-сессии.
5. **Управление сессиями.** Рассмотреть список последних сессий и возврат к ним
   без потери контекста. Создание, переименование и удаление сессий должны быть
   отдельными явными операциями; удаление не предполагается по умолчанию.

Перед реализацией каждого пункта нужно определить границы задачи, доступность,
мобильное поведение и regression-тесты. Изменения не должны ослаблять redaction,
session ownership, abort/generation semantics или canonical verification.

## Definition of Done для MVP

- Все критерии из `product-mvp.md` выполнены.
- `plugin-contract.md` реализован и покрыт контрактными тестами.
- Ядро не содержит доменной логики задач и заметок.
- Канбан, список, заметки и поиск являются отдельными плагинами.
- HTTP API использует те же команды, что интерфейс.
- MCP-адаптер не имеет доступа к базе данных.
- Приложение работает на Linux и Windows без Docker и внешней СУБД.
- Typecheck, линтер и автоматические тесты проходят на обеих ОС.
- Документация запуска, SQLite backup и восстановления актуальна.
- Релиз `0.1.0` прошёл release-проверки и опубликован из тега `v0.1.0`.
- Нет известных критических дефектов потери данных.

## Риски и меры

| Риск | Мера |
|---|---|
| Ядро стало слишком сложным | Каждая возможность добавляется только под конкретный встроенный плагин |
| Контракт зафиксирован слишком рано | Версия v1 минимальна; расширения проходят правила совместимости |
| UI-плагин ломает shell | Границы ошибок и safe mode |
| Плагины неявно зависят друг от друга | Автоматическая проверка импортов и контрактные тесты |
| Поиск отстаёт от данных | События, версии ресурсов и полная переиндексация |
| SQLite блокирует писателей при долгой транзакции | Короткие write-транзакции, `busy_timeout`, bounded retry и тесты конкурентного доступа |
| Нативный модуль `better-sqlite3` не устанавливается на одной из ОС | Обязательный install-тест на Linux и Windows, prebuilt binaries и fallback-план сборки |
| Синхронный API SQLite протекает в доменный код | Асинхронные Store-контракты и conformance suite на provider с задержками |
| Async-транзакции перемешиваются на одном соединении | Сериализация write-транзакций, rollback по rejected Promise и тест с задержкой |
| Недоверенный плагин получает доступ к данным | Явное ограничение: только доверенные локальные плагины |
| Потеря данных при миграции | Транзакции, online backup, restore и запрет изменения применённых миграций |

## Что не делать в MVP

- Docker и внешний сервер БД;
- размещение базы на сетевой файловой системе;
- автоматический перенос существующих данных между Storage Provider;
- marketplace и удалённую установку плагинов;
- песочницу и RPC между процессами;
- event sourcing и гарантированную доставку событий;
- отдельный поисковый сервис;
- embeddings и семантический поиск;
- REST-фасад поверх команд;
- настраиваемые рабочие процессы;
- аккаунты и совместную работу.

Эти возможности не должны блокировать MVP и могут быть добавлены отдельными плагинами или новыми версиями контракта.
