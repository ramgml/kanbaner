# Продуктовая спецификация MVP

- Статус: принято
- Дата: 2026-11-06

## 1. Цель

Дать одному пользователю локальный инструмент для управления задачами и заметками, который остаётся простым в использовании, но расширяется плагинами без переписывания ядра.

MVP должен доказать три вещи:

1. Плагинная архитектура пригодна для повседневной работы, а не только для демонстрации.
2. Доменные плагины можно комбинировать через стабильный контракт.
3. Внешний агент может работать с данными через API и MCP, не получая прямого доступа к базе.

## 2. Пользователь и условия работы

- Один пользователь на установку.
- Регистрация, вход и разграничение прав отсутствуют.
- Приложение открывается в браузере на компьютере или мобильном устройстве.
- Поддерживаемые ОС MVP: Linux и Windows.
- Данные хранятся в локальном SQLite в режиме WAL.
- Внешний сервер БД, Docker и TCP-порт не требуются.
- По умолчанию сервер доступен только на localhost.
- Запуск в локальной сети допустим только при доверии ко всем устройствам в сети.
- Для HTTP API используется отдельный локальный токен.

## 3. Продуктовые принципы

1. **Plugin-first.** Канбан, список, заметки и поиск являются плагинами.
2. **Разделение домена и представления.** Домен задач не зависит от канбана или списка.
3. **Ядро не знает предметную область.** В ядре нет понятий задачи, заметки или Markdown.
4. **Единый контракт.** UI, HTTP API и MCP используют одни и те же команды и запросы.
5. **Локальность.** Ядро не содержит ИИ и обязательных облачных зависимостей. Необязательная OpenCode-интеграция использует внешний Service и только уже настроенную пользователем конфигурацию провайдеров.
6. **Предсказуемость.** Плагин можно отключить, не теряя его данные.
7. **Расширяемость без патча ядра.** Типовая новая функция реализуется отдельным плагином.

## 4. Объём MVP

### Включено

| Область | Возможности |
|---|---|
| Плагинная система | Манифесты, зависимости, активация, отключение, миграции, safe mode |
| Хранилище | SQLite WAL, Storage Provider, FTS5, online backup, Linux и Windows |
| Задачи | Проекты, задачи, один уровень подзадач, приоритет, срок, теги, описание |
| Статусы | `Backlog`, `To do`, `In progress`, `Done` |
| Представления | Канбан и список |
| Заметки | Markdown, самостоятельные и проектные заметки |
| Связи | Универсальные связи заметок с задачами и другими ресурсами |
| Поиск | Полнотекстовый поиск по задачам и заметкам, фильтры |
| Плагин-менеджер | Список плагинов, включение, отключение, диагностика |
| HTTP API | Команды, запросы, обнаружение возможностей, локальный токен |
| MCP | Необязательный stdio-адаптер поверх разрешённых HTTP-команд |
| OpenCode | Необязательная панель чата, модели текущего Service, streaming и полный built-in toolset с ограниченным Kanbaner MCP |
| Установка плагинов | Ручное размещение в локальном каталоге |

### Не включено

- аккаунты, команды и совместная работа;
- роли и права пользователей;
- собственные модели, ИИ-логика в ядре и embedded OpenCode SDK;
- управление облачными AI-провайдерами и их секретами из Kanbaner, embeddings и семантический поиск;
- мобильные и десктопные приложения;
- offline-режим и синхронизация;
- публичный хостинг и multitenancy;
- marketplace и автоматическая установка плагинов;
- календарь, повторяющиеся задачи и напоминания;
- уведомления и внешние интеграции;
- настраиваемые рабочие процессы;
- многоуровневые подзадачи;
- автоматический перенос существующих данных при смене Storage Provider;
- жёсткая изоляция сторонних плагинов.

## 5. Основные сценарии

1. Пользователь создаёт проект, при необходимости настраивает колонки, добавляет задачи и проводит их по колонкам на канбане.
2. Пользователь переключается на список, фильтрует задачи по проекту, колонке, статусу, сроку и тегу.
3. Пользователь создаёт заметку в Markdown и связывает её с несколькими задачами.
4. Пользователь ищет заметку по тексту и переходит к связанным задачам.
5. Пользователь временно отключает плагин канбана; задачи, список и API продолжают работать.
6. Внешний агент через MCP получает список задач, создаёт задачу и добавляет заметку.
7. При падении одного плагина ядро запускается в safe mode и показывает диагностику.
8. Пользователь устанавливает дополнительный плагин в локальный каталог и включает его без изменения ядра.
9. Пользователь явно открывает панель OpenCode, выбирает модель текущего Service и получает streaming-ответ; агент создаёт или обновляет ресурс только через ограниченный MCP.

## 6. Функциональные требования

### 6.1. Задачи и колонки

- Задача принадлежит проекту.
- Задача имеет заголовок, Markdown-описание, колонку, статус, приоритет, срок и позицию.
- Подзадача может иметь только один уровень вложенности.
- Завершение задачи фиксирует время завершения.
- Позиция задачи уникальна в пределах проекта и колонки.
- Каждая задача имеет монотонную версию для защиты от конфликтующих изменений.
- Удаление проекта требует явного подтверждения и удаляет его задачи и колонки.
- Удаление задачи удаляет её подзадачи согласно правилам плагина `tasks`.
- Колонка принадлежит проекту, имеет заголовок, тип (открытая или Done), позицию и монотонную версию.
- Проект и колонка могут иметь необязательный цвет из фиксированной доменной палитры; отсутствие цвета означает стандартное оформление.
- Приоритет задачи определяет цветовой акцент карточки без отдельного пользовательского поля цвета.
- Проект может содержать несколько открытых и несколько Done-колонок.
- Новый проект атомарно получает три исходные колонки: ToDo, In Progress и Done.
- Проект, созданный до появления пользовательских колонок, получает Backlog, To do, In progress и Done; его задачи детерминированно привязываются к колонкам по прежнему статусу.
- Явный legacy-статус (`backlog`, `todo`, `in_progress`, `done`) при создании или перемещении задачи лениво создаёт недостающую колонку в той же транзакции, чтобы старый клиент продолжал работать; опубликованное после коммита событие сообщает о созданной колонке.
- `status` задачи остаётся совместимым зеркалом типа колонки: Done-колонка даёт `done`, открытая — `in_progress` (legacy-значения `backlog`/`todo` сохраняются в исходных колонках).
- Переименование и перестановка колонок не меняют задачи.
- Удаление колонки требует явного подтверждения и атомарно переносит все её задачи в выбранную колонку того же проекта; перенос дописывается после максимальной позиции target. Нельзя удалить последнюю открытую колонку, последнюю Done-колонку, саму себя и колонку другого проекта.
- В проекте всегда остаётся хотя бы одна открытая и хотя бы одна Done-колонка.
- Завершение задачи переводит её в первую Done-колонку проекта.

### 6.2. Представления

- Канбан показывает пользовательские колонки проекта в сохранённом порядке.
- Перемещение карточки меняет колонку и позицию.
- Список поддерживает фильтры по колонке, статусу и сортировку.
- Канбан и список работают через публичные запросы и команды `tasks`.
- Название и описание карточки редактируются на своих местах; клик вне редактора сохраняет изменения, `Escape` отменяет их, отдельные кнопки Save/Cancel не требуются.
- В режиме чтения описание карточки и его подсказка показывают CommonMark/GFM через безопасный React-рендер; raw HTML не выполняется, а ссылки не запускают inline-редактор.
- Меню колонки закрывается по выбору действия, `Escape` и нажатию вне меню.
- Массовые перенос и удаление карточек выполняются атомарными командами домена; удаление требует подтверждения.
- Цветовые образцы имеют текстовые доступные имена и не полагаются только на цвет для передачи состояния.
- Отключение представления не влияет на данные задач.

### 6.3. Заметки

- Заметка имеет заголовок, Markdown-содержимое, версию, родителя и позицию среди
  siblings; корневые и вложенные страницы образуют дерево без циклов.
- Визуальный блочный редактор поддерживает CommonMark/GFM, side menu с
  добавлением и drag handle, formatting toolbar, slash-действия и вложенность.
  Каноническим форматом остаётся Markdown; блочное представление не сохраняется,
  его синтаксическое оформление может нормализоваться при round-trip, а raw HTML
  не выполняется.
- Заголовок и содержимое автосохраняются через partial update с
  `expectedVersion`. Конфликт версий не перезаписывает локальный черновик.
- Заметка может существовать без проекта и без активного плагина задач.
- Избранное и время последнего открытия хранятся отдельно и не увеличивают
  версию содержимого. Доступны список недавних и полнотекстовый поиск.
- Связь заметки с задачей, проектом или другим ресурсом хранится как
  универсальная ссылка на ресурс; переход выполняется через `ResourceRef`.
- Локальные PNG/JPEG/GIF/WebP до 5 MiB хранятся отдельно от текста и вставляются
  через `attachment://<id>`. Экспорт создаёт самодостаточный `.md` с data URL.
- Удаление ветки требует явного подтверждения по свежему preview и каскадно
  очищает потомков, вложения, активность, связи и поисковый индекс. Ожидаемый
  размер поддерева проверяется атомарно при удалении.
- Удаление вложения выполняется только явным действием после сохранения и
  проверки, что файл больше не используется; автоматической очистки во время
  редактирования нет.
- Удаление связанной сущности не должно оставлять рабочую ссылку на
  несуществующий ресурс.

### 6.4. Поиск

- Ищет по заголовкам и содержимому задач и заметок.
- Провайдеры поиска регистрируются плагинами.
- Поддерживает фильтр по типу ресурса и проекту.
- Возвращает ссылки на найденные ресурсы.
- После включения плагина доступна полная переиндексация его данных.
- Поиск не требует векторной базы и embeddings.

### 6.5. Плагины

- Плагин имеет уникальный идентификатор, версию и диапазон совместимости с ядром.
- Зависимости проверяются до активации.
- Циклические зависимости блокируются.
- Миграции плагина применяются до активации.
- Отключение сохраняет данные.
- Ошибка активации не должна блокировать запуск ядра.
- Встроенные плагины загружаются тем же способом, что и дополнительные.
- Ядро не импортирует внутренние модули плагинов.

### 6.6. HTTP API и MCP

- API использует те же команды и запросы, что интерфейс.
- Токен передаётся в `Authorization: Bearer`.
- MCP-адаптер не имеет доступа к базе данных.
- Универсальный MCP публикует только команды с `exposure.mcp = true`. Отдельный OpenCode MCP использует явно зафиксированный ручной allowlist и не расширяет его автоматически по метаданным.
- Разрушительные операции не маскируются под универсальное обновление.
- MCP является опциональным процессом и не влияет на работу интерфейса.

### 6.7. OpenCode-интеграция

- Интеграция реализована отдельным плагином `@kanbaner/opencode` и не добавляет ИИ-логику в ядро.
- Панель закрыта по умолчанию и запускает подключение к Service только после явного открытия пользователем. На desktop она находится справа, на мобильном занимает весь экран; состояние панели и ID последней сессии сохраняются локально.
- Используется текущий OpenCode Service через `Service.ensure()` и `@opencode/client`; embedded SDK не применяется.
- Каталог содержит только публичные ID, названия, activation и variants моделей/провайдеров. Provider settings, credentials, headers и request body не покидают сервер.
- Создаются только сессии агента `kanbaner` с `metadata.source=kanbaner`. Чтение, model switch и prompt других сессий запрещены.
- Prompt передаёт streaming events через NDJSON: `connected`, `delta`/`text`, `tool`, служебный `finalizing` и ровно один terminal. Перед canonical lookup gateway выпускает `finalizing`; сам по себе он не подтверждает результат и не является terminal. Каждый prompt получает client-generated stable turn ID (`^msg_[A-Za-z0-9_-]{8,64}$`), который передаётся в `session.prompt({id})` и не зависит от ordinal. Если Service вернул другой admitted ID, gateway выпускает `kanbaner.turn.admitted` и связывает client ID с admitted.
- Исход prompt подтверждается по canonical history точного turn ID, а не по типу upstream-события и не по UI-тексту. Если результат не подтверждён, панель показывает «Результат не подтверждён», сохраняет streamed-текст и предлагает ручную кнопку «Проверить статус». Автоматический refresh или повтор prompt в этом состоянии не выполняются; ручная проверка использует существующий `GET /api/opencode/session/{sessionID}?turnID={turnID}` и возвращает серверный `outcome` (`done`, `error`, `cancelled`, `pending`, `missing`) без нового prompt. Status query принимает client ID через alias-map и фактический admitted `SessionMessageID` Service (вне strict `msg_` pattern) с отдельной bounded-валидацией; canonical history заменяет streamed-сообщения только при `done`.
- После возможного admission ошибка никогда не повторяется автоматически: rejected `fetch`, rejected `client.session.prompt()`, неизвестный сбой и оборванный поток дают unconfirmed с `retryable:false`; при rejected prompt сначала выполняется bounded canonical lookup по stable turn ID. Автоматический повтор разрешён только для сбоя до вызова prompt (408, 429, 5xx или `OpenCodeGatewayError` до первого streamed-события) и отправляет те же текст и файлы; 4xx и любая неопределённость после admission не повторяются. Остановка выполняется через `session.interrupt` и отмену HTTP-потока.
- К prompt можно прикрепить до 5 файлов общим размером до 8 MiB: UTF-8 text/code — до 1 MiB, каждый PNG/JPEG/GIF/WebP/PDF — до 5 MiB. Браузер читает файл через `FileReader` и отправляет `{name, mime, base64}`; сервер передаёт только inline `data:` URL в prompt выбранной модели. `file:` URL, произвольные server paths и чтение файлов с диска отсутствуют.
- Сервер проверяет канонический Base64, UTF-8 и сигнатуры image/PDF. Ошибки публичные и не содержат base64 или содержимого файлов; browser history получает только `name` и `mime`. Если выбранная модель не объявляет поддержку image/PDF-входа, панель показывает предупреждение, но не блокирует отправку prompt: вложение уходит как есть, а OpenCode/provider может заменить его служебной заметкой или отклонить.
- PNG/JPEG/GIF/WebP показывают preview в composer и сообщениях, включая восстановленную после перезагрузки историю. Для canonical вложения UI отдельно запрашивает binary preview по точным session/message/attachment index через same-origin UI transport; Base64 в history JSON не добавляется. При недоступности или невалидности canonical inline-источника отображается обычная карточка вложения.
- По явному решению пользователя от 2026-11-20 chat-агент `kanbaner` имеет полный доступ к стандартным built-in tools OpenCode: `question`, `websearch`, `webfetch`, `read`, `glob`, `grep`, `edit`, `shell`, `subagent`, `skill` и `external_directory`. `edit` покрывает `edit`/`write`/`patch`. Это не песочница: агент может читать и изменять локальные файлы, включая секреты и `.env`, выполнять shell с правами пользователя и обращаться к сети. Ограничение доступа к секретам, файлам и сети не гарантируется.
- Ручной MCP allowlist Kanbaner остаётся ограниченным: list/get/create/update/complete/move для проектов, задач и заметок. Delete MCP tools не регистрируются. Сторонние MCP servers, Code Mode `execute` и wildcard allow для чужих tools не включены.
- Раскрываемый catalog в панели показывает built-in tools и MCP tools отдельными группами с `risk` read/write; для MCP также показывается `expectedVersion`. Предупреждение «Полный доступ: интернет, файлы и shell» отображается внутри раскрытых деталей.
- Обновления принимают `expectedVersion`. Mutations получают `Idempotency-Key`, привязанный к идентичности MCP-вызова и экземпляра server, чтобы повтор запроса не дублировал запись, а новое намеренное создание с тем же input оставалось возможным.
- Секреты не записываются в `opencode.jsonc` и не передаются в браузер. Внутренний UI transport отделён от Bearer-защищённого машинного `/api/v1` и ограничен same-origin проверками и `x-kanbaner-client: ui`.
- Недоступность OpenCode Service не влияет на задачи, заметки, навигацию и остальные плагины.

## 7. UX-требования

### Компьютер

- Слева находится навигация по проектам и разделам.
- В центре отображается канбан, список или редактор заметки.
- Детали задачи и связанные заметки открываются в боковой панели.
- Необязательный чат OpenCode открывается в глобальной правой панели.
- Плагины добавляют пункты навигации и представления через слоты ядра.

### Мобильный браузер

- Основная навигация находится снизу.
- Канбан прокручивается по горизонтали.
- Редактор задачи и заметки открывается на весь экран.
- Панель OpenCode в открытом состоянии занимает весь экран и имеет доступную кнопку закрытия.
- Основные операции доступны без drag-and-drop.
- Интерфейс не требует наведения мыши.

### Общие требования

- Все основные действия доступны с клавиатуры.
- Формы показывают ошибки валидации рядом с полями.
- Конфликт версий объясняется пользователю и не приводит к молчаливой потере изменений.
- Недоступный плагин не должен скрывать остальные разделы приложения.
- В глобальных настройках пользователь может выбрать масштаб интерфейса 90%,
  100%, 110% или 125%. Значение по умолчанию — 100%; выбор применяется сразу,
  сохраняется локально в браузере и восстанавливается при следующем запуске.

## 8. Критерии готовности MVP

1. Пользователь создаёт проект и проходит задачей все четыре статуса.
2. Канбан и список показывают согласованные данные.
3. Порядок карточек сохраняется после перезапуска.
4. Заметка создаётся, редактируется и связывается с несколькими задачами.
5. Полнотекстовый поиск находит задачу и заметку по содержимому.
6. Отключение `kanban` не ломает `tasks`, список и API.
7. Отключение `notes` не затрагивает данные задач.
8. Ошибка тестового плагина запускает ядро в safe mode.
9. Тестовый плагин добавляет представление, команду и поисковый провайдер без изменений ядра.
10. HTTP-клиент с валидным токеном выполняет разрешённую команду.
11. MCP-клиент получает список задач и создаёт заметку.
12. Перезапуск приложения не приводит к потере данных или повторному применению миграций.
13. Приложение запускается и проходит базовые сценарии на Linux и Windows без Docker и внешней СУБД.

## 9. Ограничения безопасности

- Интерфейс не имеет аутентификации, поэтому не должен быть доступен из недоверенной сети.
- API защищён токеном, но все валидные токены имеют полный доступ к разрешённым командам.
- Плагины выполняются как доверенный код и потенциально могут обойти декларативные ограничения.
- Секреты не попадают в браузер, журналы и ответы API; ошибки OpenCode и провайдеров возвращаются через публичные стабильные сообщения без upstream response и headers.
- Удаление данных выполняется только явной командой.
- Резервное копирование SQLite выполняется через online `.backup()` и остаётся ответственностью пользователя.

## 10. Критерии успеха архитектуры

- Новое представление задач создаётся отдельным плагином без правок ядра и `tasks`.
- Новый тип ресурса связывается с заметками через `ResourceRef`.
- Новый плагин публикует MCP-инструменты через метаданные команд.
- Обновление UI-плагина не требует миграции ядра.
- Контракт плагинов документирован и покрыт тестами совместимости.
