# AGENTS.md

Правила для агентов, работающих с репозиторием Kanbaner.

## 1. Назначение проекта

Kanbaner — локальная однопользовательская система управления задачами и заметками с адаптивным веб-интерфейсом.

Система строится как минимальное plugin-ядро:

- задачи, канбан, список, заметки и поиск являются плагинами;
- встроенные и дополнительные плагины используют один публичный SDK;
- ядро предоставляет инфраструктуру, но не содержит доменной логики;
- внешние агенты работают через HTTP API и необязательный MCP-адаптер;
- встроенного ИИ нет.

## 2. Язык и стиль работы

- Общайся с пользователем по-русски, если он не попросил иначе.
- Новые спецификации пиши по-русски.
- Код, имена типов, команд и таблиц — на английском.
- Ссылайся на конкретные файлы и пути.
- Не скрывай ошибки, конфликты требований и незавершённые проверки.
- Не расширяй задачу без необходимости.

## 4. Архитектурные инварианты

- Установка локальная и однопользовательская.
- Регистрации, аккаунтов и ролей нет.
- Основное хранилище — SQLite в режиме WAL.
- Storage backend подключается как провайдер; доменные плагины работают через Store-контракты.
- Внешний сервер БД, Docker и TCP-порт не используются.
- Поддерживаемые ОС MVP: Linux и Windows.
- Обращения доменных и UI-плагинов к хранилищу идут через Storage Provider Registry.
- Сервер по умолчанию слушает localhost.
- Ядро не содержит понятий задачи, проекта, заметки, статуса или Markdown.
- Домен `tasks` не зависит от канбана или списка.
- `notes` не зависит от `tasks`; связи выражаются через `ResourceRef`.
- Все встроенные функции загружаются через plugin-механизм.
- Плагины считаются доверенным локальным кодом.
- Жёсткая песочница, marketplace и удалённая загрузка кода не входят в MVP.
- Встроенный ИИ, embeddings и семантический поиск не входят в MVP.
- MCP является внешним адаптером и не подключается к базе данных.
- Микросервисы и межплагинные транзакции не используются.

Любое изменение этих инвариантов требует явного решения пользователя и обновления спецификаций.

## 5. Правила разработки плагинов

### Границы

- Плагин зависит от `@kanbaner/plugin-sdk`, но не от `@kanbaner/kernel`.
- Плагин не импортирует внутренние модули другого плагина.
- Плагин не читает и не изменяет данные другого плагина.
- Плагин не манипулирует DOM другого плагина.
- Для перехода к чужому ресурсу используется `ResourceRef` и публичный API.
- Новую функцию сначала реализуй как плагин. Расширение ядра допустимо только для действительно общей инфраструктуры.

### Взаимодействие

Используй только публичные механизмы:

- команды — для изменений;
- запросы — для чтения;
- события — для реакции на уже выполненные изменения;
- `ResourceRef` — для ссылок между доменами;
- UI slots — для расширения интерфейса.

Не создавай скрытые связи через прямые импорты, общие глобальные объекты или чужие таблицы.

### Команды и запросы

- ID команды или запроса должен быть глобально уникальным и namespace-ированным.
- Вход и выход описываются JSON Schema.
- Команда валидирует аргументы до записи.
- Мутация выполняется в транзакции плагина.
- Частичный успех запрещён.
- Разрушительная операция должна быть отдельной командой с `risk = destructive`.
- Изменение версионируемой сущности принимает `expectedVersion`.
- Повторяемые операции агентов поддерживают `Idempotency-Key`.
- Команда не публикует событие до успешного коммита.

### События

- Публикуй событие после коммита.
- Считай доставку best-effort.
- Обработчик события должен быть идемпотентным.
- Не используй событие как замену транзакции.
- Для собственного индекса предусматривай полную переиндексацию.
- Не полагайся на гарантированный порядок событий между разными ресурсами.

### UI

- Плагин регистрирует представления и вклады через SDK.
- Не изменяй чужие React-компоненты и DOM.
- Используй базовые слоты ядра или явно опубликованный слот другого плагина.
- Ошибка рендера плагина не должна ронять весь shell.
- Основные действия должны быть доступны с клавиатуры.
- Drag-and-drop не может быть единственным способом выполнить действие.

## 6. Контракт и совместимость

Контракт плагинов описан в `specs/plugin-contract.md`.

- Несовместимое изменение требует новой major-версии контракта.
- Добавление необязательного поля считается совместимым.
- Нельзя менять смысл существующего поля в пределах версии.
- Не переиспользуй удалённые command ID, event type и resource type.
- Обновляй контрактные тесты вместе с контрактом.
- Не создавай отдельную реализацию операции для HTTP или MCP.
- Экспорт в HTTP и MCP включается только явно.
- Для неясного API библиотеки проверяй актуальную документацию, не полагайся на память.
- Технологии, библиотеки и версии не дублируются в задачах; источник истины — `specs/technology-stack.md`.

## 7. Данные и миграции

- Каждый плагин владеет своим namespace данных.
- Доменный плагин работает через Store-контракт, а не через SQL или драйвер БД.
- В доменном коде запрещены SQL, `PRAGMA`, `MATCH`, `RETURNING`, имена таблиц и импорт драйвера БД.
- Публичные операции Storage Provider и Store-контрактов асинхронны; синхронный API драйвера не выходит за пределы провайдера.
- Транзакция монополизирует соединение; другие операции ждут и не выполняются внутри чужой транзакции.
- Отклонённый Promise внутри транзакции приводит к rollback.
- ID генерируются приложением или доменным плагином до записи, а не autoincrement конкретной СУБД.
- Время хранится в UTC; формат timestamp определяется Store-контрактом.
- Доступ к хранилищу выполняется только через Storage Provider Registry ядра.
- Соединением с базой управляет только Storage Provider; доменный или UI-плагин не открывает собственное соединение.
- MVP использует SQLite WAL через `better-sqlite3`.
- Провайдер обязан поддерживать транзакции; savepoints опциональны.
- Один экземпляр приложения владеет одним каталогом данных.
- Каталог данных задаётся через `KANBANER_DATA_DIR`; пути должны работать на Linux и Windows.
- Не открывай базу из MCP, браузера или доменного плагина.
- Online backup выполняется внутри приложения через Storage Provider; отдельный процесс не подключается к работающей базе.
- Offline restore CLI допускается только при остановленном приложении и только через код провайдера.
- Используй singleton при hot reload Next.js.
- Закрывай соединение при завершении приложения и выполняй WAL checkpoint.
- Не размещай базу на сетевой файловой системе.
- Резервное копирование выполняется только online через `.backup()`.
- Не копируй файлы базы, WAL и SHM работающего приложения.
- Восстановление выполняется только при остановленном приложении в новый каталог данных.
- Смена backend поддерживается для пустого хранилища; перенос существующих данных выполняется отдельным export/import и не входит в MVP.
- Миграции выполняются до активации новой версии.
- Storage Provider открывается и проверяется до применения миграций остальных плагинов.
- Применённую миграцию нельзя редактировать.
- Миграция должна быть атомарной и идемпотентной по факту применения.
- Миграция привязана к backend и не изменяет таблицы другого плагина.
- Отключение плагина не удаляет данные.
- Удаление данных выполняется только явной операцией с подтверждением.
- Перед несовместимой миграцией предусматривай резервное копирование.
- При удалении ресурса очищай универсальные связи и поисковый индекс.

## 8. HTTP API и MCP

- HTTP API использует те же команды и запросы, что интерфейс.
- Токен хранится только на сервере в `KANBANER_API_TOKEN`.
- Токен не попадает в клиентский JavaScript, журналы и ответы.
- Все операции, кроме health, требуют Bearer token.
- Неэкспортированная операция недоступна через API и MCP.
- MCP-адаптер не имеет доступа к базе данных.
- MCP-адаптер не содержит доменной логики.
- Разрушительные MCP-инструменты должны быть явными и помеченными.
- Недоступность MCP не влияет на работу приложения.

## 11. Параллельная разработка и worktree

### Когда использовать

- Если задача делится на 2+ независимых части и нужна параллельная разработка, загрузи skill `parallel-worktrees` и следуй его протоколу.
- Практически параллелить имеет смысл 3–7 задач. Небольшую или тесно связанную задачу выполняй последовательно.
- Критерий выбора — необходимость изоляции и параллельной работы, а не тип файлов.
- Документация может разрабатываться в worktree наравне с кодом, если затрагивает самостоятельный набор файлов, сопровождает feature-ветку или выполняется параллельно.
- Связанные документы с общими ссылками и терминологией выполняй одной задачей в одном worktree.
- Не создавай worktree только ради формальности или отдельного коммита.

### Владение файлами

- У каждого файла должен быть один владелец.
- Общие контракты, миграции, `package.json`, lock-файлы и точки интеграции относятся к одной задаче.
- Если два куска неизбежно меняют один файл, это один кусок работы.
- Worker не изменяет чужие worktree, ветки и незакоммиченные файлы.

### Организация

- Основной checkout принадлежит оркестратору.
- Worker работает в `.worktrees/<slug>` на ветке `feat/<slug>` или `fix/<slug>`, созданной от `dev`.
- Ветки `release/*` и `hotfix/*` создаёт только оркестратор.
- Перед началом проверь `git status` и `git worktree list`.
- Не запускай несколько агентов на один worktree.
- Оркестратор не пишет код в worktree worker-а без явной необходимости.

### Бриф worker-а

Бриф должен содержать:

- путь к worktree и имя ветки;
- список своих и запрещённых файлов;
- нужные интерфейсы и контракты;
- команду проверок;
- требование прогнать тесты;
- требование закоммитить только свои изменения.

### Правила worker-а

- Изменяй только файлы своей задачи.
- Соблюдай архитектурные границы и Plugin Contract.
- Не меняй общий контракт без согласования с оркестратором.
- Прогони проверки до коммита.
- Закоммить результат отдельной командой.
- Не выполняй `push`, `merge`, `rebase`, `reset --hard`, force-push и удаление чужих веток или worktree.
- Сообщи о коммите, результате проверок и оставшихся рисках.

### Интеграция

- Мерж, проверки на `dev`, push и удаление деревьев выполняет оркестратор.
- Базовой веткой интеграции задач является `dev`.
- `main` обновляется только через `release/*` и `hotfix/*` по `specs/development-workflow.md`.
- Используй `tools.gitops.merge_queue` с базой `dev`, если инструмент доступен; иначе следуй протоколу skill `parallel-worktrees`.
- После rebase и каждого merge тесты должны быть зелёными.
- Push выполняется только после успешной интеграции всей очереди.
- Удаляй только свои worktree и только после успешного мержа или явной отмены.
- Не удаляй worktree с незакоммиченными изменениями без подтверждения.

### Коммиты

- В обычной одиночной задаче не коммить и не пушь без явной просьбы пользователя.
- В режиме `parallel-worktrees` worker коммитит свои изменения по протоколу.
- Сообщение коммита: `<type>(<scope>): <краткое описание>`; scope необязателен.
- Допустимые типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`.
- Release-коммит: `chore: release vX.Y.Z`.
- Коммит и push выполняются разными командами.

### Эскалация человеку

Остановись и спроси человека при:

- смысловом конфликте архитектуры или Plugin Contract;
- изменении публичного API, схемы данных или продуктового поведения;
- красных тестах после двух попыток исправления;
- инфраструктурном сбое;
- необходимости force-push, `reset --hard` или удаления чужих коммитов;
- более чем трёх конфликтных файлах в одном merge.

Рутинные `add`, `commit`, `merge`, `push` и удаление своих worktree в рамках протокола не требуют отдельного разрешения.

## 12. Локальный трекер задач

Конкретные задачи разработки хранятся в `tasks/KAN-NNN-*.md`. Правила очереди описаны в `tasks/README.md`.

- Спецификации остаются источником архитектурных решений; не дублируй их в задачах.
- Только оркестратор выдаёт ID и меняет `status`, `owner`, `branch`, `worktree` и `blocked_by`.
- Worker не редактирует файл задачи в параллельном режиме.
- Worker создаёт отчёт `tasks/reports/KAN-NNN.md`.
- Новые задачи, найденные worker-ом, предлагаются в отчёте без назначения ID.
- Не начинай задачу с незакрытыми `blocked_by`.
- `in_progress` фиксируется до запуска worker-а.
- `review` означает, что есть коммит и пройденные проверки.
- `done` ставится только после мержа в `dev` и зелёных проверок на `dev`. Релиз в `main` не требуется для `done`.
- Не поддерживай общий `BOARD.md` вручную.
- При одиночной работе агент действует как оркестратор и может обновлять задачу по тем же правилам.
- Если задача противоречит спецификации, остановись и сообщи о расхождении.

## 13. Рабочий процесс

1. Прочитай задачу `tasks/KAN-NNN-*.md`, `tasks/README.md` и релевантные спецификации.
2. Проверь состояние репозитория и отсутствие чужих незакоммиченных изменений.
3. Определи границы задачи и затронутые контракты.
4. Если задача делится на независимые части, выбери режим worktree.
5. Реализуй минимальный вертикальный срез.
6. Добавь или обнови тесты.
7. Прогони typecheck, линтер и тесты.
8. Обнови документацию и `AGENTS.md`, если изменились правила или команды.
9. Заверши работу отчётом о результате и проверках.

## 14. Команды проекта

Требования: Node.js `24.22.2`, pnpm `12.18.0` через Corepack. Версии зафиксированы в
`package.json`, а `.npmrc` включает `engine-strict` и `strict-peer-dependencies`.

Подготовка окружения:

```bash
corepack enable
corepack prepare pnpm@12.18.0 --activate
```

Установка зависимостей:

```bash
pnpm install --frozen-lockfile --strict-peer-dependencies
```

Разработка и сборка:

```bash
pnpm dev
pnpm build
pnpm start
pnpm check:composition
```

Проверки:

```bash
pnpm typecheck
pnpm lint
pnpm lint:fix
pnpm format
pnpm format:check
pnpm test
pnpm test:watch
pnpm test:sqlite
pnpm check:imports
pnpm --filter @kanbaner/web test:e2e
pnpm storage:restore
pnpm check
```

`pnpm check` последовательно выполняет `format:check`, `lint`, `typecheck`, `test` и `build`.
E2E-тесты запускаются в production shell через Playwright Chromium. Миграции Storage Provider
применяются автоматически при bootstrap; offline restore выполняется только при остановленном
приложении через `pnpm storage:restore`.

Все команды кроссплатформенные и не требуют bash, Docker или установленного сервера БД.

## 15. Критерии завершённой задачи

- Требование пользователя выполнено.
- Архитектурные инварианты не нарушены.
- Публичные контракты не изменены скрыто.
- Тесты и проверки пройдены или явно описаны как недоступные.
- Данные и чужие изменения не повреждены.
- Документация соответствует коду.
- Итоговый отчёт содержит изменённые файлы, проверки и известные ограничения.
