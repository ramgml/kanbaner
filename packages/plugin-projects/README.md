# @kanbaner/plugin-projects

Единый UI-плагин рабочего пространства проектов Kanbaner. Он объединяет
прежние `plugin-kanban` и `plugin-task-list`: переключение проектов в sidebar,
доску одного проекта, список задач, мобильный bottom sheet и переключатель
`Список / Канбан`.

## Манифест

- Plugin ID: `kanbaner.projects`
- Версия: `0.1.0`
- Зависит от: `kanbaner.tasks` `^0.1.0`
- Потребляет: `kanbaner.tasks.commands.v1`, `kanbaner.tasks.queries.v1`
- Предоставляет: `kanbaner.projects.ui.v1`
- Разрешения: `commands`, `events`, `ui`
- Entrypoints: серверный `dist/index.js`, клиентский `dist/ui.js`

Плагин не владеет данными. Проекты, задачи и сводки читаются и изменяются
только через публичные операции `kanbaner.tasks`. Отключение UI-плагина не
удаляет данные и не влияет на API.

## Поведение

- В shell есть один пункт «Проекты». Он ведёт на `/view/projects?entry=1`;
  обзор восстанавливает последнее представление проекта из `localStorage`
  (`kanbaner.projects.lastView`) и открывает `/view/kanban` либо
  `/view/tasks`. Без сохранённого вида, при неизвестном/повреждённом значении
  или ошибке чтения storage вход ведёт в канбан. Валидный `?project=` из
  query сохраняется; иначе подставляется последний валидный проект. Пока вход
  обрабатывается, плагин показывает нейтральную загрузку и не читает сводки
  обзора/не рендерит форму проекта; список проектов при этом загружается для
  проверки `?project=`. Guard `entryHandledRef` сбрасывается после снятия
  `entry`, поэтому повторный клик по пункту без remount снова обрабатывает
  вход.
- Секция «Проекты» видна только на `/view/kanban`, `/view/tasks` и
  `/view/projects`; в настройках и plugin manager её нет.
- Выбор проекта меняет `?project=<id>` без промежуточного экрана и запоминает
  последний выбор в `localStorage`.
- `/view/kanban` без проекта открывает последний или единственный проект; при
  неоднозначном выборе показывает подсказку выбрать проект в sidebar.
- `packages/plugin-projects/src/ui/view-toggle.tsx` рендерит переключатель
  `Список / Канбан` настоящими `<a>` с `aria-pressed` в обоих состояниях.
  Переключатель живёт только в шапке проекта (`ProjectHeader`) и сохраняет
  `project`, `tag` и `task` в query string. Внутри модала карточки его больше
  нет: уход из модала возможен только через шапку или явное закрытие, а
  несохранённый inline- или быстрый черновик проходит через подтверждение
  закрытия.
- Действия интерфейса используют `lucide-react`: создание, настройки, меню,
  drag, переименование, перемещение, удаление, сохранение, закрытие, приоритет,
  срок, теги и подзадачи. Иконки декоративные (`aria-hidden`), поэтому
  accessible name задаёт текст кнопки или её `aria-label`; размеры hit target и
  мобильная раскладка не меняются.
- Карточка канбана редактирует название и описание на своих местах. Заголовок
  открывается одинарным кликом на desktop, одиночным touch-тапом и клавишами
  Enter/F2 с клавиатуры; описание — теми же способами по своей области.
  Редактор заголовка — auto-resize textarea: длинный текст переносится и виден
  целиком, клик устанавливает курсор в любую видимую часть. Вставленные переводы
  строк заменяются пробелами, поэтому значение остаётся однострочным.
  Редактор описания тоже автоматически подстраивает высоту при открытии и вводе,
  сохраняя переносы Markdown и показывая весь текст без внутренней прокрутки.
  В режиме чтения общий `MarkdownContent` рендерит CommonMark/GFM через
  `react-markdown` + `remark-gfm`: заголовки, акценты, списки, задачи, ссылки,
  код, цитаты, таблицы, зачёркивание и изображения. Raw HTML отключён, URL
  проходит стандартную sanitization библиотеки; отклонённые javascript-ссылки
  остаются plain text. Обычные ссылки открываются в новой вкладке с
  `rel="noreferrer nofollow"` и не запускают inline-редактор, а область описания
  использует `role="group"`, поэтому интерактивные элементы не вложены в button.
  Заголовок сохраняется по Enter, описание — по Ctrl/Cmd+Enter; заметных кнопок
  Save/Cancel у редакторов нет. Escape завершает только активный редактор и не
  закрывает модал; Escape перехватывается на контейнере редактора, поэтому не
  доходит до native dialog. Touch-тап открывает поле
  только для primary-указателя без движения, второго пальца, long press
  (выделения) и `pointercancel`; drag и native scroll не блокируются.
  Клик вне активного редактора автоматически сохраняет его черновик. Завершение
  autosave не отбирает фокус у следующего контрола. Одновременно активен один
  редактор, а попытка открыть второй при изменённом черновике блокируется явным
  сообщением.
  Сохранение отправляет строго partial `task.update`: только `title` или только
  `descriptionMarkdown`, `id` и `expectedVersion`, зафиксированный при открытии
  редактора. Пустое название отклоняется, неизменённое значение не отправляет
  команду. Поздний refresh не затирает draft, показывает stale-уведомление, а
  `VERSION_CONFLICT` оставляет серверную версию без перезаписи. Конфликт
  быстрой команды (приоритет, срок, теги, перемещение, завершение) не удаляет
  независимый inline-черновик: редактор и draft остаются со stale-маркером.
  Очистка по конфликту выполняется только для сессии, из которой пришёл сам
  inline-save. Каждая асинхронная операция привязана к task ID и монотонной
  generation: поздний success/error/conflict A после A→B или A→B→A не меняет
  UI-состояние B и не оставляет его заблокированным. При этом успешная
  серверная команда (priority/complete/delete/inline save/subtask create) и
  `VERSION_CONFLICT` всегда инвалидируют данные через revision refresh,
  независимо от generation: поздний delete не оставляет призрачную карточку, а
  ABA-success обновляет текущую A, сохраняя её новый inline draft со stale.
  Generation ограничивает только ownership UI: очистку сессии, closeNow,
  ошибки/конфликты, quick cleanup и возврат saved для текущей задачи. Ошибки
  чтения и командные ошибки разделены: refresh очищает только ошибку чтения,
  поэтому поздний success/conflict A не скрывает INTERNAL-ошибку B и её inline
  draft; новая команда той же задачи снимает прежнюю командную ошибку, а смена
  задачи/close очищают состояние. Активный inline-черновик входит в общий
  dirty-close guard; «Продолжить редактирование» возвращает фокус в активное
  поле.
- Task-list пишет query через router-aware `replaceSearch`, поэтому заголовок
  строит ссылки из актуального `workspaceSearch`, а не из устаревшего
  router-состояния. Внутри одного проекта toggle сохраняет `project`, `tag` и
  `task`; смена проекта осознанно снимает `task` прежнего проекта.
- Создание карточки требует только название. Проект берётся из доски, колонка —
  из фактического заголовка, позицию вычисляет доменный append. Открытая
  карточка не заменяется полной формой: название и Markdown-описание
  редактируются inline, а статус, приоритет, срок, теги и подзадачи остаются
  быстрыми полями рядом. Кнопка `+ Добавить карточку` и composer находятся
  сразу под заголовком каждой колонки, вне прокручиваемого списка карточек
  (`shrink-0`), поэтому создание доступно без прокрутки и при длинной колонке.
  Нижней копии кнопки нет.
- Доска строится только из `kanbaner.tasks.column.list`, а не из
  `TASK_STATUSES`. Новый проект показывает три default-колонки `ToDo`,
  `In Progress`, `Done`; legacy-проект сохраняет `Backlog`, `To do`,
  `In progress`, `Done`. Каждая колонка запрашивает задачи через
  `task.list{columnId}` и имеет собственную пагинацию.
- Состояние доски связано с `projectId`: после переключения A→B колонки,
  карточки и вкладки A скрыты до успешного `column.list` B. Пока B не
  загружен, создание задачи disabled, а CRUD/DnD и delete-target хендлеры
  проверяют `projectId`; поздние ответы A не перезаписывают B. Перед любой
  mutation-командой после awaited read проверяется
  `effectiveProjectIdRef`/`projectGenerationRef`; при смене проекта команда не
  отправляется, optimistic pending отменяется, активный pointer drag
  снимается. Размонтирование `KanbanView` отдельным cleanup увеличивает
  generation, очищает `effectiveProjectIdRef`, снимает pointer listeners и
  инвалидирует delete dialog/count requests; поздние ответы не выполняют
  mutation.
- Колонки создаются только в «Настройках доски» (канбан и список): форма с
  названием и типом `open` («Обычная») или `done` вызывает существующую
  `column.create` без `position`, поэтому домен атомарно дописывает колонку в
  конец порядка. Ошибка валидации и двойная отправка не теряют ввод; после
  успеха черновик очищается, фокус возвращается в поле названия. Ошибка
  `column.list` после успешного создания показывает отдельное сообщение с
  кнопкой «Повторить загрузку»; повторяется только чтение, повторная мутация не
  предлагается. Пока операция в полёте или идёт retry загрузки, модалку нельзя
  закрыть ни Escape/backdrop, ни «Готово»/discard: синхронный refresh guard
  снимается только в captured finally последнего чтения `column.list`.
  Выбранная задача списка не сбрасывается.
- Меню заголовка колонки содержит переименование, `Переместить влево`,
  `Переместить вправо` и удаление. Нативный `<details>` закрывается кликом по
  свободному месту доски, Escape с возвратом фокуса на trigger и любым выбором
  действия; document-listeners работают только при открытом меню и не
  перехватывают события DnD. Переименование использует
  `column.update{expectedVersion}` и сохраняет ввод при ошибке; кнопки
  перемещения доступны с клавиатуры и на мобильном, а drag handle заголовка
  меняет порядок через `column.move`. Оптимистичный порядок откатывается, а
  `VERSION_CONFLICT` показывает конфликт и перечитывает фактический порядок.
- Настройки проекта содержат доступную с клавиатуры палитру «Цвет доски».
  Выбор отправляет color-only `project.update{id, expectedVersion, color}` без
  `title` и не перезаписывает параллельный черновик названия; при
  `VERSION_CONFLICT` версия перечитывается, а выбранный цвет остаётся
  несохранённым, пока пользователь не повторит выбор. Меню колонки содержит
  такую же палитру и отправляет color-only `column.update{id, expectedVersion,
color}` без `title`, закрывая меню и возвращая фокус на trigger. В обеих
  палитрах есть `aria-pressed`, русские accessible names, pending, error и
  notice; повторный выбор того же цвета и второй клик во время сохранения
  команду не отправляют.
- Цвета доски и колонок выбираются только по фиксированному enum
  `BoardColor`; произвольные HEX/CSS из данных не применяются. Неизвестное или
  отсутствующее значение трактуется как `default` и сохраняет прежнее
  оформление. Фон доски меняется мягко, фон колонки — заметнее, а `default`
  воспроизводит прежние цвета; пары light/dark заданы целыми классами, поэтому
  текст и контролы остаются контрастными в обеих темах. Карточка получает
  цветную левую полосу и Lucide-флаг приоритета: high — red, medium — amber,
  low — green; фон карточки остаётся `--card`, поэтому акцент не ухудшает
  читаемость.
- Наведение мыши на карточку с непустым описанием показывает его через 400 ms в
  fixed portal tooltip; клавиатурный `focus-visible` на заголовке открывает её
  сразу и связывает через `aria-describedby`. Markdown рендерится тем же общим
  компонентом, что в модале, целиком и без raw HTML. Tooltip выбирает положение
  выше/ниже карточки, ограничен viewport и не меняет layout колонки. На него можно перевести курсор и
  прокрутить длинное описание: задержка закрытия 150 ms даёт перейти с карточки,
  а scroll внутри tooltip не закрывает её. Уход курсора/focus вне интерактивной
  области, Escape, scroll/resize снаружи, pointerdown, drag и открытие
  меню/карточки скрывают её; touch-hover не используется, DnD не перехватывается.
- Рабочая типографика увеличена без изменения размеров контролов: `text-xs` —
  13 px, `text-sm` — 15 px, основной `text-base` — 17 px. Прежние произвольные
  11 px заменены на `text-xs`, заголовок карточки 13 px — на `text-sm`.
- Удаление колонки — destructive-диалог с явным `targetColumnId`, количеством
  переносимых задач и последствиями для `completedAt`. Целевой список строится
  только из колонок текущего проекта и исключает удаляемую; последняя открытая
  или последняя Done-колонка не удаляется. Точный счётчик читается отдельным
  `task.list{projectId,columnId,limit:1}` без активного tag, confirm заблокирован
  до успешного ответа и перепроверяется перед командой; если число изменилось,
  команда не отправляется, показывается новое число и требуется повторный
  confirm. Ошибка счётчика показывается отдельно и не превращается в 0. Диалог
  привязан к request/source/target: поздний ответ после смены проекта/цели
  отменяется. После успеха перечитываются задачи, колонки и сводка.
- Rename/move/delete колонок держат pending до awaited refresh `column.list`.
  Успешное сообщение показывается только после свежего списка; ошибка refresh
  отображается отдельно. Optimistic reorder сначала сохраняет snapshot порядка:
  при ошибке команды порядок восстанавливается сразу, независимо от refresh;
  при конфликте и неудачном refresh доска скрывается как недоверенная. При
  `VERSION_CONFLICT` форма/диалог остаются доступными после refresh и повторная
  отправка использует обновлённые `expectedVersion` и `targetColumnId`.
- После успешного `column.create` из настроек настройки перечитывают
  `column.list`, а уведомление представления запускает полный `reloadBoard`,
  поэтому новая пустая колонка сразу показывает empty state. Если refresh не
  удался, сообщение предлагает только повторить загрузку, а не создавать
  колонку снова.
- Заголовок доски показывает `Всего`, `Просрочено` и счётчики фактических
  колонок, не навязывая фиксированные четыре статуса. `task.move`,
  `task.create` и `task.complete` работают через `columnId`; `status` остаётся
  совместимым зеркалом колонки. В карточке и списке выбор перемещения строится
  из фактических колонок, включая несколько Done-колонок.
- Список задач фильтруется по колонке выбранного проекта (`?column=<id>`), а
  сортировка/пагинация сохраняются. Фильтр валидируется только после успешной
  загрузки колонок именно текущего проекта; stale/пустой/ошибочный ответ не
  сбрасывает `?column=`. Старая ссылка `?status=backlog` поддерживается как
  публичный legacy-путь: список показывает предупреждение, композер использует
  одну подпись/один destination (`Backlog` или фактическую колонку статуса), а
  создание задачи передаёт legacy `status` и лениво материализует колонку без
  прямого доступа к базе.
- Высота области колонок ограничивается доступной высотой viewport и
  пересчитывается при resize, открытии/закрытии inline-панели создания и
  изменении верхней геометрии. Поэтому длинная колонка прокручивается внутри
  себя, а composer остаётся видимым под заголовком.
- Верхняя drop-зона определяется явным `data-kanban-drop-zone="top"` у
  composer/заголовка, а не координатой первой карточки: после прокрутки
  (`scrollTop > 0`) drop в composer всё равно вставляет перед первой. Drop
  первой карточки на эту зону — no-op, не append. Вставка между карточками и
  append ниже последней по-прежнему считаются по геометрии карточек.
- Кнопка «Новый проект» в заголовке списка публикует общий
  `requestProjectCreate()`: на desktop открывается форма sidebar, на mobile —
  bottom sheet. Клика по скрытой desktop-кнопке больше нет.
- `project.list` догружается по `nextOffset` страницами по 200: созданный
  201-й проект открывается и попадает в sidebar, а не считается удалённым.
- Кнопка «Настроить» в заголовке канбана и списка открывает modal
  «Настройки доски». Название проекта сохраняется отдельной
  `kanbaner.tasks.project.update` с актуальной версией; список фактических
  колонок позволяет переименовать каждую колонку через `column.update`,
  поменять порядок drag handle или кнопками перемещения через `column.move`, и
  закрыть настройки кнопкой «Готово». Создание новой колонки — единственная мутация
  типа в модалке: она дописывается в конец через `column.create`. Пакетного
  сохранения, удаления и смены типа существующих колонок в модалке нет. У
  каждой операции собственный pending, awaited refresh
  `column.list`/`project.list` и `expectedVersion`; при `VERSION_CONFLICT`
  версия перечитывается, ввод сохраняется, повторная отправка использует
  свежий snapshot. Создание привязано к captured project/generation: после
  смены проекта поздний ответ не добавляет колонку и не обновляет чужой
  список. `column.list` refresh защищён монотонным sequence: ответы, пришедшие
  в обратном порядке, игнорируются и не откатывают более свежий
  порядок/версии. `column.move` сериализован глобально, а ожидающие операции
  привязаны к captured generation/operation token: закрытие и повторное
  открытие модалки не снимает pending нового сохранения. Закрытие с
  несохранённым названием проекта, колонки или черновиком новой колонки
  требует подтверждения; «Закрыть без сохранения» проходит тот же pending
  guard, что и «Готово», а редактирование названия скрывает подтверждение.
  Escape и focus trap принадлежат только модалке: выбранная задача списка,
  inline-создание и его черновик не закрываются. После сохранения
  `bumpProjectsRevision()` обновляет заголовок, sidebar, mobile sheet и обзор,
  а представление перечитывает колонки, доску и сводку. ID проекта, маршрут,
  выбранный вид и `task`/`tag` в query не меняются.
- В верхней строке карточки слева расположен чекбокс выбора, справа — меню
  действий; заголовок занимает отдельную строку во всю ширину. Чекбокс имеет
  доступное имя `Выбрать задачу …`, визуальный размер 16 px и label 20×20 px, исключён
  из drag и не открывает карточку. Меню, заголовок и whole-card drag остаются
  прежними.
- Массовый выбор хранится как `Map` id → snapshot `Task` в порядке кликов и
  привязан к текущему `projectId`; смена проекта очищает его. Смена tag сразу
  убирает из выбора задачи, которых нет в новом фильтре, а обычный
  refresh/resize сохраняет выбор, пока задачи существуют, и обновляет их
  версии из актуальных snapshot. Если задача выпала из загруженной страницы,
  `task.get` принимает её только при совпадении `projectId` и активного tag:
  задача, у которой тег удалён в другой вкладке, снимается с выбора и не
  попадает в повторный payload; подходящие под фильтр задачи за границей
  страницы сохраняются. При count > 0 внизу рабочей области показывается fixed
  панель «Выбрано N» с селектом фактических колонок, «Удалить» и «Снять выбор».
  На desktop она расположена по центру снизу, на mobile — выше плавающей
  навигации; horizontal overflow отсутствует, действия доступны с клавиатуры.
  Пока панель активна, прокручиваемые списки колонок получают нижний scroll-space,
  поэтому нижние чекбоксы можно поднять над панелью и продолжить выбор.
- Выбор target сразу отправляет одну `task.moveMany` с `items` в порядке выбора
  и `columnId`, отдельной кнопки «Переместить» нет. Домен дописывает задачи в
  конец target. После ошибки target сбрасывается на placeholder, поэтому повтор
  в ту же колонку выполняется новым выбором со свежими версиями. UI сохраняет
  `TaskMoveManyOutput` с фактическими positions, до reload регистрирует
  `loadedCountsRef`/`visibilityRef` для каждой перемещённой задачи и догружает
  target до последней позиции. Поэтому карточки сразу видимы и при append за
  границей страницы, и при same-column append. Успех очищает выбор и выполняет
  awaited reload доски и `bumpKanbanRevision()`, поэтому счётчики колонок и
  сводка обновляются. Pending блокирует повторную отправку, ошибка сохраняет
  выбор.
- «Удалить» открывает отдельный destructive `ModalDialog` с текстом «Выбрано
  задач: N» и явным указанием, что каскадные подзадачи в это число не входят.
  Подтверждение отправляет одну `task.deleteMany` с `confirm: true`; во время
  pending диалог нельзя закрыть или подтвердить повторно. Успех очищает выбор,
  перечитывает доску и сводку. При `VERSION_CONFLICT` или другой ошибке доска
  перечитывается, существующий выбор сохраняется с актуальными версиями,
  исчезнувшие и не соответствующие активному tag задачи из него удаляются.
  Сообщение «доска перечитана» показывается только после успешного refresh.
  Если перечитать доску не удалось, UI явно сообщает, что версии НЕ обновлены,
  блокирует повтор и предлагает «Обновить доску»; повторная команда уходит
  только после успешной перечитки со свежими `expectedVersion`.
  Последовательных single-команд `task.delete`/`task.move` для массовых
  действий нет.
- Закрытие Trello-карточки во время pending-команды учитывает только поле,
  которое уже отправляется: независимые inline/quick/subtask черновики
  по-прежнему требуют подтверждения. Если независимых черновиков нет,
  карточка закрывается без ложного confirm, а поздний success обновляет доску.
- Блокировка повтора после неудачной перечитки снимается, когда массовый выбор
  становится пустым: без payload скрытого запрета нет. Смена tag, оставившая
  выбор пустым, также снимает блокировку. Перечитка различает
  applied/failed/superseded: `applied` возвращается только при полном успехе
  всех колонок и reconciliation; ошибка `task.list` любой колонки или
  временная ошибка `task.get` — `failed`, поэтому stale payload остаётся
  заблокированным до полного refresh. Устаревшая R1 не выставляет блокировку
  после успешной R2. Если во время refresh tag очистил selection, continuation
  не возвращает hidden block: состояние сбрасывается, checkbox остаются
  доступными. Visibility для moveMany регистрируется только для задач,
  соответствующих текущим project и активному tag; смена tag во время pending
  не оставляет лишних required IDs и полной догрузки.
- Карточку можно перетаскивать за любую неинтерактивную область article и за
  заголовок: на desktop после сдвига 7 px, на touch — после long press 220 ms.
  Отдельной drag-ручки нет; кнопка меню находится в верхней строке справа, а
  заголовок занимает всю ширину карточки отдельной строкой. Кнопки, ссылки,
  поля, contenteditable и меню drag не
  начинают; выделение блокирует drag только если его anchor/focus находятся
  внутри этой карточки. До long press `touch-action` разрешает pan-x/pan-y,
  после long press прокрутка блокируется и pointer удерживается capture.
  Обычный клик по заголовку открывает карточку, а click после завершённого drag
  подавляется; новое pointer-взаимодействие снимает устаревшее подавление.
  Очистка pointer listeners выполняется при завершении drag, смене проекта и
  unmount; альтернативой остаются меню «Переместить в…» и кнопки порядка.
  Во время drag portal с `pointer-events: none` показывает копию карточки под
  курсором с исходным offset и не перехватывает hit-testing. Индикатор вставки
  абсолютно позиционирован у границы целевой карточки и не сдвигает список;
  промежуток между карточками вычисляется по ближайшей середине, а не как append.
- Меню карточки рендерится порталом в `document.body` как fixed-overlay от
  кнопки меню действий: оно не участвует в flow карточки, не меняет её размер, не
  обрезается overflow колонки, переворачивается вверх при нехватке места,
  прижимается к границам viewport и перепозиционируется/закрывается при
  прокрутке. После открытия фокус переходит в первое доступное действие.
  `role="menu"`/`menuitem` поддерживают ArrowUp/ArrowDown/Home/End, Escape и
  Tab с возвратом фокуса на trigger; открыто не больше одного меню, focusout и
  outside click закрывают его. Клик внутри меню не начинает drag.
- Desktop-колонки имеют фиксированную ширину `flex: 0 0 288px` и не
  растягиваются при resize широкого экрана; отдельной кнопки создания колонки
  на доске нет. При большом числе колонок доска прокручивается горизонтально,
  а на мобильном сохраняется ширина около `85vw` (не более 272 px).
- На мобильном плагин публикует trigger «Проекты» в overlay-слое: shell
  навигация не содержит доменных пунктов. Выбор проекта закрывает sheet.

## Структура

```text
src/
  index.ts        серверная регистрация metadata
  metadata.ts     Plugin ID, маршруты, UI-вклады
  ui.tsx          клиентский entrypoint: привязка рендереров
  ui/             доска, sidebar, обзор, composer, общий query state
  task-list/      список задач, детали, собственный query state
```

`packages/task-ui` остаётся общей библиотекой примитивов и не становится
плагином. Код плагина не импортирует `kernel`, storage и внутренности других
плагинов.
