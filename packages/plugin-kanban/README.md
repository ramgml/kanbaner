# @kanbaner/plugin-kanban

UI-плагин канбана Kanbaner. Не владеет данными: все задачи читаются и
изменяются через публичные команды и запросы плагина `kanbaner.tasks`.

## Идентификация

- Plugin ID: `kanbaner.kanban`
- Версия манифеста: `1.0.0`, Host API `^1.0.0`
- Требует: `kanbaner.tasks` `^1.0.0`
- Потребляет: `kanbaner.tasks.commands.v1`, `kanbaner.tasks.queries.v1`
- Предоставляет: `kanbaner.kanban.ui.v1`
- Разрешения: `commands`, `events`, `ui`
- Маршрут: `/view/kanban`

## Вклады

| ID                           | Слот           | Вид          | Назначение                         |
| ---------------------------- | -------------- | ------------ | ---------------------------------- |
| `kanbaner.kanban.view`       | `app.main`     | `view`       | Доска с четырьмя колонками         |
| `kanbaner.kanban.navigation` | `app.sidebar`  | `navigation` | Ссылка «Канбан»                    |
| `kanbaner.kanban.details`    | `app.overlays` | `panel`      | Детали/редактор выбранной карточки |

Серверный entrypoint (`dist/index.js`) регистрирует только metadata. Реальные
React-рендереры находятся в клиентском entrypoint (`dist/ui.js`) и
привязываются к metadata в `apps/web/src/ui/builtin-ui-plugins.ts`.

## Доска

- Фиксированный порядок колонок: `backlog`, `todo`, `in_progress`, `done`.
- Заголовок, количество задач (`total` из `task.list`) и пустое состояние.

### Визуал и рабочая область

- Рабочая область доски — мягкий сине-серый фон (`#e2e8f0`, в тёмной теме
  `#1e293b`) с тонкой рамкой; она визуально отделена от светлого shell.
- Колонки — светло-серые списки (`#f1f5f9`, в тёмной теме `#263244`), белые
  карточки с тенью, заголовки и счётчики в шапке колонки.
- Ширина колонки на desktop — от 272 px с гибким распределением доступной
  ширины main; на mobile — `85vw` с ограничением 272 px и scroll-snap.
- Если колонки не помещаются по ширине, у контейнера появляются явные
  affordance: правый edge fade (`kanban-scroll-fade`), подсказка
  «Прокрутите вправо →» (`kanban-scroll-hint`) и `padding-end`, чтобы последняя
  колонка не выглядела обрезанной. Подсказки скрываются, когда прокрутка
  достигла края, и пересчитываются по `scroll`, `resize` и `ResizeObserver`.
  Покрыто component-тестами с mocked geometry и браузерным E2E (появление при
  overflow и исчезновение у правого края).
- Шапка доски показывает название выбранного проекта и его описание; в режиме
  «Все проекты» — агрегированный заголовок без технического текста о домене.
- Активные фильтры проекта и тега отображаются чипами с доступным сбросом.
- На mobile под шапкой есть вкладки статусов: они переключают активную колонку,
  прокручивают к ней и синхронизируются с ручной прокруткой. Scroll-snap и
  отсутствие горизонтального overflow страницы сохранены.

### Карточка

- Карточка: заголовок, приоритет, срок, теги, число непосредственных подзадач,
  индикаторы сохранения и конфликта версий.
- Заголовок — главный элемент; показываются максимум два тега и `+N`.
- Срок отображается семантически: «Просрочено», «Сегодня», «Завтра» или дата.
- Pending и конфликт версий показываются компактными индикаторами.
- Интерактивные элементы карточки (открытие, меню действий, drag handle и
  пункты меню) на mobile имеют высоту не меньше 40 px (`min-h-10`); на desktop
  допускается компактный вариант `xl:min-h-7`.
- Загрузка через `kanbaner.tasks.task.list` с фильтрами `projectId`/`tag` и
  сортировкой `position asc`.
- Пагинация внутри каждой колонки: страницы по 10 карточек, кнопка
  «Показать ещё» использует серверный `nextOffset` как курсор. Пустая или
  полностью дублированная страница всегда перечитывает колонку с начала:
  локальные ID могли устареть при уменьшении `total` или сдвиге позиций.
  `nextOffset`/`total` такой страницы не используются для закрытия пагинации;
  это делает только актуальный reload. Reload не вызывает `loadMore`, поэтому
  цикла нет.
- Запоздавшие ответы `loadMore` отменяются по поколению/фильтру/ревизии и не
  применяются после смены фильтра, move или reload.
- После move доска перечитывается с сохранением уже догруженного количества.
  Требования видимости хранятся в `Map<taskId, { status, position, filterKey }>`
  для всех одновременных moves; target-колонка догружается до максимума
  required-позиций и продолжает читаться, пока в результатах не появятся все
  required ID (`mustIncludeIds`). Требование снимается только когда текущий
  reload действительно содержит ID; reload с другим фильтром его не стирает.
  Поэтому две одновременные карточки за page boundary не теряются.
- Фильтры проекта и тега хранятся в query string (`project`, `tag`) и
  переживают reload. Выбранная карточка хранится в `task`.
- Query string обновляется через `replaceSearch` из router-aware shell
  (`router.replace` теми же параметрами, что и `search`). Это держит
  `useSearchParams` синхронным; fallback — `history.replaceState`.
- Горизонтальная прокрутка включена только у контейнера колонок; страница на
  360 px не получает горизонтальный overflow.

## Создание на доске

- На панели доступны «Новый проект» и «Новая задача», в каждой колонке —
  быстрый composer, а при закрытом composer — отдельное действие
  «Добавить с деталями» (совместимость с KAN-015).
- Быстрый composer (`kanban-quick-add-<status>`): Trello-like «+ Добавить
  карточку» внизу колонки. По активации показывает textarea с autofocus,
  кнопки «Добавить карточку» и закрытие, а также «Добавить с деталями».
  - `Enter` создаёт задачу, `Shift+Enter` переносит строку, `Escape` закрывает
    composer и возвращает фокус на кнопку открытия через opener ref.
  - Проект берётся из активного фильтра, статус — из колонки, позицию
    определяет доменный append. Если проект не выбран, composer просит выбрать
    его и сохраняет введённый заголовок.
  - После успеха composer остаётся открытым для следующей задачи; новая
    карточка видна и переживает reload. Фокус возвращается в textarea через
    effect только после снятия `submitting`, поэтому работает и submit мышью.
  - Двойной submit блокируется guard-ом и не создаёт дубликат; ошибка
    сохраняет введённый текст.
- При открытом composer остаётся один путь в полную форму — кнопка самого
  composer-а. Она передаёт текущие title/projectId в общий full-form draft
  (`KanbanView.taskDraft`), а отдельная кнопка KAN-015 скрыта, пока composer
  открыт. Cancel полной формы сохраняет originating quick draft; после
  успешного создания он очищается по reset-токену, чтобы заголовок не создал
  дубль.
- Открытые composer отслеживаются как `ReadonlySet<TaskStatus>`: несколько
  колонок могут быть открыты одновременно, статус добавляется при открытии и
  удаляется только при закрытии своей колонки. Поэтому details-кнопка скрыта у
  каждой открытой колонки и не появляется у соседней при закрытии другой.
- Полная форма (`kanban-create-task-<status>`) — прежний путь KAN-015 через
  общие `ProjectForm` и `TaskForm` из `@kanbaner/task-ui`; плагин вызывает
  только `kanbaner.tasks.project.create` и `kanbaner.tasks.task.create`.
  Позицию задачи определяет домен атомарным append: канбан не передаёт
  `position` и не пересчитывает порядок вручную.
- Кнопка колонки предустанавливает её статус. Активный фильтр проекта
  подставляется в форму; без фильтра проект не выбран, и пользователь обязан
  выбрать его явно. Родитель необязателен и выбирается только среди корневых
  задач выбранного проекта.
- После `project.create` выполняется повторный `project.list`: проект сразу
  доступен в фильтре и форме, текущий выбор фильтра не сбрасывается.
- После `task.create` увеличивается локальная ревизия. Доска перечитывается,
  а target-колонка догружается до созданного ID через тот же механизм
  видимости, что и после перемещения. Поэтому карточка видна, даже если
  оказалась за границей первой страницы. Если созданная задача не попадает в
  активный фильтр проекта или тега, фильтр переключается только в объёме,
  необходимом для её показа. Сравнение тега идёт через публичный
  `normalizeTag`: `Release` и `release` эквивалентны, а реально несовпадающий
  тег сбрасывается.
- Отправка блокируется до завершения команды (guard + `submitting`), поэтому
  двойной клик или повторный Enter не создаёт дубликат — как для задачи, так и
  для проекта. Ошибка показывается внутри формы, введённые значения
  сохраняются; при успехе форма закрывается.
- Черновик задачи/проекта хранится в `KanbanView` через additive
  controlled-API общих форм (`values`/`onValuesChange`), а не внутри
  размонтируемой формы. Поэтому при mobile → desktop → mobile сохраняются
  title, description, tags, parent, status и project. Новая session открывает
  чистый draft с предустановкой колонки/фильтра.
- Формы открываются только на `/view/kanban`. На mobile используется нативный
  `ModalDialog` с focus trap, Escape и возвратом фокуса; на desktop — inline
  панель над колонками. Переключение breakpoint сохраняет открытый режим формы,
  а `restoreFocusSelector` возвращает фокус на кнопку, которая открыла форму.

## Перемещение и порядок

- Команда: `kanbaner.tasks.task.move` с `expectedVersion`, `status`,
  `position`. `completedAt` при переходе в `done` выставляет домен.
- Позиция считается по полному нефильтрованному ordered-списку
  `(projectId, status)` (все страницы `task.list`, `limit ≤ 200`): `append` —
  реальная длина scope, `beforeId` — индекс в этом же списке.
- Действия «Выше»/«Ниже» относятся к видимому порядку. Сначала строится
  optimistic placement, затем берётся следующая видимая после перемещаемой
  карточка: её ID становится `before`-anchor-ом, а отсутствие следующей даёт
  `append`. Полный scope переводит anchor в позицию, поэтому скрытые соседи
  сдвигают индекс, но не направление (пример `A(release), B(other),
C(release)`: «Ниже» для A даёт `C, A`, а не `A, C`).
- `reloadBoard` читает актуальные фильтры и поколение из ref: запоздавший
  reload после move не перезаписывает колонку старым фильтром.
- Drag-and-drop реализован нативными pointer events на drag handle. Новых
  DnD-библиотек нет.
- DnD не единственный путь: у каждой карточки есть меню «Переместить в…»,
  «Выше», «Ниже», «В начало», «В конец». Все действия доступны с клавиатуры и
  на мобильных.
- Оптимистичное обновление: карточка сразу меняет колонку/место, pending
  показывается только на ней. При ошибке выполняется откат к серверному
  snapshot и выводится сообщение.
- `VERSION_CONFLICT` откатывает оптимистичное состояние и перечитывает доску,
  не отправляя устаревшую команду повторно. Store повышает версии сдвинутых
  соседей, поэтому после успешного move данные берутся из повторного запроса.

## Детали и редактор

- Overlay использует `ModalDialog` и `TaskForm` из `@kanbaner/task-ui` и
  `invoke` UI-рантайма; собственной копии форм и доменных запросов вне
  компонентов нет.
- Рендерится только при `pathname === "/view/kanban"`, непустом `task` в query
  string и открытом состоянии; при client-side переходе на другой маршрут или
  Link-переходе с изменением query исчезает.
- На desktop карточка открывается центрированным Trello-like модалом поверх
  доски (`kanban-details`, `data-variant="desktop"`): ширина до 860 px,
  `max-height` ограничен viewport, прокручивается только внутреннее
  содержимое. Сверху — заголовок, проект, статус и закрытие `×`. Слева —
  Markdown-описание и подзадачи, справа — действия: статус/перемещение,
  приоритет, срок, теги, завершение и удаление. На узких экранах колонки
  складываются в одну.
- Desktop и mobile используют один общий нативный `<dialog>` из
  `@kanbaner/task-ui` (`ModalDialog`): inert-фон, focus trap, Escape и возврат
  фокуса на карточку. Desktop-вариант отличается только классами
  (`data-variant="desktop"`, центрирование, 860 px); mobile — полноэкранный
  (`data-variant="mobile"`). Поэтому breakpoint меняет раскладку того же
  модала и не создаёт второй модальный слой.
- Заголовок и Markdown-описание редактируются общей `TaskForm` в режиме
  `edit`; проект и родитель доступны только для чтения. `expectedVersion`
  фиксируется в edit-session при открытии формы и не заменяется на версию из
  перечитанной карточки. Если серверная версия изменилась, черновик остаётся в
  форме, показывается `kanban-edit-stale` с «Отменить правки», а сохранение
  устаревшего черновика получает `VERSION_CONFLICT` и не перезаписывает чужую
  правку. После успешного `task.update` выполняется повторный `task.get`,
  поэтому заголовок, описание, версия и `completedAt` берутся из сервера.
- Быстрые действия вызывают публичные команды `task.move`, `task.complete` и
  `task.update` (`priority`, `dueAt`, `tags`). Все они блокируются на время
  выполнения и используют `expectedVersion` текущей задачи; повторный клик до
  завершения команды игнорируется, ошибка сохраняет введённые значения.
- `VERSION_CONFLICT` не повторяет устаревшую команду: показывается сообщение,
  редактор закрывается, ревизия перечитывает карточку и доску.
- Удаление требует inline-подтверждения (`task-delete` →
  `task-delete-confirm-panel`) и вызывает `task.delete` с `confirm: true`.
- Переключение A → B не показывает данные A: рендер и все команды используют
  только `currentTask`, у которого `task.id === taskId`; до загрузки B действия
  заблокированы, project/parent/subtasks относятся к B.
- Подзадачи показываются списком с заголовком и статусом. `task.list`
  дочитывается по `nextOffset` (страницы по 200), поэтому видны все подзадачи,
  включая созданную за границей первой страницы. Клик открывает подзадачу в том
  же модале, ссылка «Родитель» возвращает к корню. Создать подзадачу можно
  только у корневой задачи (`parentTaskId === null`), родитель передаётся
  текущим корнем; один уровень вложенности сохраняется.
- Черновики быстрых действий (статус перемещения, срок, теги, форма подзадачи)
  хранятся в `TaskOverlay`, а не в пересоздаваемом модале. Успешная команда по
  другому полю и смена breakpoint обновляют только серверные значения,
  несохранённые поля остаются. Любой такой черновик входит в общий dirty guard:
  Escape, `×`, backdrop и возврат breakpoint требуют подтверждения с вариантами
  «Закрыть без сохранения» и «Продолжить редактирование».
- Статус, срок и теги сливаются с новой серверной версией трёхсторонне: чистое
  локальное поле принимает серверное значение; dirty-поле при неизменном
  серверном остаётся локальным; если изменились оба, локальное значение
  сохраняется и показывается `kanban-quick-conflict` с явными действиями
  «Взять серверные» и «Оставить мои». Молчаливой перезаписи нет.
- Теги сравниваются и канонизируются по правилам домена (trim, нижний регистр,
  дедупликация). После успешного сохранения `Release`, `release` и
  `release, release` приводятся к серверной форме `release`; поле становится
  чистым, повторное сохранение не отправляет команду, а закрытие не требует
  подтверждения. Срок канонизируется по дате серверного `dueAt`.
- Подтверждение закрытия — `alertdialog` внутри модала: фокус переходит в него,
  Tab/Shift+Tab не выходят за его кнопки, а «Продолжить редактирование»
  возвращает фокус в изменённое поле формы или быстрого действия.
- Число подзадач видимых корневых карточек перезапрашивается по ревизии;
  ошибка запроса показывается как `—` и не кэшируется как `0`.

## Границы импорта

- UI-код импортирует только `@kanbaner/plugin-sdk`,
  `@kanbaner/plugin-tasks/contract`, `@kanbaner/task-ui` и React.
- CSS-классы плагина попадают в Tailwind через
  `@source "../../../../packages/plugin-kanban/src"` в `apps/web/src/app/globals.css`.
- Запрещены корневой `@kanbaner/plugin-tasks`, `@kanbaner/kernel`,
  `@kanbaner/storage-sqlite`, внутренности `apps/web` и
  `@kanbaner/plugin-task-list`.
- UI-entrypoint разрешён только composition-модулю
  `apps/web/src/ui/builtin-ui-plugins.ts`.
- Серверный граф не импортирует React и клиентские компоненты. Проверки
  выполняет `scripts/check-import-boundaries.mjs` вместе с self-test.

## Проверки

```bash
pnpm install --frozen-lockfile --strict-peer-dependencies

node scripts/check-import-boundaries.mjs --self-test
pnpm check
cd apps/web && pnpm exec playwright test
```

## Ограничения

- Доска показывает задачи всех проектов, если фильтр проекта не выбран.
  Позиции уникальны внутри проекта, поэтому визуальный порядок между
  проектами определяется сортировкой `position, id` домена.
- Число непосредственных подзадач запрашивается отдельным `task.list` с
  `parentTaskId` и `limit: 1` для каждой видимой корневой карточки; отдельного
  агрегата в контракте `kanbaner.tasks` нет.
- Отключение плагина убирает маршрут и вклады, но не удаляет задачи.
