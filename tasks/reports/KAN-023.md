## Что сделано

В домен `kanbaner.tasks` добавлена модель пользовательских колонок проекта.

- Новая сущность `TaskColumn`: `id`, `projectId`, `title`, `status`, `position`,
  `version`, `createdAt`, `updatedAt`. Открытые колонки хранят `status =
in_progress`, Done-колонки — `done`; допускается несколько колонок каждого
  типа.
- `Task` получил необязательный `columnId`. Для новых задач он заполняется
  всегда; legacy-документы без `columnId` читаются через effective-колонку по
  прежнему `status` (`resolveTaskColumnId`).
- `project.create` атомарно создаёт три default-колонки: `ToDo`, `In Progress`,
  `Done` с детерминированными ID
  `column-<projectId>-todo|in-progress|done`.
- Legacy-проект без документов колонок получает `Backlog`, `To do`,
  `In progress`, `Done` с ID `column-<projectId>-legacy-<status>`.
- Технический backfill при активации проставляет `task.columnId` по статусу,
  не меняя публичные `task.version` и `task.updatedAt`. Backfill выполняется
  отдельной транзакцией на проект и awaited до завершения активации; сбой
  одного проекта логируется как `tasks.column_backfill_failed` и не отменяет
  остальные. Переиндексация поиска остаётся независимой best-effort.
- `column.list` и `task.list{columnId}` — read-only query-пути: они не
  материализуют колонки и не делают read-repair. Default/legacy-колонки
  материализует awaited startup backfill; если backfill проекта упал, query
  честно возвращает пустой список или `NOT_FOUND`.
- `document.version > task.version` разрешён **только** как результат этого
  backfill. Обычные мутации обязаны сохранять версии синхронными, обратное
  расхождение отвергается `VALIDATION_ERROR`. Инвариант задокументирован в
  `specs/architecture.md` и README.
- Явный legacy `status` в `task.create`/`task.move`, для которого в проекте нет
  колонки, лениво материализует её в той же транзакции: Backlog встаёт в
  позицию 0, остальные — по порядку legacy-статусов. Новый проект сохраняет три
  default-колонки, а `columnId`/`status` задачи синхронизируются. Если колонку
  создал Store, activation публикует `column.created` после коммита, а
  сдвинутые существующие колонки — `column.updated` с `changed: ["position"]`.
  Повторные и конкурентные операции не создают дублей.
- Позиция задачи уникальна в области `(projectId, columnId)`; позиция колонки —
  в области `projectId`. Append, явная вставка и move повышают версии
  фактически сдвинутых соседей.
- CRUD колонок: `column.create`, `column.update`, `column.move`,
  `column.delete` (`destructive`, `confirm: true`, `targetColumnId`).
- `column.delete` атомарно переносит задачи в target-колонку того же проекта,
  обновляет `columnId`, `status`, `position`, `completedAt` и версии, а также
  возвращает `movedTasks` и сдвинутые `updatedColumns`. Позиция в target —
  `max(position) + 1`, а не `count`, поэтому разреженные позиции не дают
  дублей. Запрещены удаление последней открытой колонки (`COLUMN_LAST_OPEN`),
  последней Done-колонки (`COLUMN_LAST_DONE`), self-target и target другого
  проекта. В проекте всегда остаётся минимум одна открытая и одна Done-колонка,
  поэтому create/complete не попадают в невозможное состояние.
- `task.create` и `task.move` принимают `columnId` и/или legacy `status`.
  Mismatch даёт `COLUMN_STATUS_MISMATCH`, отсутствие обоих — `COLUMN_REQUIRED`.
  Старый клиент без `columnId` создаёт задачу в `todo`, move по `status`
  выбирает первую колонку с этим статусом.
- `task.complete` переводит задачу в первую Done-колонку проекта
  (`DONE_COLUMN_NOT_FOUND`, если Done-колонки нет).
- `task.list` фильтрует по `columnId`; комбинация с чужим `projectId`
  отвергается, неизвестная колонка даёт `NOT_FOUND`.
- `project.delete` каскадно удаляет колонки, возвращает `deletedColumns` в
  Store-результате и payload `project.deleted`, а также публикует отдельный
  `column.deleted` для каждой колонки, чтобы подписчики очистили универсальные
  ссылки.
- Activation публикует после коммита `column.created|updated|moved|deleted`,
  `task.moved` для задач, сменивших колонку при `column.delete`, и
  `task.updated` для фактически сдвинутых соседей. Добавлен тип ресурса
  `task-column` и `formatColumnRef`.
- `TasksIdFactory` расширен `nextColumnId()`; runtime генерирует
  `column-<uuid>`.

Публичные команды и запросы расширены совместимо в рамках v1: существующие ID
и поля не менялись, новые поля и операции добавлены аддитивно.

## Исправления по независимому ревью

- BLOCKER: `activation.task.list` прокидывает `columnId` в
  `store.listTasks`; добавлен интеграционный regression через публичный query
  (две колонки, точные `total`/`items`/`nextOffset`, чужой проект и
  отсутствующая колонка).
- HIGH: default нового проекта остаётся три колонки, но явные legacy
  `task.create`/`task.move` материализуют недостающую колонку атомарно, с
  `column.created` после коммита и без дублей при повторе. Исходные E2E
  Backlog-сценарии восстановлены из `3c56fee`; fixed UI по-прежнему проверяется
  как четыре фиксированные колонки, динамический рендер — KAN-024.
- MEDIUM: `column.delete` дописывает задачи после `max(position) + 1`;
  conformance-кейс с разреженными позициями 5/10 проверяет результат 11 и
  отсутствие дублей.
- MEDIUM: backfill идёт по одному проекту в отдельной транзакции с отдельным
  `tasks.column_backfill_failed` и продолжением остальных; интеграционный тест
  имитирует сбой записи колонки одного проекта.
- MEDIUM: `project.delete` публикует `column.deleted` на каждую колонку,
  интеграционный тест проверяет события и недоступность ResourceRef.
- MEDIUM: `column.delete` публикует `task.moved` с `from/to column/status` для
  перенесённых задач, а сдвиги позиций остаются `task.updated`.
- MEDIUM: отдельные ошибки `COLUMN_LAST_OPEN`/`COLUMN_LAST_DONE` и инвариант
  минимум одной open и одной Done-колонки; обновлены Store, spec, README и
  conformance.
- LOW: сохранён `taskPositionScopeKey(projectId, status)` и добавлен
  `taskColumnPositionScopeKey(projectId, columnId)`; обновлены комментарии
  `column.deleted`.

## Финальные findings ревью

- `column.list` и `task.list{columnId}` больше не пишут БД: убраны
  `ensureProjectColumns`/backfill из query-путей. `plugin-contract.md` не
  менялся. Материализация остаётся awaited startup backfill по одному проекту;
  query при упавшем backfill возвращает фактическое состояние.
- Conformance-кейс `query: column.list и task.list не выполняют read-repair`
  проверяет пустой список/NOT_FOUND до backfill и совпадение числа документов
  до/после запросов. Startup-тест больше не ждёт read-repair: колонки готовы к
  возврату активации.
- Ленивая материализация Backlog публикует `column.updated`
  (`changed: ["position"]`) для сдвинутых существующих default-колонок и
  `column.created` только для новой; интеграционный тест проверяет обе группы.
- `column.delete` проверяет `max(position) + 1` на `MAX_POSITION` и при
  переполнении отдаёт `INVALID_POSITION` без частичной записи;
  conformance-кейс расширен.
- JSDoc области позиции в `store.ts`, `constants.ts`, `schemas/common.ts`
  приведён к `(projectId, columnId)`; комментарий legacy-insertion описывает
  фактический алгоритм.
- Startup backfill не публикует доменные события; восстановление подписчиков и
  поиска — полная переиндексация и чтение list после рестарта.

## Риски и ограничения

- События колонок и перенесённых задач остаются best-effort: сбой публикации
  не откатывает мутацию.
- `status` остаётся зеркалом колонки, поэтому перевод задачи между колонками
  одного типа (например, двумя открытыми) не меняет `status`; клиенту нужно
  ориентироваться на `columnId`.
- Пользовательские колонки не мигрируют существующие SQL-таблицы: плагин
  хранит их в document collection `task-columns`.
- Fixed UI показывает Backlog только после ленивой материализации или для
  legacy-проекта; полноценная динамическая доска — KAN-024.
