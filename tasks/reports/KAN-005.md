## 1. Итог

Реализованы две инфраструктурные части ядра без доменных типов, без БД, без очередей и без
event sourcing:

- `packages/kernel/src/events/**` — шина доменных событий с exact/wildcard-подписками через SDK,
  валидацией `EventEnvelope`, явной публикацией `publishAfterCommit`, асинхронной best-effort
  доставкой, изоляцией ошибок подписчиков, безопасным журналированием и in-memory dedupe по
  `eventId`;
- `packages/kernel/src/resources/**` — `ResourceRegistry`, реализация SDK `ResourceService`,
  backend-neutral порт `LinkStore`, `LinkService`, in-memory реализация порта для тестов и
  подписчик очистки связей по событию `*.deleted`.

Корневой `packages/kernel/src/index.ts`, `package.json`, SDK, приложение, спецификации, файл
задачи, `plugins/**`, `operations/**` и `storage/**` не изменялись.

## 2. События

### 2.1. Публичная семантика

- Подписка принимает точный тип события или wildcard только в конце сегментов. Проверка и
  сопоставление делегированы SDK: `isEventSubscription` и `matchesEventSubscription`.
- Wildcard в середине, частичный wildcard и одиночный `*` отклоняются `TypeError`.
- Неизвестный точный тип события не является ошибкой активации: подписка просто не получает
  событий, пока такой тип не появится.
- Публикация выполняется только явным методом `publishAfterCommit(envelope, { traceId })`.
  Автоматической публикации нет; метод не открывает транзакцию, не ждёт коммита и не откатывает
  источник. Вызывающая сторона обязана вызвать его после успешной фиксации изменения.
- Перед доставкой конверт валидируется через SDK `validateEventEnvelope`. Некорректный конверт не
  доставляется, возвращает `{ status: "invalid", errors }` и журналируется без payload.
- Доставка асинхронная и best-effort: подписчики вызываются параллельно, результат не является
  подтверждением успешной обработки. В результате есть `matchedSubscribers` и
  `failedSubscribers`.
- Ошибка подписчика изолируется: остальные подписчики продолжают работу, источник не откатывается.
- Ошибка журналируется структурно с полями `eventId`, `eventType`, `traceId`, `pluginId` и
  `errorName`. Payload, сообщение ошибки, стек и содержимое ресурсов в журнал не попадают.
- Повторный `eventId` в пределах процесса отбрасывается in-memory dedupe и возвращает
  `{ status: "duplicate" }`. Это не exactly-once: dedupe ограничен по размеру (по умолчанию
  10 000 идентификаторов), живёт в памяти процесса, теряется при перезапуске, а вытесненные
  идентификаторы могут быть доставлены повторно. Подписчики обязаны оставаться идемпотентными.
- `dispose()` очищает подписки и историю `eventId`.

## 3. Ресурсы и связи

### 3.1. Реестр и ResourceService

- `ResourceRegistry.register` принимает plugin ID владельца, список типов ресурсов и адаптер с
  обязательным `resolve`, необязательными `canOpen`/`open`.
- Один plugin ID регистрируется один раз. Дубликат владельца, типа ресурса у другого владельца,
  повтор типа в одном списке, некорректный plugin ID/тип и адаптер без `resolve` отклоняются
  стабильными кодами `DUPLICATE_OWNER`, `DUPLICATE_RESOURCE_TYPE`, `INVALID_REGISTRATION`.
- Проверки выполняются до изменения состояния: неудачная регистрация не оставляет частичных
  записей.
- `resolve` разрешает `ResourceRef` только через адаптер plugin ID из самой ссылки. Неизвестный
  plugin ID или тип, а также `null`/`undefined` от адаптера дают `NOT_FOUND` в `OperationResult`.
  Некорректная строка ссылки даёт `VALIDATION_ERROR`.
- `resolve` не изменяет реестр и не вызывает `canOpen`/`open`. Возвращённый адаптером descriptor
  проверяется по SDK-схеме, а его `ref` и `resourceType` должны совпадать с запросом; иначе
  возвращается `INTERNAL_ERROR`.
- `canOpen` не бросает исключений: неизвестный ресурс, ошибка адаптера и некорректная ссылка дают
  `false`. Если `canOpen` не объявлен, наличие `open` означает `true`.
- `open` бросает `ResourceServiceError` со стабильным кодом `VALIDATION_ERROR`, `NOT_FOUND`,
  `PLUGIN_UNAVAILABLE` (владелец не поддерживает открытие) или `INTERNAL_ERROR`.
- Ошибки адаптеров журналируются безопасно: только операция, pluginId, resourceType, `errorName`
  или стабильная причина; сообщение исходной ошибки не раскрывается.

### 3.2. Связи

- `LinkStore` — backend-neutral асинхронный порт без SQL, таблиц и драйвера БД. Уникальность
  определяется тройкой `sourceRef` + `targetRef` + `relation`; `add` атомарен и при дубликате
  возвращает существующую связь; `remove` идемпотентен; `listByRef` возвращает связи с обеих
  сторон; `deleteByRef` очищает обе стороны.
- `LinkService` реализует `link`/`unlink`/`list`/`cleanup`: проверяет `ResourceRef` и
  namespace-ированный `relation` через SDK, генерирует UTC `createdAt`, идемпотентен при повторе,
  фильтрует список по relation и изолирует ошибки store в `INTERNAL_ERROR`.
- `InMemoryLinkStore` — только тестовая/локальная реализация порта. Персистентности нет;
  реализация Storage Provider остаётся в KAN-006.
- `KernelResourceService` реализует SDK-интерфейс `ResourceService` и делегирует
  `resolve`/`canOpen`/`open` реестру, а `link`/`unlink`/`list` — `LinkService`. Дополнительно
  доступен `cleanup`.
- `subscribeResourceDeletedCleanup` подписывает очистку связей на переданные wildcard-шаблоны.
  Обработчик смотрит только на последний сегмент `deleted` и `envelope.resource`, поэтому не знает
  доменных типов. Контракт не имеет глобального `*`, поэтому composition root передаёт по одному
  шаблону на namespace включённых плагинов (`kanbaner.*`, `acme.*` и т. п.).
- Ошибка очистки пробрасывается в шину, где изолируется и журналируется без payload.

## 6. Невыполненные проверки и остаточные риски

1. **Dedupe не является exactly-once.** Это осознанно документированный in-memory механизм:
   ограничен по числу eventId, не переживает перезапуск и не является очередью. Гарантия
   идемпотентной обработки остаётся обязанностью подписчика.
2. **Persistent LinkStore не реализован.** KAN-006 должен реализовать порт через Storage Provider;
   in-memory store не обеспечивает сохранность и не должен использоваться в production.
3. **Подписка на удаление требует шаблонов namespace.** Контракт разрешает wildcard только в конце
   сегментов, поэтому нет глобального `*`; composition root должен передать шаблоны для
   namespace включённых плагинов.
4. **Соглашение `*.deleted`.** Очистка связей распознаёт последний сегмент `deleted` без доменных
   типов. Если контракт когда-либо введёт другое имя действия удаления, подписчик нужно обновить.
5. **`open` без обработчика возвращает `PLUGIN_UNAVAILABLE`.** В SDK нет отдельного кода
   «операция не поддерживается»; выбран ближайший стабильный код. Это решение зафиксировано в
   коде и тестах.
6. **Windows не проверен.** Окружение worker-а — Linux. Код не использует платформенных API, но
   отдельный прогон на Windows не выполнялся.
7. **Корневой composition point не изменялся.** Экспорт `events/**` и `resources/**` из
   `packages/kernel/src/index.ts` остаётся за оркестратором согласно границам владения.
