## 1. Итог

Реализован серверный runtime плагинов в `@kanbaner/kernel`:

- кроссплатформенное обнаружение локальных `plugin.json`;
- валидация манифеста через публичный SDK до любого импорта кода;
- проверка `hostApi` и диапазонов версий зависимостей через `semver.satisfies`;
- детерминированный граф зависимостей, топологическая активация и циклы с участниками;
- блокировка дублирующихся Plugin ID, отсутствующих и несовместимых зависимостей;
- состояния `failed`, `disabled`, `incompatible`, `missing_dependency`, `safe_mode`;
- изоляция ошибок активации, импорта, hook-ов и деактивации;
- обратная деактивация, откат частичной активации;
- публичный API состояния и диагностики для plugin manager;
- lifecycle hooks для будущего runner-а миграций;
- реальная активация серверного entrypoint через `pathToFileURL` и dynamic import;
- запрет удалённых, абсолютных и выходящих за каталог плагина путей.

Домены, БД, команды, события, ресурсы, UI и миграции не добавлялись.

## 3. Принятые решения

### 3.1. Обнаружение

- Плагин — непосредственный подкаталог корня, содержащий `plugin.json`.
- Корней может быть несколько; результаты сортируются по безопасному ярлыку, индексу корня
  и пути, поэтому порядок файловой системы не влияет на результат.
- `node:path` и `node:fs/promises` используются без bash и платформенных скриптов.
- Абсолютные пути не попадают в публичную диагностику: `source` имеет вид
  `<каталог>/plugin.json`.

### 3.2. Валидация до импорта

- `parsePluginManifest` разбирает JSON, поддерживает UTF-8 BOM и вызывает
  `validatePluginManifest` из SDK.
- Невалидный JSON или схема переводят только этот плагин в `failed`.
- Серверный код невалидного плагина не импортируется; это проверено fixture-модулями,
  которые бросают исключение на верхнем уровне.
- Одинаковый Plugin ID в разных корнях блокирует обе записи с диагностикой
  `duplicate_plugin_id`; зависимые получают `missing_dependency`.

### 3.3. Версии

- По дополнению оркестратора добавлены прямые `semver@7.8.6` (dependency) и
  `@types/semver@7.8.0` (devDependency) в `packages/kernel/package.json` и `pnpm-lock.yaml`.
- `hostApi` проверяется как `satisfies(hostApiVersion, manifest.hostApi)`.
- `requires` проверяется как `satisfies(version зависимости, requiredRange)`.
- Версия Host API по умолчанию — `1.0.0`; её можно переопределить в options.
- Неверный диапазон не считается совместимым; форма диапазона уже проверена SDK.

### 3.4. Граф и блокировки

- Циклы ищутся итеративным алгоритмом Косараджу; участники каждого цикла сортируются.
- Ациклические узлы упорядочиваются алгоритмом Кана; готовые узлы выбираются
  лексикографически по Plugin ID.
- Сначала отмечаются прямые проблемы: duplicate, disabled, hostApi, локальные пути.
- Проблемные узлы исключаются из графа; зависимые блокируются в топологическом порядке.
- Перед каждой активацией выполняется повторная проверка, что все зависимости уже `active`.
  Это блокирует зависимых после runtime-ошибки зависимости, а не только после статической
  проверки.

Соответствие состояний:

| Причина                                                                 | Состояние            |
| ----------------------------------------------------------------------- | -------------------- |
| Невалидный манифест, дубликат ID, цикл, ошибка импорта/активации/hook-а | `failed`             |
| Отключён конфигурацией                                                  | `disabled`           |
| Несовместимый `hostApi` или версия зависимости                          | `incompatible`       |
| Нет зависимости, зависимость недоступна/отключена/упала                 | `missing_dependency` |
| Явный запуск в safe mode                                                | `safe_mode`          |

### 3.5. Активация и деактивация

- Entrypoint разрешается только внутри каталога плагина; отклоняются URL-схемы,
  абсолютные пути, `..`-выходы, NUL и обратные слэши (для одинаковой трактовки Linux/Windows).
- Загрузка выполняется через `pathToFileURL(...).href` и динамический `import()`.
- Поддерживаются именованные `activate`/`deactivate`, объект по умолчанию и функция
  по умолчанию как `activate`.
- `migrate` hook вызывается до импорта и активации.
- При ошибке активации или `afterActivate` вызывается собственный `deactivate` как откат.
- Деактивация идёт строго в обратном порядке активации; ошибка одного плагина не мешает
  деактивировать остальные.
- Ошибки hook-ов, логгера и наблюдателя изолированы.

### 3.6. Диагностика и состояние

- Диагностика содержит стабильный код, фазу, Plugin ID, относительный `source` и безопасные
  детали (идентификаторы, диапазоны версий, причины).
- Сообщения фиксированные; стеки, текст исключений, секреты и абсолютные пути не попадают
  ни в снимок, ни в логгер.
- `getSnapshot()` возвращает рекурсивно замороженные JSON-совместимые данные без Map/Set
  и внутренних записей; `manifest` и диагностики клонируются.
- `problems` содержит проблемные плагины и последнюю причину; `mode`/`safeMode` отражают
  наличие проблем или явный safe mode.
- Safe mode не останавливает unrelated плагины: здоровые плагины активируются, проблемные
  и зависимые от них блокируются.

## 8. Невыполненные проверки

- Windows не проверен: текущее окружение Linux. Пути строятся через `node:path`, entrypoint
  загружается через `pathToFileURL`, но отдельный прогон на Windows не выполнялся.
- Symlink-тест на Linux выполнен реально. На Windows без соответствующих прав он честно
  помечается как skip через `context.skip`, а не считается пройденным.
- Реальные миграции и Storage Provider не проверялись: KAN-003 проверяет только локальность
  и тип каталога `migrations`, а выполнение миграций остаётся следующему этапу.
- Клиентская регистрация UI-вкладов не реализована: это KAN-007.
- Динамическое включение/отключение уже запущенного плагина не реализовано. Конфигурация
  `disabledPlugins` действует на старте; для изменения набора нужен `stop()` и новый `start()`.

## 9. Остаточные риски

1. **Windows-пути и junction.** Манифесты должны использовать прямые слэши; обратные слэши
   отклоняются намеренно. Canonical containment реализован через `realpath`, но Windows
   junction-поведение отдельно не прогонялось.
2. **Rollback не повторяется.** Если `deactivate` при откате бросил исключение, runtime
   фиксирует `rollback_failed`, но повторную попытку не делает: плагин остаётся `failed`.
3. **Кэш ESM.** Повторный `start()` после `stop()` использует кэш динамического импорта Node.
   Состояние плагина сбрасывается, но module-level состояние самого плагина не пересоздаётся.
4. **Safe mode автоматически включается при любом problem-статусе**, включая несовместимость,
   отсутствующую зависимость и недоступный root. Это соответствует требованию «safe mode
   содержит проблемные плагины», но требует согласованного отображения в plugin manager.
5. **Диагностика не содержит текст исключения.** Это осознанная защита от утечки секретов и
   внутренних путей; для отладки разработчику нужен отдельный механизм с явным включением.
6. **`root#N` позиционный.** Метка различает корни и не раскрывает абсолютный путь, но при
   изменении порядка `pluginDirectories` меняется и метка. Это приемлемо для локального
   однопользовательского runtime.
7. **Обнаружение сканирует только непосредственные подкаталоги корня и игнорирует
   `node_modules`.** Вложенные структуры плагинов не поддерживаются.
