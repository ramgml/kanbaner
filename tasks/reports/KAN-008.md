## 1. Итог

Plugin Contract v1 доказан на реальном fixture-плагине. Fixture использует только
`@kanbaner/plugin-sdk`, активируется публичным lifecycle и регистрирует команду, запрос,
тип ресурса, событие, идемпотентный обработчик audit-записи, UI-вклады и SQLite-миграцию.
Production-код shell не импортирует fixture: UI-метаданные приходят с сервера как
сериализуемые декларации SDK, а command/query выполняются через общий `OperationBus`
через server action.

Расширение lifecycle и composition:

- `PluginActivationServices`/`PluginHostServices` и структурные контракты
  `PluginCommandService`, `PluginQueryService`, `ResourceRegistrar`, `EventService`,
  `UiContributionRegistrar` добавлены в публичный SDK (`packages/plugin-sdk/src/activation.ts`).
- `PluginHostServices.storage` остаётся полным `StorageProvider` только у доверенного
  composition root. Activation и execution получают bound `PluginStorage` по текущему
  `pluginId`: доступны только `documents` и transaction-scoped `documents`, без
  `open/close/migrations/pluginStates/links/searchIndex/createStore` и без чужого
  namespace-а. `OperationBus` выбирает фасад по `operation.pluginId`, а не отдаёт
  raw singleton.
- `ExecutionContext.events` — publication-only `PluginEventPublisher`: подписки
  регистрируются только activation tracker-ом и снимаются при `stop()`. Публикация
  проверяет `source`, `type` и владельца `ResourceRef`; чужой namespace отклоняется
  с `PERMISSION_DENIED` в execution и activation.
- Поиск вынесен в публичный контракт SDK: `SearchDocumentInput`,
  `toSearchDocument`, `PluginSearchService` и host `SearchRegistrar`. Плагин получает
  bound-сервис, host-индекс между плагинами не раскрывается.
- Cleanup удалённого ресурса проверяет, что `ResourceRef` принадлежит `envelope.source`,
  очищает связи и поисковый документ ответственного плагина; чужие связи сохраняются.
- `PluginRuntime` принимает общие сервисы composition root, создаёт bound-сервисы на
  плагин и снимает все регистрации при rollback, `deactivate()` и повторном `start()`.
- Unavailable defaults не дают плагину молча «активироваться» без composition root.
- `apps/web` собирает один экземпляр EventBus, ResourceRegistry, LinkService,
  KernelResourceService, OperationBus и UI metadata registry поверх активного Storage
  Provider. Production LinkStore — SQLite, не in-memory.
- `ResourceServiceError` маппится в единый конверт операции; удаление ресурса очищает
  универсальные связи и поисковый индекс через подписку на событие.
- Загрузка серверного модуля плагина помечена `webpackIgnore`/`turbopackIgnore`, иначе
  production Next/Turbopack пытался разрешить динамический import на этапе сборки и
  падал с `MODULE_NOT_FOUND`.

Поведение KAN-007/KAN-009 сохранено: plugin manager по-прежнему управляет lifecycle,
SQLite WAL остаётся активным provider-ом, отдельной реализации операций для UI/MCP нет.

## 2. Fixture-плагин

`packages/plugin-fixture`:

- manifest `plugin.json` (`kanbaner.fixture`, host API `^1.0.0`);
- команда `kanbaner.fixture.item.create` (`mutation`, `risk = write`, `exposure.ui = true`);
- команда `kanbaner.fixture.item.delete` (`destructive`, `exposure.ui = false`);
- команда `kanbaner.fixture.item.reindex` (`exposure.ui = false`);
- запрос `kanbaner.fixture.item.list` (`exposure.ui = true`);
- запрос `kanbaner.fixture.item.search` (`exposure.ui = false`);
- `http` и `mcp` выключены у всех fixture-операций;
- тип ресурса `item` с `resolve`/`canOpen`/`open`;
- событие `kanbaner.fixture.item.created` публикуется только после успешной транзакции;
- событие `kanbaner.fixture.item.deleted` публикуется после удаления;
- подписка на собственное событие с идемпотентной audit-записью (повторный `eventId`
  не создаёт дубль);
- UI-вклады `panel` и `list-panel` в слот `app.main`;
- миграция `migrations/001_fixture-audit.sql` (namespace-таблица плагина).

Создание и удаление выполняются через `await storage.withTransaction(...)`. Поиск и
публикация события — best-effort после коммита: ошибка логируется и не превращает уже
зафиксированный результат в `INTERNAL_ERROR`. Полная переиндексация сохраняет документы
других плагинов.

`exposure.ui` задан явно только у `item.create` и `item.list`, потому что только эти
операции вызывают UI-вклады. Default-off в SDK не менялся: все остальные каналы и
операции остаются недоступными, пока плагин не включит их сам.

В исходниках fixture нет импортов `@kanbaner/kernel`, React, SQL, драйвера БД и
синхронных вызовов хранилища. Это проверяется `scripts/check-import-boundaries.mjs`.

## 3. Контрактные и интеграционные проверки

`tests/contract`:

- активация fixture только через публичный lifecycle;
- выполнение команды и запроса через общий `OperationBus`;
- публикация события после коммита и идемпотентность обработчика;
- отсутствие публикации при откате записи;
- публикация после коммита на delayed SQLite;
- ошибка best-effort публикации не маскирует успешный результат;
- разрешение `ResourceRef` через публичный `ResourceService`;
- создание → публичный поиск → удаление → отсутствие документа → полная переиндексация;
- очистка связей и поиска только у владельца удалённого ресурса (чужие связи сохранены);
- снятие регистраций и подписок при `stop()` с сохранением данных;
- однократное применение миграции и повторный старт на той же базе;
- повторная доставка envelope через новый EventBus/runtime не создаёт второй audit;
- работа с provider-ом, у которого включены асинхронные задержки;
- стабильные две страницы `limit`/`offset` с `nextOffset`;
- негативные проверки bound storage/search/events: чужой `pluginId`, lifecycle-методы,
  `subscribe` в execution context и чужой ResourceRef дают отказ;
- явный `exposure.ui` только у операций, реально вызываемых через UI;
- дублирующийся command ID, отсутствующая зависимость, цикл зависимостей, safe mode,
  откат регистраций после неудачной повторной активации;
- автоматическая проверка границ импортов и её self-test.

`scripts/check-import-boundaries.mjs` разбирает исходники через TypeScript AST:
named/side-effect import, export-from, `require` и dynamic import. Относительные пути
разрешаются от файла и не могут выходить за fixture; production-код не может ссылаться
на fixture ни относительно, ни по имени пакета. SQL-паттерны проверяются без учёта
регистра. Self-test отдельно проверяет relative kernel, side-effect import, lowercase SQL,
export/require/dynamic import и production relative fixture, а также отсутствие ложного
срабатывания на `@kanbaner/plugin-sdk` и локальном импорте.

### 3.1 Исправления повторного ревью

1. Raw `StorageProvider` больше не попадает в activation/execution: выдан bound
   `PluginStorage` по `operation.pluginId`; lifecycle-методы и чужие документы
   недоступны. Добавлены негативные тесты.
2. Добавлен публичный поисковый контракт (`toSearchDocument`, `PluginSearchService`,
   `SearchRegistrar`) и bound-сервис. Fixture проходит создание → поиск → удаление →
   отсутствие → полную переиндексацию. Удаление ResourceRef очищает поиск владельца.
3. Fixture пишет через `storage.withTransaction`; publish выполняется после коммита,
   best-effort-ошибка логируется и не маскирует успех. Есть тесты отката, delayed SQLite
   и ошибки публикации.
4. `ExecutionContext.events` содержит только `publishAfterCommit`; подписки живут в
   activation tracker и удаляются при `stop()`.
5. Bound publish и cleanup проверяют владельца `ResourceRef`; mismatch даёт
   `PERMISSION_DENIED`, чужие связи сохраняются.
6. Границы импортов переписаны на TypeScript AST с relative-resolution, запретом выхода
   из fixture/ссылок production → fixture и case-insensitive SQL; self-test проверяет
   отдельные сценарии и конкретные правила.
7. Повторная доставка envelope через новый EventBus/runtime на той же базе оставляет
   одну audit-запись; после `stop()` подписка не вызывается.
8. Fixture query поддерживает `limit`/`offset` и возвращает `nextOffset`; тест проверяет
   две стабильные страницы.
9. `isOperationResult` использует `validateOperationResult`: success и error — `true`,
   malformed — `false`; добавлены тесты.
10. E2E проверяет `safe-mode-notice` на `/` и `safe-mode-panel` на `/plugins`.

`tests/integration/composition-conformance.test.ts` запускает выбранные 9 case общего
Storage Provider Conformance Suite на четырёх вариантах:

1. in-memory provider;
2. in-memory provider с задержками;
3. SQLite provider;
4. SQLite provider с задержками.

Полный suite остаётся в unit-тестах provider-ов; integration-проверка фиксирует явный
путь через `createApplicationStorage`.

## 4. E2E

Playwright 1.65, production custom server, изолированный `KANBANER_DATA_DIR` внутри
`apps/web/node_modules`, без прямого доступа к SQLite и без обхода UI:

- серверный layout передаёт UI-метаданные fixture в клиентский реестр;
- кнопка вклада вызывает server action;
- команда создаёт запись и возвращает `id`;
- запрос видит созданную запись, в том числе после перезагрузки страницы;
- fixture отображается активным в plugin manager; на `/` отсутствует `safe-mode-notice`,
  на `/plugins` отсутствует `safe-mode-panel`;
- существующий shell-тест переключателя плагинов ограничен карточкой
  `example.e2e-switch`, потому что в registry появился второй плагин.

`E2E_PLUGIN_DIRS` содержит два discovery root через `path.delimiter`: каталог
E2E-fixtures и `packages/`, где ядро находит `plugin-fixture/plugin.json`. Сам путь
пакета как root не используется.

Production SIGTERM проверен `apps/web/scripts/server.shutdown.test.mjs`: сервер
перестаёт принимать запросы, дожидается deferred write и выполняет checkpoint.

## 7. Остаточные риски и ограничения

- Прогон на Windows в этом окружении недоступен. Код использует `node:path`,
  `path.delimiter` и каталоги данных внутри `node_modules`; matrix Windows остаётся
  обязательной проверкой CI. Нативный `better-sqlite3` проверен только на Linux.
- Integration-проверка Conformance запускает выбранные 9 case на четырёх provider-ах,
  а не весь suite: полный набор уже выполняется в unit-тестах provider-ов.
- Контрактные тесты проверяют публичное поведение; при изменении внутренних API ядра
  они не должны требовать правок, кроме согласованного изменения контракта.
- Fixture остаётся `private` и не публикуется; production bundle не содержит импорта
  fixture, что проверяется скриптом границ.
- `E2E_PLUGIN_DIRS` указывает на `packages/`; перед E2E fixture должен быть собран
  (`pnpm build` или `pnpm build:packages`).
