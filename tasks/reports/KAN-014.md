### Исправления по findings ревью

1. **HIGH: позиция перемещения.** `computeMovePosition` по видимому subset
   заменён на `resolveMovePosition(tasks, taskId, intent)`. Перед `task.move`
   `fetchAllScopeTasks` читает все страницы полного нефильтрованного списка
   `(projectId, status)` с `limit: 200`, без `tag` и пагинации. `append` равен
   реальной длине scope, `beforeId` — индексу в полном списке, `start`/`end`
   учитывают скрытых фильтром соседей. После успешного move
   `loadedCountsRef[status] >= position + 1`, а `fetchColumnPage` догружает
   target-колонку, пока карточка не появится.
2. **HIGH: гонки пагинации.** Добавлены поколение reload, отдельный
   sequence на каждую колонку и ключ фильтра. Курсор — серверный `nextOffset`.
   Полностью дублированная или пустая страница не закрывает пагинацию:
   колонка перечитывается с начала. Запоздавший `loadMore` не применяется
   после filter change, move или reload.
3. **MEDIUM: устаревшая задача в overlay.** Рендер и все команды используют
   `currentTask` только при `task.id === taskId`. При переходе A → B данные A
   не показываются, действия заблокированы до загрузки B, project/parent
   относятся к B.
4. **MEDIUM: query navigation.** Добавлен additive `search` в
   `UiRendererProps`; он протянут через `AppShell` (`useSearchParams`) →
   `UiSlot`/`ContributionRenderer` → `PluginView` → registry → плагин.
   Дополнительно shell передаёт `replaceSearch` (`router.replace`), поэтому
   `useSearchParams` остаётся синхронным после локального изменения query;
   fallback — `history.replaceState`. Настоящий `Link` на тот же pathname
   закрывает overlay, уход на другой маршрут скрывает его. `task-list` и
   fixture не затронуты.
5. **MEDIUM: счётчики подзадач.** По `query.revision` счётчики
   перезапрашиваются для всех видимых корневых карточек. Ошибка запроса
   отображается как `—` и не кэшируется как `0`. После удаления подзадачи в
   overlay счётчик родителя обновляется без remount доски.
6. **LOW: focus в modal.** `ModalDialog` фокусирует первый focusable, когда
   содержимое появилось после загрузки; сам `<dialog>` не считается
   пользовательским фокусом. После реального действия
   (`click`/`pointerdown`/`keydown`) фокус не перехватывается.
7. **Tailwind.** В `apps/web/src/app/globals.css` добавлен
   `@source "../../../../packages/plugin-kanban/src"`.

### Исправления повторного ревью

1. **HIGH: filtered «Выше»/«Ниже».** `MoveIntent` больше не содержит
   `relative`: направление нельзя считать как `currentIndex ± 1` полного
   scope. Сначала строится optimistic placement по видимому списку, затем
   `visibleMoveIntent` берёт следующую видимую карточку после перемещаемой:
   её ID становится `before`-anchor-ом, отсутствие следующей даёт `append`.
   Полный scope используется только для перевода anchor-а в позицию. Пример
   `A(release), B(other), C(release)`: «Ниже» для A даёт `C, A`, а не `A, C`.
   Покрыто component-тестами «Ниже»/«Выше» со скрытыми соседями с обеих
   сторон и отдельным E2E.
2. **MEDIUM: terminal-дубликаты и stale ID.** Если `appended.length === 0`
   (пустая или полностью дублированная страница), колонка **всегда**
   перечитывается с начала через `reloadBoard()`; пагинация не закрывается по
   счётчику этой страницы. Это убирает stale ID при уменьшении `total` или
   сдвиге позиций: reload не вызывает `loadMore`, поэтому цикла нет, а
   актуальные `total`/`nextOffset` приходят из нового чтения. Deferred-тест с
   `items.length < total` проверяет восстановление скрытых задач; regression
   test «удалены 2 из первых 10, loadMore пуст, total=10» проверяет, что stale
   ID исчезают, а две прежние хвостовые задачи появляются.
3. **MEDIUM: одновременные moves.** Один `visibilityRef` заменён на
   `Map<taskId, { status, position, filterKey }>`. `reloadBoard` учитывает весь
   набор требований текущего фильтра: цель по количеству — максимум
   required-позиций, а `fetchColumnPage` дополнительно читает страницы, пока
   не появятся все required ID. Требование снимается только когда актуальный
   reload действительно содержит ID; reload с другим фильтром его не стирает.
   Deferred-тест двух одновременных append с позициями 12 и 13 проверяет, что
   обе карточки за границей страницы остаются видимыми.

## Ограничения и риски

- **Restart процесса в E2E:** Playwright сам владеет lifecycle webServer,
  поэтому сценарий перезапускает не процесс, а страницу (`reload`) и повторно
  читает SQLite. Корректность graceful shutdown/checkpoint проверена отдельным
  `server.shutdown.test.mjs`; для настоящего process restart нужен отдельный
  тестовый harness.
- Позиции уникальны в области `(projectId, status)`. На общей доске без
  фильтра проекта порядок между проектами определяется доменной сортировкой
  `position, id`, а не глобальным индексом колонки.
- Число непосредственных подзадач — отдельный `task.list` с
  `parentTaskId`/`limit: 1` на каждую видимую корневую карточку (N+1).
  Агрегата в контракте задач нет.
- `replaceSearch` вызывает `router.replace` на каждое изменение query
  (включая ввод тега). Для локального однопользовательского приложения это
  приемлемо и сохраняет `useSearchParams` источником истины; при необходимости
  можно добавить debounce отдельной задачей.
- DnD не покрыт jsdom-тестом pointer-геометрии: E2E проверяет реальные
  pointer events в Chromium, component-тесты — состояние и команды.
- Компонентные тесты используют модульное состояние query string; между
  тестами оно сбрасывается `resetKanbanQueryForTests`, а writer-ы очищаются
  при unmount.
- Требование видимости привязано к `filterKey`. Если фильтр сменился во время
  move и карточка в него не попадает, требование остаётся в `Map` до reload с
  исходным фильтром; это не теряет карточку, но может дать один лишний
  догрузочный запрос. Очистка по «доказанному отсутствию» не делается, чтобы
  не снять требование до появления карточки.
