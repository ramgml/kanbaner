## 1. Итог

Реализована шина команд и запросов ядра в `packages/kernel/src/operations/**`.

Шина предоставляет отдельные хранилища команд и запросов с общим пространством
operation ID, проверяет метаданные и вход через публичные валидаторы Plugin SDK,
возвращает единый `OperationResult` и поддерживает вложенные вызовы с общим
`traceId`, ограничением глубины и обнаружением циклов. HTTP, БД, события,
ресурсы и доменные команды не добавлялись.

## 2. Публичный API

Точка входа — `packages/kernel/src/operations/index.ts`.

```ts
import {
  OperationFailure,
  OperationRegistrationError,
  createOperationBus,
} from "./operations/index.ts";

const bus = createOperationBus({
  maxDepth: 16,
  validateOutput: false,
  logger,
  resources,
  storage,
});

bus.registerCommand({ metadata: commandMetadata, handler });
bus.registerQuery({ metadata: queryMetadata, handler });

const result = await bus.executeCommand(
  "kanbaner.tasks.create",
  { title: "Подготовить релиз" },
  { source: { type: "ui", id: "web" }, idempotencyKey: "optional-key" },
);
```

Основные экспорты:

- `OperationBus`, `createOperationBus`, `OperationBusOptions`;
- `OperationRegistry`, `OperationStore`;
- `CommandExecutor`, `QueryExecutor`, `ExecutionOptions`;
- `CommandRegistration`, `QueryRegistration`, `OperationHandler`;
- `OperationDescriptor`, `RegisteredOperation`;
- `OperationFailure`, `OperationRegistrationError`, `OPERATION_LIMIT_REASONS`;
- `createRequestId`, `createTraceId`, `NOOP_LOGGER`, `createUnavailableResourceService`;
- `DEFAULT_MAX_DEPTH`.

Семантика:

- обработчик возвращает только данные; шина оборачивает их в `{ ok: true, data }`;
- ожидаемая ошибка — `throw new OperationFailure(code, message, { details })`;
- ошибка вложенного вызова пробрасывается через `OperationFailure.from(result.error)`;
- верхний вызов принимает `source`, `signal`, `deadline`, `idempotencyKey`;
- `ctx.commands.execute` и `ctx.queries.execute` доступны обработчику и сохраняют
  `traceId`, `source`, deadline и цепочку выполнения.

## 3. Принятые решения

### 3.1. Реестры и уникальность ID

- Команды и запросы хранятся в отдельных `TypedOperationStore` с собственными
  `Map`. Наружу они опубликованы как `OperationRegistry.commands` и
  `OperationRegistry.queries`.
- Общий `Set` operation ID обеспечивает уникальность внутри одного вида и между
  командами и запросами.
- Дубликат отклоняется до изменения реестра с
  `OperationRegistrationError.code = "DUPLICATE_OPERATION_ID"`.
- `unregister` освобождает ID; это подготовка к деактивации плагина в KAN-003.

### 3.2. Метаданные

- Используются `validateCommandMetadata` и `validateQueryMetadata` из SDK:
  `kind`, `risk`, `version`, `exposure`, `inputSchema`, `outputSchema` и
  компилируемость схем.
- Дополнительно отклоняются неизвестные каналы `exposure` (`ftp`, опечатки):
  неизвестный канал нельзя молча игнорировать.
- `resolveExposure` применяется при регистрации; отсутствующий `exposure`
  превращается в `{ ui: false, http: false, mcp: false }`.
- Ошибка регистрации содержит только безопасные `path`, `schemaPath`, `keyword`
  и `message`, без значений входа.

### 3.3. Валидация входа и выхода

- Валидаторы входа и выхода компилируются один раз при регистрации через
  `createOperationInputValidator` и `createOperationOutputValidator`.
- Вход проверяется до вызова обработчика. При ошибке возвращается
  `VALIDATION_ERROR` с безопасными issues, обработчик не вызывается.
- Проверка выхода включается только явно: `createOperationBus({ validateOutput: true })`.
  Это тестовый/strict-режим. Неверный выход даёт `INTERNAL_ERROR` с
  `details.reason = "invalid_output"`.
- AJV напрямую не используется и схемы не дублируются: только SDK-валидаторы.

### 3.4. Конверт результата и ошибки

Успех и ошибка всегда возвращаются как `OperationResult`, исключения наружу не
выбрасываются.

| Ситуация                              | Код                | `details`                             |
| ------------------------------------- | ------------------ | ------------------------------------- |
| Неизвестная операция или чужой реестр | `NOT_FOUND`        | `operationId`, `kind`                 |
| Неверный вход                         | `VALIDATION_ERROR` | `operationId`, `issues`               |
| Неверный source/deadline/idempotency  | `VALIDATION_ERROR` | `field` или `issues`                  |
| Отмена                                | `CANCELLED`        | —                                     |
| Deadline                              | `TIMEOUT`          | —                                     |
| Цикл вложенных вызовов                | `INTERNAL_ERROR`   | `reason = "operation_cycle"`, `chain` |
| Превышение глубины                    | `INTERNAL_ERROR`   | `reason`, `depth`, `maxDepth`         |
| Неверный выход                        | `INTERNAL_ERROR`   | `reason = "invalid_output"`, `issues` |
| Произвольное исключение               | `INTERNAL_ERROR`   | —                                     |

Для циклов и глубины не вводились новые коды Plugin Contract: используются
стабильные причины в `details.reason`. Произвольный `Error` не передаёт наружу
сообщение, стек, внутренние пути и секреты.

### 3.5. Контекст и трассировка

- `requestId` и `traceId` создаются через `randomUUID` из `node:crypto`.
- Вложенный вызов получает новый `requestId`, но сохраняет `traceId` и `source`
  родителя. Плагин не может подменить источник вложенного вызова.
- `source.type` по умолчанию — `system`; source валидируется схемой SDK.
- `deadline` вложенного вызова — более ранний из родительского и собственного.
- `idempotencyKey` передаётся в контекст без хранения и дедупликации; вложенный
  вызов не наследует ключ родителя, его нужно передать явно.
- Стек выполнения хранит ID всех активных вызовов; цикл определяется по
  повторному ID в текущей цепочке. Глубина верхнего вызова — 1, по умолчанию
  допускается 16 уровней.

### 3.6. Отмена и таймаут

- `AbortSignal` кооперативный: обработчик получает сигнал и может остановиться.
- Шина также прекращает ожидание по сигналу и deadline, даже если обработчик
  игнорирует сигнал. Позднее завершение обработчика не создаёт unhandled
  rejection: к его Promise всегда подключён обработчик.
- Таймаут дополнительно прерывает внутренний `AbortController`, чтобы
  кооперативный обработчик увидел отмену.
- Причина прерывания передаётся вложенным вызовам через reason сигнала, поэтому
  таймаут родителя не превращается в `CANCELLED` у потомка.
- Отмена после уже выполненной записи не откатывается; шина не обещает rollback.

### 3.7. Инфраструктурные заглушки

- `ctx.resources` по умолчанию — явно недоступный сервис, возвращающий
  `PLUGIN_UNAVAILABLE` через rejected Promise. Пустые успешные данные не
  подделываются.
- `ctx.storage` передаётся из настроек шины как `unknown`; Storage Provider
  появится в KAN-006/KAN-009.
- Логгер по умолчанию — no-op. При завершении пишется только безопасный набор:
  `operationId`, `pluginId`, `kind`, `source.type`, `requestId`, `traceId`,
  `depth`, `durationMs`, `ok`, `code`. Вход, payload, сообщения исключений и
  детали ошибок не журналируются.

## 7. Остаточные риски и ограничения

1. Корневой `packages/kernel/src/index.ts` намеренно не изменён. Шина станет
   частью публичного API пакета после координации с оркестратором; сейчас она
   доступна через локальный `operations/index.ts` и тесты.
2. `ctx.resources` — заглушка до KAN-005. Обращение к ней даёт
   `PLUGIN_UNAVAILABLE`, а не рабочий сервис ресурсов.
3. Идемпотентность не реализована ядром: ключ только передаётся плагину.
   Хранение, сравнение payload и `IDEMPOTENCY_CONFLICT` остаются в доменном
   плагине.
4. Отмена и таймаут не откатывают уже выполненные записи. Это осознанно: шина
   не управляет транзакциями плагина и не обещает компенсацию.
5. Для циклов и глубины используется `INTERNAL_ERROR` с `details.reason`,
   поскольку добавлять новый код в Plugin Contract v1 нельзя. Если контракт
   получит отдельный стабильный код, маппинг нужно обновить.
6. Сообщение и `details` в `OperationFailure` формирует плагин; шина доверяет
   ему как доверенному локальному коду. Произвольные исключения санитизируются.
7. Версия операции проверяется в метаданных, но согласование версии при вызове
   (`operationVersion`) не реализовано — это не входило в KAN-004.
8. Логирование ограничено безопасным `debug`-событием; постоянного журнала и
   метрик нет.
9. Отдельного `pluginId` при регистрации нет: он выводится из operation ID.
   Привязка операций к жизненному циклу плагина остаётся в KAN-003.
