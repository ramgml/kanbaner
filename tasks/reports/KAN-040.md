# KAN-040 — Отчёт

- Задача: `tasks/KAN-040-contract-test-timeouts.md`
- Ветка: `fix/kan-040-contract-timeouts`
- Worktree: `.worktrees/kan-040-contract-timeouts`
- Коммит: `<sha будет указан оркестратору после commit>`

## Итог

Причина падений — холодный старт тяжёлых integration/contract suite под полной
нагрузкой полного прогона, а не дефект lifecycle. Тесты не удалены, не
переведены в `skip`, утверждения не ослаблены. Для четырёх suite, которые
поднимают полный composition root (SQLite + discovery + динамический импорт и
активация всех встроенных плагинов), задан явный конечный таймаут 30 с.
Остальные тесты продолжают работать с глобальными 5 с.

## Доказательство причины

Измерения на 20 vCPU, Node 24.22.2, Vitest 5.1.0.

1. Воспроизведение на исходном коде: полный `pnpm vitest run` упал на
   `tests/contract/task-list-disabled.test.ts` («не активируется и не публикует
   UI-вклады») с `Test timed out in 5000ms`; тело теста — 5095 мс.
   Всего 119 файлов / 1637 passed / 1 failed, 48.35 с.
   Сам Vitest сообщил: `119 workers spawned · ~707ms startup each`.
2. Изолированный запуск тех же двух файлов: 20/20 passed за 19.24 с. То есть
   без конкуренции за CPU всё завершается, зависания нет.
3. Тот же полный прогон с `--testTimeout=30000`: 1638/1638 passed.
   Длительности проблемных первых тестов — 3869 мс (`fixture-activation`),
   3964 мс (`task-list-disabled`), 3995 мс (`tasks-activation`), то есть
   значения ходят вокруг границы 5 с, а не зависают.
4. Профилирование фаз `startFixtureHarness` (временная инструментация, затем
   удалена):
   - `prepareProvider` (SQLite + миграции): 10–120 мс;
   - `createApplicationPluginComposition`: ~1 мс;
   - `bindPlugins`: 0–1 мс;
   - `runtime.start` (discovery + динамический импорт + активация плагинов):
     первый harness в воркере — 3401–3870 мс, последующие — p50 ~1088 мс;
   - все 28 запусков harness в полном прогоне завершились, максимум total
     ~3991 мс, ни одного зависания дольше 30 с.
     Это профиль cold start на воркер, а не lifecycle-дефект.
5. Дополнительное подтверждение границы: промежуточный `pnpm check` после
   исправления только fixture-harness упал уже на
   `tests/integration/tasks-activation.test.ts` с тем же `5000ms`. У этого
   файла первый тест в загруженном прогоне занимал 3995 мс — та же причина,
   другой suite.
6. Проверка, что таймаут реально применяется: временно выставленное значение
   1 с дало `Test timed out in 1000ms` для `task-list-disabled` (2 теста) и
   `tasks-activation` (32 теста); после возврата 30 с всё зелёное.

`tests/integration/notes-activation.test.ts` не менялся: его максимальная
наблюдаемая длительность — 1712 мс, далеко от границы; менять его нет оснований.

## Что сделано

- Добавлен общий helper `tests/suite-timeouts.ts` с
  `HEAVY_PLUGIN_SUITE_TIMEOUT_MS = 30_000` и готовыми опциями suite
  `heavyPluginSuite`.
- Таймаут подключён точечно к suite, которые поднимают полный composition root:
  - `tests/contract/fixture-activation.test.ts`;
  - `tests/contract/lifecycle-contract.test.ts`;
  - `tests/contract/task-list-disabled.test.ts`;
  - `tests/integration/tasks-activation.test.ts`.
- Глобальный `testTimeout` в `vitest.config.ts` не менялся; unit-тесты остались
  с 5 с. Таймаут конечный, поэтому настоящее зависание lifecycle по-прежнему
  будет обнаружено (через 30 с).

## Проверки

Финальная версия кода (после всех правок):

- `pnpm vitest run` №1 — passed: 119 файлов / 1638 тестов, 49.80 с.
- `pnpm vitest run` №2 (сразу после №1) — passed: 119 файлов / 1638 тестов,
  53.87 с.
- `pnpm check` — exit 0: `format:check`, `lint`, `typecheck`, `test`
  (119 файлов / 1638 тестов, 51.60 с) и `build` прошли.
- `pnpm lint` отдельно — exit 0.
- `prettier --check` по изменённым файлам — passed.
- Проверка применения таймаута через временное значение 1 с — подтверждена,
  затем значение возвращено на 30 с.

До исправления:

- `pnpm vitest run` — 1 failed / 1637 passed (timeout 5000 мс в
  `task-list-disabled`), 48.35 с.
- `pnpm vitest run` — 119 файлов / 1638 тестов passed, 47.03 с.
- `pnpm vitest run` — 119 файлов / 1638 тестов passed, 50.79 с.
- Изолированно 2 файла — 20/20 passed, 19.24 с.
- `pnpm check` (промежуточная версия) — exit 1, timeout в
  `tests/integration/tasks-activation.test.ts`.

## Отклонения от плана

- Изначально таймаут был добавлен только в трёх contract-файлах через константу
  в `tests/contract/fixture-harness.ts`. `pnpm check` выявил тот же cold start
  в `tests/integration/tasks-activation.test.ts`, поэтому константа вынесена в
  общий `tests/suite-timeouts.ts` и подключена к четвёртому suite.
- Вариант с `describe(name, { timeout }, fn)` отклонён: Prettier переформатирует
  тело на многострочный вызов и создаёт diff на ~1100 строк. Использован
  вынесенный объект опций `heavyPluginSuite`, diff минимальный.

## Риски и ограничения

- Таймаут 30 с в четырёх тяжёлых suite означает, что реальный lifecycle-дефект
  в них будет обнаружен позже (до 30 с), чем при 5 с. Это осознанный компромисс:
  значение конечно и явно, покрытие и утверждения не изменены.
- Измерения сделаны на 20 vCPU. На машине с другим числом ядер абсолютные
  длительности будут другими, но запас 30 с рассчитан с большим отрывом от
  наблюдавшихся 4–5 с.
- E2E-тесты (`pnpm --filter @kanbaner/web test:e2e`) в рамках задачи не
  запускались: они не входят в `pnpm check` и не затрагиваются изменением.
- `notes-activation`, несмотря на схожую архитектуру, не переведён на новый
  таймаут: наблюдаемый максимум 1712 мс не даёт доказательств необходимости.

## Предложенные задачи

- При желании уменьшить cold start полного прогона: рассмотреть `isolate: false`
  или разнесение тяжёлых activation suite по отдельному проекту Vitest, чтобы
  не зависеть от числа воркеров. Требует отдельной проверки на утечки состояния
  между файлами.
