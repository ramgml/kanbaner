### 2.1. Дополнительный duplicate-`$id` fix

При проверке `createResultValidator(JsonObjectSchema)` Ajv падал с
`reference "urn:kanbaner:json-object:N" resolves to more than one schema`: одна и та же
схема с `$id` встраивалась и в success-ветку (`data`), и в error-ветку (`error.details`).

Исправление:

- в `errors.ts` добавлены фабрики `createPluginErrorSchema()` и `createErrorResultSchema()`,
  которые создают свежие вложенные JSON-схемы с уникальными `$id`;
- `createResultSchema` использует `createErrorResultSchema()` вместо константы
  `ErrorResultSchema`;
- добавлен регрессионный тест: `createResultValidator(JsonObjectSchema)` и
  `createResultValidator(createJsonObjectSchema())` успешно принимают
  `{ ok: true, data: { a: 1 } }`, принимают валидную error-ветку и отклоняют
  `data: null`, function внутри `data` и неверный код ошибки;
- проверено, что фабрики не создают новых конфликтов при вложении success/error веток.

### 2.2. Системный boundary-guard

Повторное ревью показало, что прежний guard зависел от маркера корневой схемы и поэтому
пропускал `Date`/`Map` и циклы внутри `inputSchema`/`outputSchema` при валидации metadata,
а также в `validateWithSchema(createResultSchema(...), value)` и
`createSchemaValidator(OperationEnvelopeSchema)`.

Исправление:

- `findJsonValueIssue` теперь вызывается до Ajv в `validateWithSchema` и в обоих методах
  `createSchemaValidator` (`check` и `validate`), независимо от схемы;
- все специализированные валидаторы (`validateOperationEnvelope`, `validateEventEnvelope`,
  `validateOperationResult`, `validatePluginError`, `validateResourceDescriptor`,
  `createResultValidator` и metadata-валидаторы) используют общий путь и не содержат
  собственных обходных pre-check;
- циклы и non-plain объекты отклоняются до компиляции/вызова Ajv, поэтому stack overflow
  невозможен;
- валидные повторно используемые (не циклические) объекты и схемы по-прежнему принимаются:
  guard удаляет объект из stack после завершения ветки, а не считает любое повторение циклом;
- маркер `JSON_CONTRACT_SCHEMA`/`isJsonContractSchema` удалён: он больше не влияет на
  безопасность и не создаёт ложного впечатления, что guard можно включить только маркером.

## 4. Принятые решения

### 4.1. Идентификаторы и версии

- Plugin ID — ровно два сегмента `<namespace>.<plugin>` в нижнем регистре; сегменты
  `[a-z][a-z0-9-]*`.
- Operation ID — Plugin ID плюс один или несколько action-сегментов.
- Event type — ровно четыре сегмента: Plugin ID, resource type, past-tense action.
- Contract ID — Plugin ID, имя контракта и `.v<major>`.
- Relation — минимум два namespace-сегмента; `minLength = 3`, поэтому `a.b` валиден.
- Версия плагина проверяется как строгий SemVer 2.0.0 с обязательными
  `major.minor.patch`, корректными prerelease/build и запретом ведущих нулей.
- `hostApi` проверяется через `semver.validRange` с отдельным запретом пустой строки;
  совместимость версий остаётся задачей ядра.

### 4.2. Манифест

- Обязательные поля: `id`, `name`, `version`, `hostApi`, `entrypoints`, `requires`, `consumes`,
  `provides`, `permissions`.
- `migrations` необязателен, как требует бриф и сценарий плагина без данных.
- `entrypoints` требует хотя бы один из `server`/`client`; неизвестные entrypoints отклоняются.
- `requires` — объект Plugin ID → диапазон версии. Неверные ключи и значения отклоняются.
- `consumes`/`provides` проверяются как Contract ID и не содержат дубликатов.
- `permissions` — непустые строки без дубликатов; декларативные permissions не объявляются
  песочницей.

### 4.3. Команды, запросы и экспорт

- `mutation` и `query` разделены отдельными схемами и типами.
- Mutation: `risk = read | write | destructive`, обязательный `idempotency = none | supported`.
- Query: только `risk = read`, без `idempotency`.
- `inputSchema` и `outputSchema` — JSON Schema-объекты; при валидации метаданных они
  дополнительно проверяются meta-schema Draft 2020-12 и на компилируемость с локальными `$ref`.
- `exposure` необязателен; отсутствующее поле или канал означает `false`. Помощник
  `resolveExposure` всегда возвращает все три канала, по умолчанию выключенные.
- HTTP/MCP-адаптеры не реализованы: SDK фиксирует только метаданные и безопасный default off.

### 4.4. Ошибки и результаты

Единый конверт: успех `{ ok: true, data, meta? }`, ошибка
`{ ok: false, error: { code, message, retryable, details? } }`.

Принятая карта `retryable`:

| Код                      | retryable |
| ------------------------ | --------- |
| `VALIDATION_ERROR`       | false     |
| `NOT_FOUND`              | false     |
| `VERSION_CONFLICT`       | false     |
| `IDEMPOTENCY_CONFLICT`   | false     |
| `PERMISSION_DENIED`      | false     |
| `DEPENDENCY_UNAVAILABLE` | true      |
| `PLUGIN_UNAVAILABLE`     | true      |
| `CANCELLED`              | false     |
| `TIMEOUT`                | true      |
| `RATE_LIMITED`           | true      |
| `INTERNAL_ERROR`         | false     |

`details` имеет тип JSON-объекта и по контракту не должен содержать секреты, стек, внутренние
пути и содержимое чужих данных. `createPluginError` подставляет `retryable` по коду; явное
переопределение оставлено для осознанных случаев.

### 4.5. События

- Конверт содержит `eventId`, `type`, `contractVersion = 1`, `source`, `occurredAt` в UTC,
  `resource`, необязательный `resourceVersion`, `payload`.
- Подписка допускает wildcard только последним сегментом: `kanbaner.*`,
  `kanbaner.tasks.*`, `kanbaner.tasks.task.*`, а также точный тип события.
- Wildcard в середине, частичный wildcard и `*` без сегментов отклоняются.
- `matchesEventSubscription` сравнивает по границе сегментов, а не по подстроке.

### 4.6. Ресурсы и связи

- ResourceRef — `<plugin-id>:<resource-type>:<opaque-id>`.
- `opaqueId` не интерпретируется и не связывается с ULID; допускается произвольная непустая
  строка без `:` и пробельных символов.
- `parseResourceRef` и `formatResourceRef` проверяют строковый тип каждой части в рантайме и
  бросают `TypeError` с безопасным сообщением; `isResourceRef` и `validateResourceRef` дают
  проверку без исключения.
- `ResourceService` асинхронный: `link`, `unlink`, `list`, `resolve`, `canOpen`, `open`.
- `resolve` возвращает `OperationResult<ResourceDescriptor>`; удалённый ресурс — `NOT_FOUND`,
  а не `null`.
- Связь не является внешним ключом между данными плагинов; relation namespace-ирован.

### 4.7. Контекст выполнения и UI

- `ExecutionContext<TStorage = unknown>` содержит `requestId`, `traceId`, `source`, `signal`,
  `deadline`, `idempotencyKey`, `logger`, `commands`, `queries`, `resources`, `storage`.
- `storage` не заменён выдуманным Storage Provider-контрактом.
- Логгер — структурный интерфейс, не зависит от Pino.
- `deadline` выбран как `Date`, поскольку контекст внутрипроцессный; логические конверты
  остаются сериализуемыми отдельно.
- UI-вклады — метаданные без React, Tailwind и DOM. Базовые слоты ядра экспортируются
  константой; плагины могут публиковать собственные слоты того же формата.

### 4.8. Валидация

- TypeBox — единственный источник JSON Schema и статических типов для манифеста, операций,
  событий, ресурсов и UI-контрактов.
- Ajv 8.20 подключается через `ajv/dist/2020.js`; все самостоятельные схемы помечены
  `$schema: https://json-schema.org/draft/2020-12/schema`.
- Ajv работает в strict-режиме с `allErrors: true`; `ajv-formats` регистрирует стандартные
  форматы, включая `date-time`, а `host-api-range` связывает Ajv с `semver`.
- Для каждой схемы создаётся отдельный экземпляр Ajv и кэшируется по объекту схемы. Это
  изолирует одинаковые `$id` разных плагинов; тест с двумя схемами `$id = urn:plugin:schema`
  проходит.
- Рекурсивные JSON-схемы создаются фабриками с уникальными `$id`. Для вложенных
  success/error-веток результата используются `createErrorResultSchema` и
  `createPluginErrorSchema`, чтобы не дублировать `$id` одной и той же схемы.
- Boundary-guard `findJsonValueIssue` выполняется до Ajv на каждой публичной границе:
  в `validateWithSchema` и в обоих методах `createSchemaValidator`. Он не зависит от
  маркера схемы и покрывает вложенные metadata-схемы, составные result-схемы и конверты.
- Валидные повторно используемые, но не циклические объекты и схемы принимаются: guard
  отслеживает только текущий путь обхода и снимает объект со stack после ветки.
- Ошибки Ajv преобразуются в `ValidationIssue` с `path`, `schemaPath`, `keyword`, `message`
  и `params`, без раскрытия Ajv-типов в публичном API.

## 8. Невыполненные проверки и остаточные риски

1. **Windows не проверен.** Текущее окружение — Linux. SDK не использует платформенные API,
   но отдельный прогон на Windows не выполнялся.
2. **Runtime, Storage Provider, БД, HTTP и MCP не реализованы** — это не входит в KAN-002.
   `ExecutionContext.storage` намеренно generic/unknown; реальный контракт появится в
   последующих задачах.
3. **`deadline: Date`** — внутрипроцессное решение. Если в будущем контекст начнут
   сериализовать между процессами, понадобится UTC-строка или число и отдельное решение
   контракта.
4. **JSON boundary-guard дополняет Ajv, а не заменяет доменные схемы.** Guard работает на
   каждой публичной границе и намеренно отклоняет `Date`, `Map`, class instances, функции,
   `undefined`, `bigint`, `NaN`/`Infinity` и циклы, даже если Ajv мог бы пропустить часть из
   них. Конкретная структура payload по-прежнему задаётся `inputSchema`/`outputSchema`
   плагина; SDK не дублирует доменные схемы.
5. **Карта `retryable` выбрана в рамках реализации.** Contract v1 требует признак, но не
   задаёт значения для каждого кода. Решение зафиксировано в таблице выше и должно
   использоваться ядром единообразно.
6. **Нет глобального реестра JSON Schema и разрешения внешних `$ref`.** Каждая схема
   компилируется отдельным Ajv-экземпляром; плагинные схемы должны быть самодостаточными
   (локальные `$ref` внутри схемы поддерживаются). Это изолирует одинаковые `$id`, но не
   превращает SDK в resolver внешних schema-реестров.
7. **`semver.validRange` проверяет форму диапазона, а не совместимость с конкретной версией
   Host API.** Фактическое сопоставление диапазонов и версий остаётся задачей ядра.
8. **ESLint 9.39.5 остаётся известным deprecated-исключением**, разрешённым
   `specs/technology-stack.md`; новых исключений KAN-002 не добавляет.
9. **`hostApi` с build-метаданными нормализуется semver.** `1.0.0+build.7` принимается как
   валидный диапазон, но `validRange` возвращает нормализованную форму без build-части; это
   ожидаемое поведение semver и не влияет на проверку формы.
