## 1. Итог

Реализован самостоятельный публичный Plugin Contract v1 в `@kanbaner/plugin-sdk` без runtime,
базы данных, HTTP/MCP-адаптера и React-зависимости. SDK собирается как ESM с declarations,
импортируется после build и содержит TypeBox-схемы, TypeScript-типы, Ajv Draft 2020-12
валидаторы и единые конверты результата/ошибки.

Пакет не импортирует `@kanbaner/kernel`, `apps/**`, React, React DOM или Tailwind. Публичные
типы не содержат `any`. `storage` в контексте выполнения оставлен generic/unknown; Storage
Provider не выдумывался.

Фактический объём проверок:

- focused package tests: 5 test files, 55 tests passed;
- полный `pnpm test` / `pnpm check`: 9 test files, 59 tests passed;
- `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` — успешно;
- runtime import собранного `dist/index.js` — успешно.

## 3. Принятые решения

### 3.1. Идентификаторы и версии

- Plugin ID — ровно два сегмента `<namespace>.<plugin>` в нижнем регистре; сегменты
  `[a-z][a-z0-9-]*`.
- Operation ID — Plugin ID плюс один или несколько action-сегментов.
- Event type — ровно четыре сегмента: Plugin ID, resource type, past-tense action.
- Contract ID — Plugin ID, имя контракта и `.v<major>`.
- Relation — минимум два namespace-сегмента; пример `kanbaner.notes.references`.
- Версия плагина проверяется как строгий SemVer 2.0.0 с обязательными
  `major.minor.patch`, корректными prerelease/build и запретом ведущих нулей.
- `hostApi` проверяется как непустой разумно валидный SemVer-диапазон: точная версия, `^`,
  `~`, comparators, `*`, `x`, объединения через `||` или пробел. Полный semver-engine не
  реализован, потому что контракт этого не требует; фактическую совместимость проверяет ядро.

### 3.2. Манифест

- Обязательные поля: `id`, `name`, `version`, `hostApi`, `entrypoints`, `requires`, `consumes`,
  `provides`, `permissions`.
- `migrations` необязателен, как требует бриф и сценарий плагина без данных.
- `entrypoints` требует хотя бы один из `server`/`client`; неизвестные entrypoints отклоняются.
- `requires` — объект Plugin ID → диапазон версии. Неверные ключи и значения отклоняются.
- `consumes`/`provides` проверяются как Contract ID и не содержат дубликатов.
- `permissions` — непустые строки без дубликатов; декларативные permissions не объявляются
  песочницей.

### 3.3. Команды, запросы и экспорт

- `mutation` и `query` разделены отдельными схемами и типами.
- Mutation: `risk = read | write | destructive`, обязательный `idempotency = none | supported`.
- Query: только `risk = read`, без `idempotency`.
- `inputSchema` и `outputSchema` — JSON Schema-объекты, описываемые TypeBox.
- `exposure` необязателен; отсутствующее поле или канал означает `false`. Помощник
  `resolveExposure` всегда возвращает все три канала, по умолчанию выключенные.
- HTTP/MCP-адаптеры не реализованы: SDK фиксирует только метаданные и безопасный default off.

### 3.4. Ошибки и результаты

Единый конверт: успех `{ ok: true, data, meta? }`, ошибка
`{ ok: false, error: { code, message, retryable, details? } }`.

Принятая карта `retryable`:

| Код                      | retryable |
| ------------------------ | --------- |
| `VALIDATION_ERROR`       | false     |
| `NOT_FOUND`              | false     |
| `VERSION_CONFLICT`       | false     |
| `IDEMPOTENCY_CONFLICT`   | false     |
| `PERMISSION_DENIED`      | false     |
| `DEPENDENCY_UNAVAILABLE` | true      |
| `PLUGIN_UNAVAILABLE`     | true      |
| `CANCELLED`              | false     |
| `TIMEOUT`                | true      |
| `RATE_LIMITED`           | true      |
| `INTERNAL_ERROR`         | false     |

`details` имеет тип JSON-объекта и по контракту не должен содержать секреты, стек, внутренние
пути и содержимое чужих данных. `createPluginError` подставляет `retryable` по коду; явное
переопределение оставлено для осознанных случаев.

### 3.5. События

- Конверт содержит `eventId`, `type`, `contractVersion = 1`, `source`, `occurredAt` в UTC,
  `resource`, необязательный `resourceVersion`, `payload`.
- Подписка допускает wildcard только последним сегментом: `kanbaner.*`,
  `kanbaner.tasks.*`, `kanbaner.tasks.task.*`, а также точный тип события.
- Wildcard в середине, частичный wildcard и `*` без сегментов отклоняются.
- `matchesEventSubscription` сравнивает по границе сегментов, а не по подстроке.

### 3.6. Ресурсы и связи

- ResourceRef — `<plugin-id>:<resource-type>:<opaque-id>`.
- `opaqueId` не интерпретируется и не связывается с ULID; допускается произвольная непустая
  строка без `:` и пробельных символов.
- `parseResourceRef` бросает `TypeError` с безопасным сообщением; `isResourceRef` и
  `validateResourceRef` дают проверку без исключения.
- `ResourceService` асинхронный: `link`, `unlink`, `list`, `resolve`, `canOpen`, `open`.
- Связь не является внешним ключом между данными плагинов; relation namespace-ирован.

### 3.7. Контекст выполнения и UI

- `ExecutionContext<TStorage = unknown>` содержит `requestId`, `traceId`, `source`, `signal`,
  `deadline`, `idempotencyKey`, `logger`, `commands`, `queries`, `resources`, `storage`.
- `storage` не заменён выдуманным Storage Provider-контрактом.
- Логгер — структурный интерфейс, не зависит от Pino.
- `deadline` выбран как `Date`, поскольку контекст внутрипроцессный; логические конверты
  остаются сериализуемыми отдельно.
- UI-вклады — метаданные без React, Tailwind и DOM. Базовые слоты ядра экспортируются
  константой; плагины могут публиковать собственные слоты того же формата.

### 3.8. Валидация

- TypeBox — единственный источник JSON Schema и статических типов для манифеста, операций,
  событий, ресурсов и UI-контрактов.
- Ajv 8.20 подключается через `ajv/dist/2020.js`; все самостоятельные схемы помечены
  `$schema: https://json-schema.org/draft/2020-12/schema`.
- Ajv работает в strict-режиме с `allErrors: true`.
- Для каждой схемы создаётся отдельный экземпляр Ajv и кэшируется по объекту схемы. Это
  изолирует одинаковые `$id` разных плагинов; тест с двумя схемами `$id = urn:plugin:schema`
  проходит.
- Ошибки Ajv преобразуются в `ValidationIssue` с `path`, `schemaPath`, `keyword`, `message`
  и `params`, без раскрытия Ajv-типов в публичном API.

## 7. Невыполненные проверки и остаточные риски

1. **Windows не проверен.** Текущее окружение — Linux. SDK не использует платформенные API,
   но отдельный прогон на Windows не выполнялся.
2. **Runtime, Storage Provider, БД, HTTP и MCP не реализованы** — это не входит в KAN-002.
   `ExecutionContext.storage` намеренно generic/unknown; реальный контракт появится в
   последующих задачах.
3. **`deadline: Date`** — внутрипроцессное решение. Если в будущем контекст начнут
   сериализовать между процессами, понадобится UTC-строка или число и отдельное решение
   контракта.
4. **`JsonValueSchema`/`JsonObjectSchema` проверяют верхний уровень JSON-совместимости.**
   Глубокая проверка payload и details делегирована конкретным `inputSchema`/`outputSchema`
   плагинов. Это осознанно, чтобы не дублировать доменные схемы в SDK.
5. **Карта `retryable` выбрана в рамках реализации.** Contract v1 требует признак, но не
   задаёт значения для каждого кода. Решение зафиксировано в таблице выше и должно
   использоваться ядром единообразно.
6. **Нет глобального реестра JSON Schema и разрешения внешних `$ref`.** Каждая схема
   компилируется отдельным Ajv-экземпляром; плагинные схемы должны быть самодостаточными.
   Это изолирует одинаковые `$id`, но не превращает SDK в resolver внешних schema-реестров.
7. **Полный semver-range engine не реализован.** `hostApi` проверяется на разумную форму;
   фактическое сопоставление диапазонов и версий остаётся задачей ядра.
8. **ESLint 9.39.5 остаётся известным deprecated-исключением**, разрешённым
   `specs/technology-stack.md`; новых исключений KAN-002 не добавляет.
