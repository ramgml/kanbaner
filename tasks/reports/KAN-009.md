## 1. Итог

Реализован первый реальный Storage Provider на SQLite WAL в
`packages/storage-sqlite`. Пакет зависит от `@kanbaner/plugin-sdk`, не зависит от
`@kanbaner/kernel` и не протекает в доменный код: синхронный `better-sqlite3`
полностью скрыт внутри асинхронного публичного API.

Провайдер реализует `StorageProvider`, транзакции и savepoints, Store-контракты
`PluginDocumentStore`, `LinkStore`, `PluginStateStore`, `MigrationStore`,
`SearchIndexStore` на FTS5, online backup через `.backup()` и offline restore в новый
каталог. Composition root `apps/web` регистрирует и открывает провайдер до старта
плагинов и до их миграций.

## 2. Архитектура пакета

Файлы `packages/storage-sqlite/src`:

- `provider.ts` — `SqliteStorageProvider`, транзакции, savepoints, bounded retry,
  online backup, внутренняя транзакция с DDL-методом для инфраструктурной миграции.
- `stores.ts` — реализация всех Store-контрактов, SQL и работа с FTS5.
- `schema.ts` — идемпотентная baseline-схема, `kanbaner.core`, версия
  `core-foundation` v1.
- `validation.ts` — валидация входов на границе Store.
- `normalizer.ts` — NFKC/нижний регистр, токенизация Unicode, безопасный FTS-запрос,
  excerpt. Русский стемминг сознательно не обещается.
- `paths.ts` — `KANBANER_DATA_DIR`, каталоги ОС по умолчанию, Windows-пути,
  запрет URI/UNC/сетевых путей.
- `namespaces.ts` — namespace-префиксы таблиц только из валидированного Plugin ID.
- `backup.ts` — online backup/restore, integrity check, очистка sidecar-файлов.
- `singleton.ts` — singleton провайдера для hot reload Next.js.
- `errors.ts` — стабильные `StorageError` без SQL, путей и кодов драйвера.
- `async-mutex.ts` — FIFO-мьютекс соединения.
- `scope.ts` — состояние транзакционной области: `active`, `rolledBack`, `pending`.
- `infrastructure-migrations.ts` — инфраструктурная миграция core-таблиц.

### Транзакции и sealing

`withTransaction` вручную выполняет `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK` и
удерживает FIFO-мьютекс до завершения async callback. Операции других вызовов ждут
и не выполняются внутри чужой транзакции. Rejected Promise приводит к rollback.

После завершения callback область «запечатывается»: новые операции отклоняются как
`TRANSACTION_CLOSED`, а начатые до запечатывания дожидаются через `pending` и
откатываются вместе с транзакцией. Вложенные savepoints используют
`SAVEPOINT` / `ROLLBACK TO` / `RELEASE`; при фактическом rollback предка собственный
snapshot не восстанавливается повторно. Это поведение проверяет общий Conformance
Suite, включая сценарии с задержками.

`SQLITE_BUSY` повторяется ограниченно и только для безопасных операций: чтения,
начала записи и `BEGIN IMMEDIATE`. Исчерпание лимита даёт retryable
`INTERNAL_ERROR` с безопасными `details` (`reason`, `attempts`), без бесконечного retry.

### WAL, схема и миграции

`open()` создаёт каталог данных и идемпотентную baseline-схему, затем устанавливает:

- `journal_mode = WAL`;
- `foreign_keys = ON`;
- `busy_timeout = 5000` по умолчанию;
- `synchronous = NORMAL`.

`close()` делает `wal_checkpoint(TRUNCATE)` (best-effort) и закрывает соединение.
Публичные ID создаются приложением/плагином до записи; rowid не используется как ID.
Время хранится строкой UTC без сдвига часового пояса.

Инфраструктурная миграция `kanbaner.core` v1 (`core-foundation`) применяется
composition root-ом **первой**, в общей транзакции с записью журнала и checksum.
Повторный запуск пропускает её по checksum; изменение содержимого уже применённой
миграции блокируется `MIGRATION_CHECKSUM_MISMATCH`.

### Store-контракты и поиск

- `PluginDocumentStore`: CAS через `expectedVersion`, `VERSION_CONFLICT`, фильтры по
  `indexedFields`, `ids`, сортировка и пагинация; JSON клонируется на границе.
- `LinkStore`: атомарная идемпотентная вставка тройки, поиск с обеих сторон,
  удаление по ref.
- `PluginStateStore`: upsert версии/enabled/state, явное удаление; удаление состояния
  не удаляет документы.
- `MigrationStore`: журнал `(backendId, pluginId, version)`, идемпотентная запись с тем
  же checksum.
- `SearchIndexStore`: FTS5 `unicode61`, нормализация NFKC + нижний регистр, фразы,
  prefix-запросы, фильтры `pluginId`/`kind`, `reindex`, `clear`, `deleteMany`.

### Backup и restore

- Online backup вызывается на активном соединении через `.backup()`; мьютекс
  удерживается только на проверку и старт копирования, поэтому записи приложения
  могут продолжаться. `close()` ждёт активные backup-и.
- После копирования backup checkpoint-ится, проверяется отдельным read-only
  соединением через `integrity_check` и очищается от пустых WAL/SHM sidecar-файлов.
- Offline restore открывает **только файл backup-а** и пишет через `.backup()` в новый
  каталог. Отклоняются: существующая база/`-wal`/`-shm`/`-journal` в цели, sidecar у
  backup-а, отсутствующий/повреждённый файл, совпадение backup и цели.
- CLI: `scripts/restore.mjs`, запуск `pnpm storage:restore --backup <file> --data-dir <new-dir>`.

### Bootstrap в приложении

`apps/web/src/server/application-storage.ts` — composition root:

1. регистрация провайдера;
2. открытие и health check;
3. инфраструктурные миграции;
4. миграции остальных плагинов.

При ошибке открытия или миграции провайдер закрывается, частично применённого набора
не остаётся. Singleton ключуется по разрешённому пути базы и сбрасывается после
ошибки; shutdown hooks закрывают runtime.

`plugin-service.ts` получил необязательный `bootstrap` hook. Он вызывается до старта
runtime плагинов ровно один раз; при ошибке флаг не выставляется, и следующий запрос
повторяет bootstrap, не запуская runtime на неготовом хранилище. Поведение KAN-007
(lifecycle, деактивация, safe mode) сохранено.

## 3. Найденные и исправленные ошибки

1. **Проверка путей после `path.resolve`.** `https://…`, `file://…` и `//server/share`
   нормализовались в локальный абсолютный путь и проходили проверку. Теперь исходная
   строка проверяется до `resolve` в `resolveDataDirectory` и `resolveDatabasePath`.
2. **Sidecar-файлы backup-а.** Read-only `integrity_check` открывает WAL-базу и создаёт
   пустые `-wal`/`-shm`. Из-за этого свежий online backup отклонялся offline restore
   как «содержащий sidecar live-базы», а backup при конкурентных записях мог оставить
   непустой WAL. Добавлены `checkpointBackupDatabase()` и `removeBackupSidecars()`:
   backup/restore завершают файл checkpoint-ом, проверяют целостность и удаляют только
   пустые sidecar-файлы. Непустой WAL не удаляется.

## 6. Остаточные риски

- `better-sqlite3` — нативный модуль; на Windows нужны prebuilt binary или toolchain.
  Проверка на Windows остаётся за релизным этапом.
- `synchronous = NORMAL` допускает потерю последних коммитов при аварийном отключении
  питания; это осознанный компромисс WAL.
- Предупреждения Turbopack о динамическом `fs`-доступе могут увеличить трассировку
  server bundle; на функциональность не влияет.
- FTS5 без морфологии: поиск по словоформам не гарантируется, стемминг не обещан.
- Offline restore CLI требует собранного `packages/storage-sqlite/dist`.
- Порт `next start` задан в `apps/web` и не переопределяется текущим smoke-скриптом.
- Restore не переносит данные между backend-ами; export/import вне MVP.
