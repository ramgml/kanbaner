## 1. Итог

Реализован первый реальный Storage Provider на SQLite WAL в
`packages/storage-sqlite`. Пакет зависит от `@kanbaner/plugin-sdk`, не зависит от
`@kanbaner/kernel` и не протекает в доменный код: синхронный `better-sqlite3`
полностью скрыт внутри асинхронного публичного API.

Провайдер реализует `StorageProvider`, транзакции и savepoints, Store-контракты
`PluginDocumentStore`, `LinkStore`, `PluginStateStore`, `MigrationStore`,
`SearchIndexStore` на FTS5, online backup через `.backup()` и offline restore в новый
каталог. Composition root `apps/web` регистрирует и открывает провайдер до старта
плагинов и до их миграций.

### Транзакции и sealing

`withTransaction` вручную выполняет `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK` и
удерживает FIFO-мьютекс до завершения async callback. Операции других вызовов ждут
и не выполняются внутри чужой транзакции. Rejected Promise приводит к rollback.

После завершения callback область «запечатывается»: новые операции отклоняются как
`TRANSACTION_CLOSED`, а начатые до запечатывания дожидаются через `pending` и
откатываются вместе с транзакцией. Вложенные savepoints используют
`SAVEPOINT` / `ROLLBACK TO` / `RELEASE`; при фактическом rollback предка собственный
snapshot не восстанавливается повторно. Это поведение проверяет общий Conformance
Suite, включая сценарии с задержками.

`AsyncLocalStorage` различает исполняемый callback операции и параллельный вызов из
callback-а транзакции с тем же scope. Обычная Store-операция выполняется немедленно
только из собственного execution scope. Savepoint push становится владельцем
SQL-стека: parent/sibling операции ждут `RELEASE`/`ROLLBACK`, затем
восстанавливается предыдущий владелец. Вложенный savepoint получает собственный
вложенный планировщик, поэтому sibling savepoints сериализуются, а inner rollback
не откатывает write parent scope.

`SQLITE_BUSY` повторяется ограниченно и только для безопасных операций: чтения,
начала записи и `BEGIN IMMEDIATE`. Исчерпание лимита даёт retryable
`INTERNAL_ERROR` с безопасными `details` (`reason`, `attempts`), без бесконечного retry.

### WAL, схема и миграции

`open()` создаёт каталог данных, устанавливает PRAGMA и в одной транзакции
`BEGIN IMMEDIATE` создаёт **только минимальную стабильную таблицу журнала**
`core_plugin_migrations` с индексом. Вся версионируемая схема (`core_documents`,
`core_plugins`, `core_resource_links`, `core_search_documents`) создаётся только в
`createCoreInfrastructureMigrations().up` в общей транзакции с записью журнала и
checksum. DDL не выполняется до проверки checksum.

PRAGMA: `journal_mode = WAL`, `foreign_keys = ON`, `busy_timeout = 5000` по умолчанию,
`synchronous = NORMAL`.

`close()` проверяет результат `wal_checkpoint(TRUNCATE)`: `busy != 0` — ошибка, а не
best-effort. Затем закрывает соединение. Публичные ID создаются
приложением/плагином до записи; rowid не используется как ID. Время хранится строкой
UTC без сдвига часового пояса.

Инфраструктурная миграция `kanbaner.core` v1 (`core-foundation`) применяется
composition root-ом **первой**, в общей транзакции с записью журнала и checksum.
Повторный запуск пропускает её по checksum; изменение содержимого уже применённой
миграции блокируется `MIGRATION_CHECKSUM_MISMATCH` без изменения БД.

### Store-контракты и поиск

- `PluginDocumentStore`: CAS через `expectedVersion`, `VERSION_CONFLICT`, фильтры по
  `indexedFields`, `ids`, сортировка и пагинация; JSON клонируется на границе.
- `LinkStore`: атомарная идемпотентная вставка тройки, поиск с обеих сторон,
  удаление по ref.
- `PluginStateStore`: upsert версии/enabled/state, явное удаление; удаление состояния
  не удаляет документы.
- `MigrationStore`: журнал `(backendId, pluginId, version)`, идемпотентная запись с тем
  же checksum.
- `SearchIndexStore`: FTS5 `unicode61`, нормализация NFKC + нижний регистр, фразы,
  prefix-запросы, фильтры `pluginId`/`kind`, `reindex`, `clear`, `deleteMany`.

### Backup и restore

- Online backup вызывается на активном соединении через `.backup()`; мьютекс
  удерживается только на проверку и старт копирования, поэтому записи приложения
  могут продолжаться. `close()` ждёт активные backup-и.
- Копия пишется в уникальный temp в каталоге назначения. После checkpoint
  (`wal_checkpoint(TRUNCATE)` с проверкой `busy`) и чистого read-only
  `integrity_check` файл публикуется атомарно через hardlink, с fallback
  `copyFile(COPYFILE_EXCL)`. Существующий destination и любые его sidecar-файлы
  **никогда не удаляются и не перезаписываются**: путь проверяется до старта и
  повторно перед публикацией. При ошибке удаляются только собственные temp-файлы.
- Offline restore открывает **только файл backup-а** и пишет через `.backup()` в
  несуществующий или полностью пустой каталог. Каталог с посторонним файлом
  отклоняется **до открытия backup-а** и остаётся нетронутым. Отклоняются также
  существующая база/`-wal`/`-shm`/`-journal` в цели, sidecar у backup-а,
  отсутствующий/повреждённый файл, совпадение backup и цели.
- CLI: `scripts/restore.mjs`, запуск `pnpm storage:restore --backup <file> --data-dir <new-dir>`.
  Модуль загружается через `pathToFileURL(modulePath).href`, поэтому пути с пробелами
  и non-ASCII работают и на POSIX, и на Windows.

### Bootstrap в приложении

`apps/web/src/server/application-storage.ts` — composition root:

1. регистрация провайдера;
2. открытие и health check;
3. инфраструктурные миграции;
4. миграции остальных плагинов.

При ошибке открытия или миграции провайдер закрывается, частично применённого набора
не остаётся. Singleton ключуется по разрешённому пути базы. `closingPromise`
сериализует `get()` и `close()`: `get()` во время close ждёт завершения и только
потом создаёт новый runtime, поэтому второго соединения с тем же каталогом не
возникает. Запись singleton-а удаляется только после попытки close. Shutdown
возвращает await-able Promise, дожидается активных операций и checkpoint-а; новые
runtime-ы после shutdown отклоняются.

Production lifecycle реализован в `apps/web/scripts/server.mjs` (custom server по
документации локального Next 16). На `SIGTERM`/`SIGINT` сервер сначала прекращает
приём запросов, закрывает idle-соединения и дожидается активных запросов, затем
вызывает `globalThis.__kanbanerStorageShutdown` — await-able bridge к
`shutdownApplicationStorage()`/checkpoint, и только после этого завершает процесс.
Приложение больше не полагается на сохранённый Promise и не оставляет независимый
`next start` signal-handler.

`plugin-service.ts` получил `bootstrap` и реальный `migrate` hook. `bootstrap`
вызывается до старта runtime плагинов ровно один раз; при ошибке флаг не
выставляется, и следующий запрос повторяет bootstrap, не запуская runtime на
неготовом хранилище. `migrate` применяет backend-specific SQLite-миграции через
активный provider. Плагин с объявленным `migrations`, но без настроенного hook-а или
доступного canonical-каталога, переводится в `failed` с диагностикой
`migration_failed` и не активируется молча. Поведение KAN-007 (lifecycle,
деактивация, safe mode) сохранено.

## 3. Исправления по ревью безопасности

1. **BLOCKER: backup не удаляет чужой destination.** Backup пишется в уникальный temp
   в каталоге назначения, checkpoint-ится, проверяется read-only и публикуется без
   overwrite (hardlink / `COPYFILE_EXCL`). Существующий destination и sidecars только
   отклоняются; при success/error чужие файлы сохраняются байт-в-байт, temp
   удаляется только собственный. `verifyDatabaseIntegrity` больше не мутирует
   файловую систему; собственный backup переводится в `journal_mode = DELETE`.
2. **HIGH: `open()` не применяет версионируемый DDL.** Создаётся только
   `core_plugin_migrations` + индекс в `BEGIN IMMEDIATE`; полная схема применяется
   исключительно в `migration.up` в общей транзакции с журналом и checksum. Тесты
   подтверждают отсутствие core-таблиц до миграции и DDL-midway rollback.
3. **HIGH: savepoint LIFO.** Новый `TransactionScheduler` сериализует sibling
   savepoints: child-область эксклюзивна относительно parent/sibling операций,
   вложенный savepoint реентерабелен. Parent write ждёт rollback child; sibling не
   завершается раньше более раннего deferred savepoint.
4. **HIGH: checkpoint.** `checkpointBackupDatabase` и `provider.close()` проверяют
   строку `wal_checkpoint(TRUNCATE)`: `busy != 0` — retryable `INTERNAL_ERROR`.
   Backup не публикуется с непустым WAL. Regression-тест удерживает reader и
   подтверждает busy.
5. **HIGH: shutdown.** `closingPromise` сериализует `get()`/`close()`, singleton
   удаляется только после close, `shutdownApplicationStorage()` await-able и
   дожидается активной операции/checkpoint-а, новые runtime-ы после shutdown
   отклоняются. Тесты покрывают deferred shutdown, `close(); get()` без ожидания и
   отсутствие второго соединения.
6. **MEDIUM: production plugin migrations.** `hooks.migrate` связан с активным
   provider/runner; добавлен детерминированный `.sql` loader
   (`<NNN>_<name>.sql`, сортировка, reject дублей/symlink/пустых файлов) и
   `executeSqliteMigrationSql` в транзакции runner-а. Плагин с `migrations` без
   hook-а/каталога активируется как `failed` (`migration_failed`), а не молча.
   Статический список миграций для тестов сохранён.
7. **MEDIUM: path validation.** `backupTo` и `restoreDatabase` проверяют исходные
   строки `destination`/`backupPath`/`dataDirectory` до `path.resolve`, поэтому
   URI/UNC/сетевые пути отклоняются, а не нормализуются в локальные.
8. **MEDIUM: restore только в новый/пустой каталог.** Посторонний файл
   отклоняется до открытия backup-а и сохраняется; созданный этой операцией пустой
   каталог удаляется при ошибке; после успеха не остаётся temp/sidecar-файлов.
9. **LOW: CLI import.** `scripts/restore.mjs` использует
   `pathToFileURL(modulePath).href`; smoke выполнен в каталогах с пробелами и
   non-ASCII.

### Повторное ревью

10. **HIGH: stack-aware scheduler.** Старый `isDescendantScope` позволял обычным
    Store-операциям и sibling savepoint пересекаться. `TransactionScheduler`
    переписан на `AsyncLocalStorage`: операция немедленна только из своего
    execution scope; savepoint push меняет владельца и восстанавливает предыдущего
    после RELEASE/ROLLBACK. Добавлены тесты depth >= 2: parent write, начатый
    первым, блокирует child; sibling savepoints внутри вложенного savepoint
    сериализуются; rollback inner не откатывает write parent scope. Deadlock при
    `await` child-операций отсутствует.
11. **HIGH: transaction-control в SQL миграциях.** `sql-scanner.ts` до первого
    statement отклоняет реальные `BEGIN`/`COMMIT`/`END`/`ROLLBACK`/`SAVEPOINT`/
    `RELEASE`, понимая `--`/`/* */` комментарии, строки, quoted/bracket
    identifiers, границы statements и trigger body. `COMMIT`/`ROLLBACK` в
    строке/комментарии допустимы. Дополнительно `withTransaction` проверяет
    `database.inTransaction` после callback/up, но не полагается только на неё.
    Тесты COMMIT/ROLLBACK подтверждают отсутствие таблиц и journal; quoted/comment
    cases проходят без false positive.
12. **MEDIUM: production shutdown.** Сохранённый в `globalThis` Promise больше не
    используется как расчёт на Next. Добавлен custom production server
    (`apps/web/scripts/server.mjs`) на `next` + `node:http`; `start` script
    переключён на него. SIGTERM/SIGINT: drain запросов → await storage shutdown и
    checkpoint → exit. Добавлен production test, который посылает SIGTERM во время
    deferred write и проверяет ожидание, exit code 0, сохранённую запись,
    `integrity_check = ok` и отсутствие WAL/SHM.

## 5. Windows

Windows-окружение в этой сессии недоступно. Честно зафиксировано:

- логика путей покрыта unit-тестами с `path.win32`: `%APPDATA%`, `C:\…`, пробелы,
  non-ASCII, case-insensitive сравнение;
- `pathToFileURL(modulePath).href` в CLI корректен для Windows-drive путей, но
  фактический CLI smoke на Windows **не выполнялся**;
- custom server `apps/web/scripts/server.mjs`, SIGTERM/SIGINT drain и production
  SIGTERM test на Windows **не проверялись**;
- фактическая установка/загрузка нативного `better-sqlite3` на Windows **не
  проверялась**;
- production smoke и graceful shutdown выполнены только на Linux.

## 6. Остаточные риски

- `better-sqlite3` — нативный модуль; на Windows нужны prebuilt binary или toolchain.
  Проверка на Windows остаётся за релизным этапом.
- `synchronous = NORMAL` допускает потерю последних коммитов при аварийном отключении
  питания; это осознанный компромисс WAL.
- Предупреждения Turbopack о динамическом `fs`-доступе могут увеличить трассировку
  server bundle; на функциональность не влияет.
- FTS5 без морфологии: поиск по словоформам не гарантируется, стемминг не обещан.
- Offline restore CLI требует собранного `packages/storage-sqlite/dist`.
- Offline restore по контракту принимает только несуществующий или полностью пустой
  каталог; восстановление поверх существующей базы намеренно недоступно.
- Публикация backup-а использует hardlink; на файловых системах без hardlink
  выполняется fallback `copyFile(COPYFILE_EXCL)`, это проверено кодом, но не каждым
  типом ФС.
- Busy-checkpoint regression-тест ждёт встроенный `busy_timeout` (до ~5 с); это
  замедляет только тест, не runtime.
- Production SIGTERM test требует собранного `.next` и запускается отдельно через
  `node --test`, а не внутри `pnpm check`.
- Test hook seam (`KANBANER_ENABLE_TEST_HOOKS` + `KANBANER_SERVER_TEST_HOOK`)
  активен только при явно заданных env; в production smoke и обычном запуске hook
  не загружается.
- SQL scanner покрывает стандартные SQLite statements, комментарии, строки,
  quoted identifiers и trigger body; экзотические vendor-расширения не проверялись.
- Custom server использует публичный `next({...})` API; при будущем мажорном
  обновлении Next контракт `prepare()`/`getRequestHandler()` нужно перепроверить по
  локальной документации.
- Restore не переносит данные между backend-ами; export/import вне MVP.
