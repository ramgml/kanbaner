## 1. Итог

Реализован адаптивный App Router shell и plugin manager без доменной логики и без
Storage Provider. Shell работает от 360 px: на desktop показывает sidebar, на мобильном —
нижнюю навигацию. Слоты `app.sidebar`, `app.main`, `app.details`, `app.settings` и
`app.overlays` рендерятся из клиентского реестра UI-вкладов. Каждый вклад изолирован
React ErrorBoundary, поэтому ошибка одного плагина не роняет shell.

Plugin manager получает состояние только через публичный runtime KAN-003. Включение и
отключение выполняются lifecycle-путём: `stop()` текущего runtime → новый runtime с
обновлённым `disabledPlugins` → `start()`. Прямая мутация состояния runtime и обход
lifecycle не используются. Если `stop()` выявил новые ошибки деактивации, новый runtime
не создаётся: клиент получает безопасную ошибку и stopped snapshot с диагностикой.

## 2. Исправленные замечания ревью

### 1. BLOCKER: корректная обработка ошибок деактивации

- `stop()` больше не считается успешным автоматически: stopped snapshot сохраняется в
  `this.snapshot`.
- Новые ошибки фазы `deactivation` (`deactivation_failed`, `hook_failed`) обнаруживаются
  сравнением счётчиков диагностик до и после остановки.
- При новой ошибке новый runtime не создаётся, `PluginServiceError("DEACTIVATION_FAILED")`
  несёт безопасный stopped snapshot, а ID проблемных плагинов попадают в
  `blockedPluginIds`.
- До явного retry (`refresh()`) `getState()` возвращает stopped snapshot и не
  перезапускает runtime; `setPluginEnabled()` повторно отклоняется с тем же snapshot.
- `refresh()` использует ту же проверку: при ошибке деактивации возвращает stopped
  snapshot, при следующем явном retry снимает блокировку и запускает runtime заново.
- Integration-тесты покрывают throwing `deactivate()`, throwing `beforeDeactivate`,
  сохранение `deactivation_failed`, stopped snapshot, запрет реактивации и успешный retry.

### 2. HIGH: batch-регистрация UI-вкладов

- `UiContributionRegistry.registerBatch()` сначала валидирует весь набор, включая
  внутренние дубликаты ID и маршрутов, и только потом пишет state.
- State обновляется один раз, подписчики получают только полный snapshot.
- Ошибка listener-а изолирована: она не откатывает регистрацию, не мешает другим
  listener-ам и не создаёт частичных записей.
- `registerUiPlugin()` переведён на `registerBatch()`.
- Тесты покрывают throwing listener, единственное уведомление, полный snapshot и откат
  batch при внутренних дубликатах.

### 3. MEDIUM: allowlist доступности плагинов

- Provider считает вклад доступным только если `pluginId` входит в `activePluginIds`.
- Unknown, removed и пустой allowlist скрывают вклад.
- Test-only режим без `availability` сохранён: он разрешает все вклады для компонентных
  тестов, но layout приложения всегда передаёт allowlist.
- Тесты покрывают unknown ID, пустой allowlist и явный активный allowlist.

### 4. MEDIUM: только маршруты `/view/`

- `normalizeUiViewRoute()` нормализует путь (query/hash/хвостовой `/`) и требует
  `^/view/<name>...$`.
- Отклоняются `/`, `/plugins`, `/settings`, `/kanban`, `/view`, `/view//...`,
  `/view/../...` и другие core routes.
- Дубликаты нормализованных маршрутов отклоняются.
- Активный пункт навигации по-прежнему определяется через `aria-current="page"`.
- Добавлены тесты на core routes, `/kanban`, невалидные сегменты и dedupe.

### 5. MEDIUM: ключ карточки плагина

- React key карточки — `${id}:${source}`.
- Дубликаты Plugin ID из разных источников рендерятся обеими карточками после refresh.
- Добавлен тест на две карточки с одинаковым ID и разными source.

### 6. MEDIUM: устойчивость Server Actions и контролов

- При ошибке server action может вернуть безопасный `state`; клиент применяет его даже
  при `ok: false`.
- `toggle()` и `refresh()` ловят rejected Promise, показывают стабильное
  `INTERNAL_ERROR`-сообщение и сбрасывают pending в `finally`.
- Тесты используют `mockRejectedValue` для toggle и refresh и проверяют снятие disabled.

### 7. MEDIUM: реальный Playwright на 360 px

- Добавлен `@playwright/test@1.65.0` (exact, stable) в `apps/web`.
- Добавлены `playwright.config.ts`, `e2e/shell.spec.ts` и fixture-плагин
  `e2e/fixtures/plugins/e2e-switch`.
- Chromium установлен; тесты идут в реальном браузере, а не в jsdom.
- Проверяются: видимость mobile navigation и скрытие desktop sidebar, отсутствие
  горизонтального overflow, Tab + Enter для перехода по ссылке, Space для Radix Switch.
- Все 3 e2e-теста проходят.

### 8. LOW: main и details — соседи горизонтального flex

- `main` и `details` находятся в одном горизонтальном flex-контейнере.
- `flex-col` остаётся только у `main`.
- Добавлен тест структуры DOM.

### 9. LOW: корректное ожидание unhandledRejection

- Тест ждёт macrotask через `setImmediate` перед снятием listener-а
  `unhandledRejection`.

### 10. LOW: санитизация исходящих данных

- Детали диагностики проходят whitelist ключей; неизвестные ключи отбрасываются.
- Сообщения диагностик и проблем стабильны и определяются по коду, а не по произвольному
  тексту runtime.
- Все исходящие строки санитизируются: POSIX, Windows, UNC и встроенные пути заменяются
  на `[redacted]`.
- Покрыты `apiToken`, `accessToken`, `filePath`, `stackTrace`, вложенные `issues[].path`
  и пути внутри текста.

## 6. Остаточные риски

1. **Набор отключённых плагинов не персистится.** До Storage Provider он живёт в памяти
   процесса и после перезапуска сбрасывается к `KANBANER_DISABLED_PLUGINS`.
2. **Изменение набора требует lifecycle restart.** Это ограничение KAN-003. Реализовано
   через `stop()` + новый `start()`; при ошибке деактивации runtime остаётся остановленным
   до явного retry.
3. **ESM-кэш.** Повторный `start()` использует кэш динамического импорта Node;
   module-level состояние плагина не пересоздаётся. Это известный риск KAN-003.
4. **`/view/test-ui` без fixture.** В production fixture не регистрируется, поэтому
   маршрут показывает пустое состояние. Реальный зарегистрированный плагин проверяется
   Playwright fixture-сценарием.
5. **Turbopack предупреждает о динамическом `fs.stat` в kernel.** Это код KAN-003,
   не изменявшийся в KAN-007; предупреждение не ломает build.
6. **Windows не проверен.** Текущее окружение Linux; пути строятся через `node:path`, но
   отдельный прогон на Windows не выполнялся.
7. **Слот `app.details` показывается только на `xl`.** На мобильном детали скрыты, чтобы
   не отнимать ширину у основного представления.
8. **Playwright использует exact stable 1.65.0 с supply-chain исключением.** Исключение
   ограничено тремя пакетами Playwright и не ослабляет другие правила.
9. **E2E требует предварительного production build.** `playwright.config.ts` запускает
   `next start`, поэтому перед `test:e2e` нужен `pnpm build` (в проверках он выполнялся
   через `pnpm check`).
