## 1. Итог

Реализован адаптивный App Router shell и plugin manager без доменной логики и без
Storage Provider. Shell работает от 360 px: на desktop показывает sidebar, на мобильном —
нижнюю навигацию. Слоты `app.sidebar`, `app.main`, `app.details`, `app.settings` и
`app.overlays` рендерятся из клиентского реестра UI-вкладов. Каждый вклад изолирован
React ErrorBoundary, поэтому ошибка одного плагина не роняет shell.

Plugin manager получает состояние только через публичный runtime KAN-003. Включение и
отключение выполняются lifecycle-путём: `stop()` текущего runtime → создание нового runtime
с обновлённым `disabledPlugins` → `start()`. Прямая мутация состояния runtime и обход
lifecycle не используются. Действие отражается без полной перезагрузки страницы: server
action возвращает новый безопасный снимок и вызывает `revalidatePath("/", "layout")`.

## 2. Принятые решения

### 2.1. Клиентский реестр UI-вкладов

- Реестр принимает метаданные SDK `UiContribution` и React-рендерер, не импортируя
  внутренности ядра, чужие плагины или DOM другого плагина.
- Глобальный ID вклада уникален; повтор ID отклоняется.
- Для `view`/`route` уникален нормализованный маршрут; маршрут приводится к виду без
  query/hash и хвостового `/`.
- Порядок в слоте — по убыванию `priority`, затем по Plugin ID и ID вклада.
- Публичный API `defineUiPlugin` / `registerUiPlugin` регистрирует вклады атомарно:
  ошибка в середине откатывает уже добавленные вклады.
- Вклады плагина скрываются, если публичный runtime сообщает, что плагин не активен
  (`disabled`, `failed`, `incompatible`, `missing_dependency`, `safe_mode`).
- Тестовый UI-плагин `example.test-ui` живёт в
  `src/ui/__fixtures__/test-ui-plugin.tsx` и регистрируется только через публичный API.

### 2.2. Маршрутизация представлений

- Вклад с `kind = view | route` и `route` открывается через
  `app/view/[[...slug]]/page.tsx` и `PluginView`.
- `PluginView` берёт путь из App Router, находит вклад через реестр и показывает
  локальное пустое состояние, если маршрут не зарегистрирован или плагин недоступен.
- Навигационные вклады (`kind = navigation`) дают ссылки в sidebar и мобильной навигации.

### 2.3. Plugin manager и lifecycle

- Состояние берётся из `PluginRuntimeSnapshot` публичного `@kanbaner/kernel`.
- Клиенту отдаётся только безопасное представление: ID, имя, версия, `hostApi`,
  `requires`, `consumes`, `provides`, `permissions`, статус, безопасные диагностики.
- `entrypoints`, `migrations`, абсолютные пути и внутренние структуры runtime в клиент
  не попадают.
- Диагностика дополнительно санитизируется: удаляются ключи, похожие на пути, токены,
  секреты и стеки; строки с абсолютными путями заменяются на `[redacted]`.
- Async logger runtime возвращает Promise и не создаёт unhandled rejection; rejected
  Promise поглощается.
- Действия сериализуются внутренней очередью сервиса.
- `disabledPlugins` хранится в памяти серверного singleton. Это осознанное ограничение
  этапа без Storage Provider; после перезапуска процесса набор отключённых плагинов
  сбрасывается к `KANBANER_DISABLED_PLUGINS`.

### 2.4. Safe mode

- Safe mode показывается и в plugin manager, и в shell.
- Причины берутся из `problems` публичного snapshot: стабильный код, статус, Plugin ID и
  безопасное сообщение. Текст исключений и внутренние пути не выводятся.
- Если runtime не удалось запустить, layout получает безопасный fallback со
  `runtime_failed`, а не падает.

### 2.5. Доступность и адаптивность

- Skip link ведёт к `<main id="main-content" tabIndex={-1}>`.
- Основная навигация — обычные `<Link>`; активный пункт получает `aria-current="page"`.
- Мобильная навигация — отдельный `<nav aria-label="Мобильная навигация">` с
  `md:hidden`; desktop sidebar — `hidden md:flex`.
- Переключатель плагина — Radix Switch с доступным именем и описанием; действие не
  зависит от drag-and-drop.
- Карточки плагинов на 360 px идут одной колонкой, на широком экране — двумя.

| --------------- | ---- | --------------------------------------------------------------- |
| `/`             | 200  | обзор, навигация, карточки разделов                             |
| `/plugins`      | 200  | пустое состояние «Плагины не обнаружены», safe mode отсутствует |

UI-плагин подключается только в тестах через публичный API. Поэтому smoke проверяет
реальный маршрут и корректное пустое состояние; успешный рендер зарегистрированного
представления проверяется component-тестом `PluginView`.

- В `.next/static` нет `createPluginRuntime`, `pluginDirectories`, `node:fs`,
  `KANBANER_PLUGIN_DIRS`, `better-sqlite3`, `discoverPluginManifests`; server-only runtime
  не попал в client bundle.
- В `.next/static` нет `ajv`, TypeBox и схем SDK.
- В `apps/web/src` нет импортов `kernel/src`, `plugin-sdk/src` и доменных плагинов.
- В `apps/web` нет второй component library.
- Содержимое заметок, токены и секреты не логируются; тесты проверяют, что абсолютные
  пути и текст исключения не попадают в клиентское состояние.

## 6. Остаточные риски

1. **Набор отключённых плагинов не персистится.** До появления Storage Provider он живёт
   в памяти процесса и после перезапуска сбрасывается. KAN-009 может подключить
   хранилище настроек.
2. **Изменение набора требует restart lifecycle.** Это ограничение KAN-003. Реализовано
   через `stop()` + новый `start()`, без обхода runtime. Перезагрузка браузера не нужна.
3. **ESM-кэш.** Повторный `start()` использует кэш динамического импорта Node; module-level
   состояние плагина не пересоздаётся. Это уже зафиксированный риск KAN-003.
4. **`/view/test-ui` без fixture.** В production тестовый UI-плагин не регистрируется,
   поэтому маршрут показывает пустое состояние. Это ожидаемо и не является доменным
   представлением.
5. **Turbopack предупреждает о динамическом `fs.stat` в kernel.** Это код KAN-003,
   не изменявшийся в KAN-007; предупреждение не ломает build.
6. **Windows не проверен.** Текущее окружение Linux; пути в приложении строятся через
   `node:path`, но отдельный прогон на Windows не выполнялся.
7. **Слот `app.details` показывается только на `xl`.** На мобильном детали не отображаются,
   чтобы не отнимать ширину у основного представления. При появлении доменных деталей
   нужен отдельный mobile-паттерн (sheet/drawer).
