## Что сделано

`kanbaner.tasks` стал рабочим headless-плагином. `activate(context)` использует
только публичный `PluginActivationContext` и не импортирует ядро, Storage
Provider, SQL или другой плагин.

- Зарегистрированы все 8 команд и 4 запроса KAN-010 из
  `TASKS_COMMAND_LIST`/`TASKS_QUERY_LIST` с `exposure.ui: true`,
  `http: false`, `mcp: false`. Схемы KAN-010 не дублируются.
- Зарегистрированы типы ресурсов `project` и `task` с `resolve`, который
  возвращает `ResourceDescriptor` или `null`.
- Мутации выполняются в `TasksStore.withTransaction`; Store создаётся из
  bound `context.storage` с application-generated UUID и UTC-временем.
- Команды поддерживают `expectedVersion` и `Idempotency-Key`.
- События публикуются после коммита через `publishAfterCommit`; сбой доставки
  логируется и не отменяет команду.
- Поисковый индекс обновляется после коммита; при активации выполняется
  best-effort полная переиндексация.
- Реализована собственная последовательная очередь активации: мутации и
  переиндексация не пересекаются, но очередь не глобальная и не блокирует
  другие плагины.

## Idempotency-Key

- Коллекция `idempotency` в namespace `kanbaner.tasks`.
- ID записи — `SHA-256("kanbaner.tasks.idempotency\n<operationId>\n<key>")`,
  а не произвольная строка ключа.
- Проверка ключа, доменная мутация и запись результата выполняются **в одной
  транзакции** через `transaction.documents`. Rejected Promise откатывает и
  мутацию, и запись.
- Ввод нормализуется и канонизируется рекурсивной сортировкой ключей JSON;
  сравнение идёт по SHA-256.
- Повтор с тем же operation ID и вводом возвращает сохранённый результат без
  мутации, события и повторной индексации.
- Другой operation ID или другой ввод с тем же ключом даёт
  `IDEMPOTENCY_CONFLICT`.
- TTL — 24 часа; истёкшие записи не блокируют ключ.
- Запись результата использует document CAS; операции без ключа не
  дедуплицируются.

## События

- `project.created|updated|deleted`,
  `task.created|updated|moved|completed|deleted`.
- `source = "kanbaner.tasks"`, `contractVersion = 1`.
- Для update/move/complete `resourceVersion` равен новой версии сущности.
- Для delete `resourceVersion = eventVersion = последняя сохранённая версия + 1`
  из Store; у каждой задачи каскада свой `eventVersion`.
- При insert/move/complete/delete activation снимает задачи проекта до и после
  мутации в той же транзакции и публикует `task.updated` для каждого фактически
  сдвинутого соседа с его новой `position` и `resourceVersion`. Основная
  задача операции исключается.
- `project.delete` публикует `project.deleted` со всеми `deletedTasks` и
  отдельные `task.deleted` для каждой задачи; `task.delete` — событие корня,
  события подзадач и `task.updated` оставшихся соседей.
- Событие не публикуется до успешного коммита. Ошибка публикации или
  `status = "invalid"` только логируется.

## Поиск

- `toTaskSearchDocument` даёт `title`/`descriptionMarkdown` в тексте и
  `metadata.projectId`/`metadata.status`.
- `upsert` после коммита: созданная/изменённая задача и сдвинутые соседи.
- `delete` после коммита: `deletedResourceRefs` из Store, включая все задачи
  каскада проекта.
- Полная переиндексация при активации идемпотентна, best-effort, не блокирует
  активацию и сериализована с мутациями через очередь активации.
- Проекты не индексируются, как и задано контрактом поиска.

## Ошибки операций

Публичный SDK не предоставляет throwable-тип, аналогичный kernel
`OperationFailure`, а плагину запрещено импортировать ядро. Решение:

- `activation/errors.ts` один раз при активации получает конструктор ошибки
  активного хоста через публичный отказ bound-поиска на ResourceRef другого
  плагина (`kanbaner.fixture:item:activation-probe`). Вызов не читает и не
  меняет данные.
- Найденный конструктор используется для доменных ошибок, чтобы шина вернула
  стабильные `VERSION_CONFLICT`, `NOT_FOUND`, `VALIDATION_ERROR`,
  `IDEMPOTENCY_CONFLICT` и т.д.
- Если хост не дал `OperationFailure`, используется локальный
  `TasksOperationError` с тем же конвертом `PluginError`; шина в худшем случае
  вернёт `INTERNAL_ERROR`.
- Уже созданный хостом `OperationFailure` пробрасывается без изменений.

Это осознанный shim и главный риск для ревью: он использует публичное
поведение bound-сервиса, а не импорт ядра.

## Риски и ограничения

- `OperationFailure` capture-shim зависит от того, что bound-поиск отклоняет
  чужой ResourceRef ожидаемой ошибкой ядра. Это публичное поведение, но не
  формальный тип SDK. Если хост изменит поведение, доменные коды деградируют
  до `INTERNAL_ERROR`, данные при этом не пострадают.
- Событие сдвинутого соседа `task.updated` содержит дополнительное поле
  `position` в payload. Интерфейс `TaskUpdatedEventPayload` KAN-010 не
  менялся (владение схемами запрещено), поэтому поле добавлено в activation.
  Подписчики должны игнорировать необязательное поле.
- Полная переиндексация на активации O(N) и best-effort. Для больших баз она
  может быть дорогой; ошибка не блокирует активацию и восстанавливается при
  следующем запуске.
- Integration-тест импортирует контракт по относительному пути
  `../../packages/plugin-tasks/src/contract.ts`, потому что корневой
  devDependencies не содержит `@kanbaner/plugin-tasks`. Это тестовая
  особенность, не публичный импорт.
- Позиции по-прежнему пересчитываются в памяти в пределах области
  `(projectId, status)`; контракт Store допускает позднюю оптимизацию без
  изменения команд.
- Плагин попадает в discovery только при `KANBANER_PLUGIN_DIRS=packages`;
  упаковка встроенных плагинов остаётся отдельной задачей.
