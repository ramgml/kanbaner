## Что сделано

`TasksStore` KAN-010 реализован поверх bound `PluginStorage` /
`PluginDocumentStore` без SQL, kernel, драйвера БД и синхронных вызовов.

- `createTasksStore({ storage, idFactory, now })` создаёт root Store над
  коллекциями `projects` и `tasks` namespace `kanbaner.tasks`.
- Root CRUD/list/move/complete/delete открывают собственную транзакцию
  провайдера. `withTransaction` передаёт `TasksStoreTransaction` с
  `documents` той же транзакции; scoped-методы не открывают вложенную.
- Вложенный `withTransaction` на scoped-интерфейсе бросает
  `TasksNestedTransactionError` (`NESTED_TRANSACTION`); savepoints не
  используются. Rejected Promise откатывает транзакцию.
- Во всех изменениях и удалениях проверяется публичная `expectedVersion`.
  Конфликт возвращает `TasksVersionConflictError` (`VERSION_CONFLICT`) с
  `expectedVersion`/`actualVersion` и не перезаписывает документ.
- На каждом чтении и записи вызывается `assertStoredTask`; проект проверяется
  по `ProjectSchema`; документ и сохранённая модель сверяются по ID и версии.
- Позиция уникальна и непрерывна `0…N-1` в области `(projectId, status)`:
  append = `max + 1`, явная позиция и move переставляют соседей в той же
  транзакции, delete закрывает разрыв. `parentTaskId` в область не входит.
- Перестановка соседей — внутренняя операция порядка: публичная `version`
  задачи не меняется, внутренняя ревизия документа растёт. Поэтому
  параллельные `create`/`complete`/`move` разных задач не получают ложный
  `VERSION_CONFLICT` из-за сдвига позиций.
- Подзадачи ограничены одним уровнем; родитель обязан находиться в том же
  проекте. Перенос между проектами отсутствует в контракте, `move` сохраняет
  `projectId` и `parentTaskId`.
- `completedAt` вычисляется через `resolveCompletedAt`: create в `done` —
  `createdAt`, вход в `done` — `updatedAt`, выход — `null`, повторный
  `complete` — no-op без изменения версии.
- Теги нормализуются при create/update, фильтр `tag` нормализуется тем же
  способом.
- `listTasks` использует `indexedFields` для `projectId`, `status`,
  `priority`, `parentTaskId`, остальные фильтры и сортировку выполняет в
  Store; поддерживает `tag`, `text` (NFKC + lowercase), `dueBefore/dueAfter`
  включительно, сортировку `position`/`createdAt`/`updatedAt`/`dueAt`/`title`
  с `id asc` tie-breaker и `null dueAt` последними, `limit 1..200`, `total`,
  `nextOffset`.
- `project.list` — `createdAt asc`, `id asc`; пагинация стабильна.
- `project.delete` каскадно удаляет все задачи, `task.delete` — подзадачи.
  Возвращается дискриминированный `DeleteStoreResult` с root
  `version`/`eventVersion = version + 1`, `deletedResourceRefs` и
  `deletedTasks` с независимыми `version`/`eventVersion`.
- `Store` экспортируется из `src/index.ts`. Conformance suite — из
  `src/testing.ts` и subpath `@kanbaner/plugin-tasks/testing`.

## Conformance

`createTasksStoreConformanceSuite({ createStore })` возвращает 24 case и не
импортирует kernel, Storage Provider, SQLite, SQL или Vitest.

Драйвер `tests/integration/tasks-store-conformance.test.ts` запускает suite на
четырёх независимых provider-вариантах:

1. `memory-tasks` — in-memory без задержек.
2. `memory-tasks-delayed` — in-memory с `operationMs`/`transactionMs`.
3. `sqlite-tasks` — SQLite с core infrastructure migrations.
4. `sqlite-tasks-delayed` — SQLite с искусственными задержками.

Итого 25 тестов на вариант (24 case + проверка размера suite), 100
integration-тестов. Проверяются CAS, rollback rejected Promise, вложенная
транзакция, scoped `documents`, конкурентные create/complete/move,
уникальность позиций, append, правила подзадач, каскадные ссылки и версии,
`completedAt`, нормализованные теги, фильтры, сортировка, пагинация без
дублей, UTC/application IDs.

## Ключевые решения

- Соседи при вставке/move/delete меняют только `position` и внутреннюю
  ревизию документа. Публичная `Task.version` меняется только
  пользовательскими create/update/move/complete. Это сохраняет CAS-смысл и
  исключает ложные конфликты при конкурентных операциях над разными задачами.
- Append реализован как `max + 1` при непрерывных позициях; явная позиция
  трактуется как индекс вставки и сдвигает соседей.
- `idFactory` и `now` в `createTasksStore` используются как fallback, если
  типизированный вход не содержит ID/времени. Контракт KAN-010 передаёт их
  готовыми.
- `TasksNotFoundError` используется для update/move/complete/get. Delete
  отсутствующей сущности остаётся идемпотентным no-op.

## Риски и ограничения

- Позиции пересчитываются в памяти в пределах области `(projectId, status)`.
  Для больших колонок это O(N) записей на вставку/move/delete; контракт Store
  скрывает реализацию и допускает позднее добавление специализированного
  Store.
- Внутренняя ревизия документа может опережать публичную `version` задачи
  после перестановки соседей. Это осознанно: публичная версия отражает
  пользовательские изменения, а CAS по документу защищает транзакцию.
- Каскадное удаление проекта выполняется одной транзакцией; размер проекта
  остаётся ответственностью пользователя.
- Root-методы, вызванные внутри callback-а `withTransaction` на том же
  провайдере, не поддерживаются контрактом: используйте переданный scoped
  Store. Защита от такого вызова не добавлялась, чтобы не вводить Node-only
  async-context в доменный пакет.
- `tsup.config.ts` изменён только для сборки тестового subpath; публичные
  схемы и production entrypoint не расширялись тестовыми утилитами.
