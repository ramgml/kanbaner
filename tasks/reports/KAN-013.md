## Что сделано

KAN-013 реализована как отдельный UI-плагин `kanbaner.task-list`, который
работает только через публичные команды и запросы домена `kanbaner.tasks`.

- Создан `packages/task-ui` — общая React/Tailwind-библиотека компонентов:
  `TaskTable`, `TaskCard`, `TaskDetails`, `TaskForm`, `ProjectForm`,
  `TaskFilters`, состояния загрузки/пустоты/ошибки, форматирование и парсинг
  значений. Пакет не является плагином и не содержит доменных операций.
- Создан `packages/plugin-task-list`:
  - `dist/index.js` регистрирует только UI-metadata (view `/view/tasks`,
    навигацию, desktop/mobile-панели деталей);
  - `dist/ui.js` содержит рендереры и использует только
    `@kanbaner/plugin-tasks/contract`, `@kanbaner/plugin-sdk` и
    `@kanbaner/task-ui`.
- Адаптивный интерфейс: таблица на десктопе, карточки на 360 px,
  полноэкранная панель деталей на мобильном, desktop-панель на `xl`.
- Список: фильтры по проекту/статусу/приоритету/тегу/сроку, сортировка,
  пагинация, состояние в query string (переживает reload и работает как
  ссылка).
- Действия: создание проекта и задачи, редактирование, завершение,
  перемещение, удаление с inline-подтверждением.
- UI-entrypoint плагина импортируется только из
  `apps/web/src/ui/builtin-ui-plugins.ts`; shell и слоты получают metadata с
  сервера и рендереры из клиентского реестра.
- `scripts/check-import-boundaries.mjs` расширен: проверка `task-ui` и
  `plugin-task-list`, запрет корневого `@kanbaner/plugin-tasks` и apps/server
  internals в UI, запрет React/client в server-графе, ограничение импорта
  UI-entrypoint composition-модулем. Self-test покрывает каждое новое
  нарушение.
- `specs/architecture.md` §6: добавлен `@kanbaner/task-ui` и правила импорта.
- `packages/plugin-task-list/README.md`: границы плагина и ограничения.

## Осознанное ограничение: родитель только при создании

Публичная команда `task.update` не принимает `parentTaskId`, поэтому:

- родитель выбирается только в форме создания задачи;
- в режиме редактирования родитель показан **только для чтения**
  (`lockParent`), выбор отсутствует;
- контракт `kanbaner.tasks` не расширялся, смена родителя не эмулируется
  отдельными командами.

Ограничение зафиксировано в `packages/plugin-task-list/README.md` и покрыто
E2E-проверкой: `select[name="parentTaskId"]` в edit отсутствует, отображается
«Без родителя (корневая)».

## Исправление VERSION_CONFLICT между экземплярами SDK

Симптом: конфликт версий приходил в UI как `INTERNAL_ERROR`
(«Внутренняя ошибка операции»).

Фактическая причина (подтверждена временными серверными логами):

- `plugin-tasks` корректно создавал `TasksVersionConflictError` и маппил его в
  `VERSION_CONFLICT`;
- ядро получало `PluginOperationError`, но `instanceof` давал `false`;
- серверный плагин загружается динамическим `import()` из собственного
  `dist`, поэтому получает второй экземпляр `@kanbaner/plugin-sdk`, а не тот,
  что собран в бандле ядра;
- `mapThrownError` превращал нераспознанную ошибку в безопасный
  `INTERNAL_ERROR`.

Исправление согласовано оркестратором и находится в
`packages/kernel/src/operations/errors.ts`:

- сохранено прежнее поведение для `instanceof PluginOperationError`;
- добавлено структурное распознавание ошибки с `name = "PluginOperationError"`
  и конвертом, прошедшим `PluginErrorSchema` через `validateWithSchema`;
- произвольные `Error` и подделки с невалидным конвертом по-прежнему дают
  `INTERNAL_ERROR` без раскрытия stack/путей/секретов.

Тесты в `packages/kernel/src/operations/bus.test.ts`:

- `распознаёт PluginOperationError из другого экземпляра SDK` →
  `VERSION_CONFLICT`;
- `не принимает подделку с невалидным конвертом ошибки` → `INTERNAL_ERROR`.

UI-часть (`packages/plugin-task-list/src/ui/task-details-panel.tsx`):

- при `VERSION_CONFLICT` устаревшая версия не отправляется повторно;
- форма закрывается, задача и список перечитываются;
- сообщение «Задача уже изменена в другом месте…» хранится отдельно от
  обычной ошибки и остаётся видимым после повторного чтения;
- правка второй вкладки не перезаписывает данные первой.

## Необходимая правка globals.css

В `apps/web/src/app/globals.css` добавлены:

```css
@source "../../../../packages/task-ui/src";
@source "../../../../packages/plugin-task-list/src";
```

Причина: Tailwind автоматически сканирует только `apps/web`, а адаптивные
классы находятся в исходниках пакетов вне этого каталога. Без `@source`
`md:block`, `xl:hidden` и другие классы не попадали в CSS: таблица на
десктопе оставалась скрытой, а мобильная панель перекрывала desktop-интерфейс.
Правка согласована как часть адаптивного UI.

### Evidence VERSION_CONFLICT

E2E-сценарий `не перезаписывает задачу при VERSION_CONFLICT из второй вкладки`:

- вкладка A сохраняет новое название;
- вкладка B отправляет устаревшую версию;
- сервер возвращает `VERSION_CONFLICT` (структурное распознавание в ядре);
- вкладка B показывает «Задача уже изменена в другом месте…», перечитывает
  задачу и отображает правку A;
- название из вкладки B отсутствует в деталях и в списке после reload.

## Исправления по ревью KAN-013

Все findings закрыты отдельным коммитом `fix(task-list): закрыть границы UI и доступность`.

1. **Санитизация ошибок (MEDIUM).** `packages/kernel/src/operations/errors.ts`
   после `validateWithSchema` не возвращает исходный `error.error`, а заново
   собирает `PluginError` через `createPluginError` только из
   `code/message/retryable/details`. Всё структурное распознавание, включая
   `instanceof`, чтение `name` и `error` и геттеры, обёрнуто в `try/catch`.
   Секретные дополнительные поля (`stack/path/secret`) не попадают в результат,
   бросающий accessor даёт `INTERNAL_ERROR`, кросс-экземплярный валидный
   конверт по-прежнему сохраняется.
2. **Чужие маршруты (MEDIUM).** Shell передаёт текущий `pathname` в публичные
   props: `UiSlot` → `ContributionRenderer` → `UiRendererProps` в
   `@kanbaner/task-ui`. Детали списка загружаются и рендерятся только при
   `pathname === "/view/tasks"`; `/plugins?task=id` не вызывает `task.get`, а
   client-side Link-переход скрывает панель.
3. **Мобильный aria-modal (MEDIUM).** Мобильная панель заменена на нативный
   `<dialog>` с `showModal()`, initial focus, явным Tab-trap, Escape через
   `cancel` и возвратом фокуса на карточку. На десктопе modal не открывается.
4. **Устаревший маршрут (MEDIUM).** `syncPlugin` удаляет маршрут при смене
   `view` на `panel`, даже если строка `route` не изменилась; `resolveRoute`
   возвращает `null`, новый panel остаётся в слоте.
5. **Владение pre-bind (MEDIUM).** `registerBatch`/`syncPlugin` проверяют
   `bound.pluginId === pluginId` до любых изменений состояния. Чужой pre-bind
   отклоняется, а `unregisterPlugin` удаляет и pre-bind рендереры плагина.
6. **Поколения и структурное равенство (LOW).** В реестр введены token
   поколений: cleanup старого sync/batch не удаляет вклады нового поколения;
   `register → bind → cleanup` снимает вклад вместе с привязкой; повторный
   структурно идентичный sync не увеличивает версию и не будит подписчиков;
   render-only привязка не считается новой metadata-регистрацией.
7. **E2E и integration (MEDIUM).** Добавлены реальная пагинация 26 задач с
   `page=2` и reload, disable/enable `kanbaner.task-list`, подзадача/родитель,
   complete и фильтры `status/tag/due`. Server-side integration
   `tests/contract/task-list-disabled.test.ts` подтверждает, что при
   отключённом списке команды/запросы `kanbaner.tasks` доступны через
   `composition.executeUiOperation`, а `completedAt` выставляется корректно.

### Повторное ревью: breakpoint и native dialog

Открытый мобильный `<dialog>` не должен оставаться modal после resize
mobile→desktop. Подписка `useSyncExternalStore` слушает
`MediaQueryList.change` для `(min-width: 1280px)`; breakpoint входит в
зависимости эффекта:

- mobile→desktop: cleanup снимает Tab-trap, вызывает `dialog.close()` и
  возвращает фокус на видимый элемент (desktop-кнопку задачи, а не скрытую
  мобильную карточку);
- desktop→mobile при выбранной задаче: эффект снова вызывает `showModal()` и
  initial focus;
- pathname gating и cleanup не изменены: вне `/view/tasks` ничего не
  открывается.

### Отсутствие HTTP API в MVP

В текущем MVP HTTP-транспорт ещё не реализован: нет `apps/web/src/app/api`,
`KANBANER_API_TOKEN` и Bearer-аутентификации. Поэтому требование «задачи
доступны через публичные operations/API при отключённом `kanbaner.task-list`»
проверяется на том же composition root, который использует UI, а не через
HTTP-запрос. Это ограничение зафиксировано здесь и в README плагина.

## Риски и ограничения

- Структурное распознавание `PluginOperationError` опирается на публичный
  конверт (`name` + `PluginErrorSchema`). Плагины считаются доверенным
  локальным кодом; посторонний объект с валидным конвертом может быть
  принят за ошибку операции, но не получит доступ к данным.
- `VERSION_CONFLICT` не выполняет автоматический merge: пользователь видит
  объяснение и должен повторить правку на свежих данных.
- Родитель задачи нельзя изменить после создания — ограничение контракта,
  зафиксировано в README и отчёте.
- `@source` привязан к путям пакетов. При переносе `packages/*` потребуется
  обновить директивы; регрессию ловят E2E на 360 px и десктопе.
- E2E выполняется в Chromium с одним worker. Пагинация проверяется реальными
  26 задачами, но другие браузеры не входят в текущий MVP-прогон.
- Focus trap опирается на нативный `<dialog>` плюс явный Tab-trap; при
  добавлении экзотических фокусируемых элементов селектор нужно расширять.
- Реестр различает поколения через внутренний token; это не публичный
  контракт, но cleanup разных sync-ов теперь безопасен.
- HTTP API в MVP отсутствует, поэтому доступность операций при отключённом
  списке доказана server-side, а не HTTP-запросом.
- Тест `tests/contract/fixture-activation.test.ts` пришлось уточнить из-за
  появления второго встроенного плагина в общем discovery root.
