# KAN-052 — Отчёт

- Задача: `tasks/KAN-052-blocknote-lifecycle-flush.md`
- Ветка: `fix/kan-052-blocknote-lifecycle-flush`
- Worktree: `.worktrees/kan-052-blocknote-lifecycle-flush`
- Коммит: `fix(notes): вынести сериализацию из lifecycle`

## Причина

BlockNote 0.54 сериализует Markdown через external HTML exporter, а React-версия
inline content `toExternalHTML` рендерит элемент через `elementRenderer` с
синхронным `flushSync` из `react-dom`. Пока такой документ не содержит inline
image, React-renderer не вызывается. Как только в заметке появлялся inline
image (image внутри emphasis, списка, цитаты, заголовка или ячейки таблицы),
вызов `editor.blocksToMarkdownLossy()` внутри `useEffect` давал:

- Console Error: `flushSync was called from inside a lifecycle method...`;
- warning `ReactInlineContentSpec: renderHTML() failed`;
- неполный внешний HTML: renderHTML обрывался, и сериализация могла потерять
  inline image.

Воспроизведение подтверждено unit-тестом с
`До ![Схема](attachment://img-1) после`: до исправления React писал flushSync
error, а exporter — warning о failed renderHTML.

Дополнительный lifecycle-путь обнаружился в E2E: `BlockNoteView` меняет
`editor.isEditable` внутри своего эффекта при смене `readOnly`/`loading`, а
`setEditable` эмитит change-событие. Наш `onChange` синхронно сериализовал
inline image и снова попадал в lifecycle.

## Решение

Исправлена причина, а не симптом: Markdown-сериализация больше не использует
React external renderer.

- В `note-editor-schema.tsx` для `inlineImage` и `linkedImage` сохранён
  React node view (`render`), но `implementation.toExternalHTML` переопределён
  на обычный DOM-контракт BlockNote (`{ dom }`). Это публичный тип
  `InlineContentSpec`/`InlineContentImplementation`.
- DOM-версия повторяет структуру прежнего React-вывода: wrapper
  `span[data-inline-content-type]` c непустыми `data-url`/`data-name`, внутри
  `<img>`; для `linkedImage` — обёртка `<a>` при валидном href.
- Все пути сериализации (`initial useEffect`, внешнее значение, `onChange` при
  `setEditable`, export/copy) теперь проходят без `flushSync`, поэтому
  синхронные state semantics сохранены без отложенных задач.

### Почему не отменяемый `setTimeout(0)`

Вариант с выносом сериализации из lifecycle в отменяемую задачу был
реализован и проверен, но отвергнут: он меняет наблюдаемое поведение.

- `onChange` становился асинхронным, поэтому `dirty`/`Сохранено` на мгновение
  отставали от документа. E2E-экспорт успевал скачать старый Markdown
  (`сохраняет вложенность списка, созданную Tab`).
- Эхо `value` от родителя приходило позже фактического состояния редактора:
  внешний reconcile применял устаревший `value` и терял символы при быстром
  вводе (`Раздел` → `Рд` в E2E slash-меню).
- Подавление console не использовалось ни в одном варианте.

Root-fix в renderer устраняет сам `flushSync` и оставляет синхронную
семантику autosave/export, поэтому выбран он.

## Тесты

Unit (`markdown-note-editor.test.tsx`), console spies на `error`/`warn`:

- initial load с inline image не пишет `flushSync` и `renderHTML() failed`,
  inline image виден, ложного `onChange` нет;
- lifecycle-смена `editable` (`readOnly`) с inline image не сериализует через
  React lifecycle и не публикует `onChange`;
- два разных `rerender` (`note-1` → `note-2` → `note-3` с inline image) до
  ожидания готовности применяют только последний документ: исходный и
  промежуточный не протекают, console-ошибок нет;
- при быстрой смене внешнего значения применяется только последнее, без
  `onChange`;
- инициализация inline image не публикует `onChange` (autosave не получает
  неполный документ).

Проверено, что три regression-теста падают на исходной схеме с реальным
flushSync error (временный `git stash` только schema-файла, затем восстановлен).

E2E `apps/web/e2e/notes.spec.ts`:

- Новый тест `не сериализует BlockNote в lifecycle и быстро переключает
заметки с inline image`:
  - слушает реальные `console` error/warning и `pageerror`;
  - загружает настоящее вложение через UI (сервер принимает только
    `attachment://` и HTTP(S), `data:` URL отклоняется доменной валидацией);
  - вставляет inline image HTML-paste с data URL существующего attachment,
    который notes-view канонизирует обратно в `attachment://`;
  - проверяет initial load после reload, inline image и сохранение;
  - сначала дожидается готовности inline-заметки, затем в одном task запускает
    два перехода `inline → plain → inline` без ожидания между кликами;
  - проверяет, что победила последняя inline-заметка (URL, `data-note-id`,
    `data-ready`, inline image и её текст), промежуточный документ не применён,
    console-сообщений о lifecycle сериализации нет.
- Сырой `<img>` в external HTML BlockNote не парсится в inline content,
  поэтому paste использует нативную обёртку `data-inline-content-type`;
  реального дефекта парсинга это не выявило.

## Ограничения и риски

- Переопределяется `implementation.toExternalHTML` публичного типа
  `InlineContentSpec`; это не внутренний импорт, но при мажорном обновлении
  BlockNote контракт нужно перепроверить. Node view и paste/copy остаются на
  штатных механизмах BlockNote.
- Внешний HTML inline image теперь строится DOM-кодом; структура wrapper/img
  повторяет прежний React-вывод, round-trip Markdown и inline images покрыт
  существующими тестами `editor-roundtrip.test.ts`.
- E2E работает в production shell: React dev warning `flushSync` там не
  печатается, поэтому регрессию ловит библиотечный warning
  `ReactInlineContentSpec: renderHTML() failed` и unit-тесты с console spies.
- Обнаружено отдельное ограничение навигации заметок (вне файлов этой
  задачи): `selectNote` в `notes-view.tsx` делает early return, если целевой id
  равен текущему `selectedIdRef`. Пока переход в другую заметку ещё грузится,
  `selectedIdRef` хранит прежнюю заметку, поэтому синхронный клик назад по ней
  игнорируется. Из-за этого буквальная последовательность `inline → plain →
inline` в одном task не запускает повторную загрузку inline. E2E использует
  эквивалентную по смыслу и более сильную схему `inline → plain → inline`
  с тремя заметками: два реально запущенных перехода, последняя inline
  побеждает. Предлагается отдельная задача на pending-selection в
  `notes-view.tsx` (ID не назначался).
- Новых зависимостей, миграций и изменений публичного API/контрактов нет.
