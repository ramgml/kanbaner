## 1. Итог

Реализован и повторно проверен backend-neutral Storage-слой:

- публичные Storage-контракты SDK: capabilities, provider, transactions/savepoints,
  Store-регистрация, `PluginDocumentStore`, `LinkStore`, `PluginStateStore`,
  `MigrationStore`, `SearchIndexStore`, UTC/application-ID семантика;
- реестр провайдеров с обязательной capability `transactions`, отказом дублирующего
  `backendId`, lifecycle-мьютексом и структурированными ошибками;
- тестовый in-memory provider с отдельным состоянием на экземпляр, искусственными
  асинхронными задержками, FIFO-очередью операций, эксклюзивными транзакциями и
  отслеживанием поздних записей;
- backend-neutral runner миграций с SHA-256, детерминированным порядком,
  атомарным exactly-once применением, проверкой checksum и backend-isolation;
- lifecycle-adapter для hook-а KAN-003;
- reusable Storage Provider Conformance Suite, пригодный для KAN-009 SQLite;
- локальные barrel-точки входа SDK и kernel, включая storage в сборку и `.d.ts`.

Структурная копия SDK-контрактов удалена. `packages/kernel/src/storage/contracts.ts`
содержит только реэкспорт публичных имён `@kanbaner/plugin-sdk`, а
`packages/kernel/src/resources/link-store.ts` — согласованный type-alias/реэкспорт

`StorageError`, что и SDK (`instanceof` согласован).

## 2. Публичные контракты SDK

Модуль `packages/plugin-sdk/src/storage/index.ts` экспортируется из корневого SDK
согласованным изменением `packages/plugin-sdk/src/index.ts`.

### 2.1. Capabilities

`StorageCapabilities` содержит явные флаги:

- `transactions` — обязательна для MVP;
- `savepoints`, `json`, `fullTextSearch`, `stemming`, `onlineBackup`, `wal`, `watch`.

`createStorageCapabilities` по умолчанию включает только `transactions`.
`missingRequiredStorageCapabilities` и `isMvpStorageProvider` дают единый способ
проверки пригодности.

### 2.2. Provider и транзакции

- `StorageProvider.open`, `close`, `healthCheck` асинхронны.
- `withTransaction(async (tx) => ...)` удерживает границу до завершения callback.
- `StorageTransaction` предоставляет те же встроенные Store, что и провайдер.
- `withSavepoint` требует capability `savepoints`, иначе `SAVEPOINTS_UNSUPPORTED`.
- `createStore(registration)` создаёт доменный Store в области провайдера или
  транзакции.
- `StorageProviderRegistry` объявлен как публичный контракт реестра.

Store-операции области транзакции/savepoint отслеживаются: после завершения callback
новые операции запрещены, начатые дожидаются через `allSettled`, и только затем
выполняются commit/rollback/release. После искусственной задержки `active` области
проверяется повторно, поэтому операция, чья задержка закончилась после callback, не
может записать данные. Вложенные savepoint-области учитывают активность предков.

### 2.3. Store-контракты

- `PluginDocumentStore`:
  - `get`, `put`, `delete`, `query`, `list`;
  - версия начинается с 1;
  - создание допускает `expectedVersion = undefined | 0`;
  - обновление требует точную текущую `expectedVersion`, иначе `VERSION_CONFLICT`;
  - `delete` поддерживает необязательную `expectedVersion`;
  - `query` фильтрует по `pluginId`, `collection`, `ids`, `indexedFields`, `sort`,
    `offset`, `limit`; произвольных SQL-предикатов нет.
- `LinkStore` полностью совместим с портом KAN-005:
  `add`, `remove`, `listByRef`, `deleteByRef`, атомарность и идемпотентность.
- `PluginStateStore`: `get`, `put`, `list`, `delete`; состояние принадлежит плагину.
- `MigrationStore`: `list`, `find`, `record`; ключ истории —
  `(backendId, pluginId, version)` с обязательной проверкой `checksum`. Все три
  операции используют каноническую проверку `backendId` из SDK.
- `SearchIndexStore`: `upsert`, `delete`, `deleteMany`, `clear`, `search`, `list`,
  `reindex`; стратегия `full-text` или `substring`, без embeddings.
  `SearchIndexDocument` не содержит `projectRef`: доменные атрибуты, включая ссылку
  на проект, передаются только в generic `metadata`, ядро их не интерпретирует.

### 2.4. ID, время и JSON

- Публичные ID создаёт приложение/плагин до записи.
- Backend не генерирует ID и не использует autoincrement/rowid как публичный ID.
- `toUtcTimestamp` и `currentUtcTimestamp` возвращают RFC 3339 UTC с `Z`.
- Неверная дата даёт структурированную ошибку, а не локальное время.
- `isJsonObjectValue` принимает только plain object (`Object.prototype` или `null`
  prototype) и выполняет глубокую проверку `validateJsonValue`.
- `Date`, `Map`, массивы, циклические ссылки, `undefined`, `NaN` и `Infinity`
  отклоняются на границе Store.

### 2.5. Ошибки

`StorageError` — единый публичный класс для SDK, kernel и будущего SQLite provider.
Коды стабильны, `retryable` вычисляется по карте, `details` имеют тип JSON-объекта.
Kernel-модуль `errors.ts` реэкспортирует SDK-класс; `StorageOperationError` оставлен
как совместимый type-alias.

## 3. Kernel: реестр и bootstrap

### 3.1. `StorageProviderRegistry`

- Регистрация по `backendId`, повтор отклоняется `DUPLICATE_BACKEND`.
- Неизвестный backend — `UNKNOWN_BACKEND`.
- Провайдер без `transactions` не регистрируется:
  `MISSING_TRANSACTIONS_CAPABILITY`.
- `capabilitiesOf` доступен до операции.
- `open`/`close`/`closeAll` сериализуются lifecycle-мьютексом: проверка активного
  backend-а и открытие выполняются в одной критической секции. Два параллельных
  `open` разных backend-ов дают один успех и один `ACTIVE_BACKEND_CONFLICT`, второго
  открытого backend-а не возникает.
- `openChecked` возвращает `{ provider, health }` с одним проверенным
  `StorageHealth`; `open` делегирует ему и возвращает только провайдера.
- При ошибке/исключении `open`, rejected/false health провайдер закрывается,
  активный backend не назначается. Ошибка cleanup не затирает первичную ошибку.
- `close` очищает активный backend в `finally`, даже если `provider.close()` упал.
- В MVP активен один backend; второй открытый backend даёт
  `ACTIVE_BACKEND_CONFLICT`.
- `registerStore`/`createStore` реализуют механизм регистрации доменных
  Store-контрактов; дубликат контракта отклоняется.
- `register` — синхронная lifecycle-операция, все операции Provider/Store
  асинхронны.

### 3.2. Bootstrap

`bootstrapStorage` выполняет строгий порядок:

1. регистрация провайдера;
2. открытие и ровно один health check через `openChecked`;
3. миграции с уже проверенным `StorageHealth`.

Ошибка регистрации/открытия/health check не запускает ни одной миграции. Bootstrap
не игнорирует health: результат `openChecked` передаётся в `StorageMigrationRunner`,
который проверяет `health.ok` без повторного вызова `healthCheck`.

При ошибке миграции провайдер закрывается, активный backend очищается
(`NO_ACTIVE_BACKEND`), исходная ошибка миграции сохраняется даже при ошибке cleanup.
Частично открытый провайдер закрывается и при ошибке `open`.

## 4. In-memory provider

`InMemoryStorageProvider`:

- каждый экземпляр владеет отдельным состоянием; глобального singleton нет;
- `open`/`close` идемпотентны;
- операции закрытого провайдера отклоняются `PROVIDER_CLOSED`;
- настраиваемые задержки `openMs`, `healthCheckMs`, `operationMs`, `transactionMs`;
- все Store операции проходят через FIFO-мьютекс;
- транзакция удерживает мьютекс до завершения async callback;
- операции другого вызова ждут и не выполняются внутри чужой транзакции;
- rollback восстанавливает снимок состояния;
- `withSavepoint` восстанавливает только вложенный снимок;
- без capability `savepoints` возвращает `SAVEPOINTS_UNSUPPORTED`;
- Store, созданный через `tx.createStore`, использует транзакционную область.

Защита от поздних записей:

- каждая область (`tx`/savepoint) хранит `active`, `rolledBack` и набор `pending`
  начатых операций;
- завершение callback запечатывает область: новые операции получают
  `TRANSACTION_CLOSED`;
- перед commit/rollback выполняется `Promise.allSettled` по `pending`;
- после `operationMs` задержки `active` проверяется повторно, поэтому операция,
  проснувшаяся после callback/rollback, не пишет;
- вложенная область проверяет активность всех предков;
- sealing и фактический rollback разделены: родитель не начинает rollback до drain
  tracked child-областей, поэтому rejected savepoint восстанавливает собственный
  snapshot при sealed-родителе и пропускает restore только после фактического
  `rolledBack` предка;
- провайдер не подавляет reject внешнего Promise: вызывающий обязан обработать
  возвращённое значение, как в обычном JS. Sealing ждёт внутреннюю задачу через
  `allSettled`, но ignored внешний Promise даёт стандартный
  `unhandledRejection`.

Логические инфраструктурные области (`core_plugins`, `core_plugin_migrations`,
`core_resource_links`) существуют как внутренние Map-структуры провайдера.
Их имена не попадают в публичные контракты.

## 5. Миграции

`StorageMigrationRunner`:

- проверяет все миграции до любых изменений;
- неверный Plugin ID даёт `INVALID_PLUGIN_ID` и не создаёт namespace;
- повтор версии или пустое содержимое даёт `INVALID_MIGRATION`;
- сортирует по `pluginId`, `version`, `name`;
- checksum — SHA-256 от однозначного `JSON.stringify([version, name, source])`;
  переносы строк в `name`/`source` не создают коллизий;
- уже применённая миграция с тем же checksum пропускается;
- другой checksum блокирует запуск `MIGRATION_CHECKSUM_MISMATCH`;
- каждая миграция и запись журнала выполняются в одной транзакции;
- rejected Promise откатывает и данные, и запись журнала;
- внутри транзакции повторно проверяется наличие записи, поэтому конкурентный
  запуск применяет миграцию один раз;
- `backendId` входит в журнал и проверки, backend isolation тестируется на одном
  провайдере через запись валидного чужого `backendId`;
- опция `health` позволяет bootstrap переиспользовать уже проверенный
  `StorageHealth` без второго health check.

`createPluginMigrationHook` адаптирует runner к `PluginMigrationContext` KAN-003:
читает migrations через внедряемый loader, пропускает `migrationsPath = null`,
отклоняет миграции чужого Plugin ID.

## 6. Conformance Suite

`createStorageProviderConformanceSuite` находится в
`packages/kernel/src/storage/conformance.ts` и экспортируется из kernel barrel.
Suite не импортирует vitest, SQLite, Docker или внешнюю СУБД: это массив
`{ name, run(provider) }`, который harness запускает своим runner-ом.

Покрытие:

- backendId и capabilities до операции;
- открытие/health/повторное открытие;
- операции закрытого провайдера;
- асинхронность публичных Store-операций;
- документы: create/get/list/query/delete, app ID, UTC, сортировка, пагинация;
- конфликт версий, `expectedVersion` при удалении и конкурентные update одной
  версии (один success, один `VERSION_CONFLICT`, итоговая версия 2);
- изоляция pluginId/collection;
- ссылки: конкурентный atomic `add`, идемпотентность, reverse relation,
  очистка source/target;
- состояние плагина и защита от внешней мутации;
- миграции: порядок, skip, checksum mismatch, rollback, backend isolation через
  `MigrationStore.record` чужого валидного `backendId`, неверный Plugin ID,
  конкурентный `runner.run` (одна запись `up`);
- commit после async callback, rollback rejected Promise;
- поздние записи: начатая операция не пишет после rollback транзакции, savepoint и
  миграции; старые данные и журнал сохраняются;
- rejected savepoint после sealing родителя: nested put успевает, родитель
  возвращается без await, savepoint позже отклоняется и восстанавливает свой
  snapshot; nested document отсутствует, данные родителя сохранены;
- ожидание операции другого вызова;
- сериализация параллельных write-транзакций;
- savepoint rollback и отказ без capability;
- поиск, fallback-стратегия, delete/reindex/clear без `projectRef`;
- Store-контракт в области провайдера и транзакции;
- реестр: capabilities, активный backend, duplicate `backendId`, конкурентные
  `open` двух backend-ов;
- bootstrap: health до миграций.

Suite запущен на обычном и искусственно замедленном in-memory provider. Оба
варианта используют `createAlternateProvider` для гонки `open`, а вариант с
задержками передаёт те же задержки и в provider без savepoints. KAN-009 сможет
подключить SQLite provider через тот же `createProvider`.

## 10. Остаточные риски

1. **In-memory provider не персистентен.** Он предназначен для тестов и локальной
   разработки; production-поведение должен подтвердить SQLite provider KAN-009.
2. **KAN-009 обязан сохранить семантику транзакций.** Exactly-once миграций,
   late-write sealing и ожидание внешних операций опираются на эксклюзивность
   транзакции провайдера; conformance должен пройти на SQLite без ослаблений.
3. **Checksum хранится в записи версии, а не в уникальном ключе.** Ключ —
   `(backendId, pluginId, version)`, checksum проверяется до/внутри транзакции.
   Это позволяет обнаружить изменение применённой миграции; альтернативный ключ с
   checksum не позволил бы отличить изменение от новой миграции.
4. **In-memory `full-text` — упрощённый token-match, не FTS5.** Реальный FTS5,
   `unicode61`, backup и WAL должны быть реализованы и проверены в KAN-009.
5. **Вызывающий обязан обработать возвращённый Promise.** Провайдер не подавляет
   reject Store-операций. Неawait-нутая операция до конца callback может успеть
   примениться и затем откатиться снимком; после callback она отклоняется
   `TRANSACTION_CLOSED`. Если вызывающий игнорирует Promise, возникает штатный
   `unhandledRejection` — это ответственность вызывающего кода, а не скрытый noop
   внутри провайдера.
6. **Windows не проверен.** Используются кроссплатформенные API Node.js, но
   отдельный прогон на Windows не выполнялся.
7. **Сложные запросы не входят в `PluginDocumentStore`.** Плагин с такими запросами
   объявляет собственный Store-контракт, как и предусмотрено архитектурой.
8. **Backup/restore не реализованы.** Это ответственность provider-а и следующих
   задач; в текущем слое нет копирования файлов БД.
9. **`StorageProviderRegistry.register` синхронный.** Это lifecycle-операция, а не
   операция хранилища; все публичные операции Provider/Store асинхронны.
10. **Полный SQLite provider ещё не проверен.** Conformance готов к KAN-009, но
    фактическая реализация SQLite/WAL/backup появится в следующей задаче.

## 11. Исправления по замечаниям ревью (2026-11-07)

1. **BLOCKER late writes.** Области tx/savepoint отслеживают `pending`; callback
   запечатывает область, `allSettled` выполняется до commit/rollback/release,
   `active` перепроверяется после задержки, вложенность учитывается. Conformance
   проверяет tx, savepoint и миграцию на обычном и замедленном provider;
   focused-тесты подтверждают `TRANSACTION_CLOSED` и сохранение старых данных.
2. **HIGH registry race.** `open`/`close`/`closeAll` сериализованы lifecycle-мьютексом;
   конкурентные `open` двух backend-ов дают один success, один
   `ACTIVE_BACKEND_CONFLICT`, health подтверждает один открытый backend.
3. **HIGH bootstrap.** Используется `openChecked` с одним проверенным health; при
   ошибке `open`/health/migration провайдер закрывается, активный backend
   очищается, первичная ошибка сохраняется при ошибке cleanup; health не
   игнорируется.
4. **MEDIUM conformance.** Backend isolation проверяется на одном провайдере через
   `MigrationStore.record` чужого валидного `backendId`; конкурентный `runner.run`

5. **Checksum.** Перешёл на `JSON.stringify([version, name, source])`; добавлен

6. **Дублирование контрактов.** `resources/link-store.ts` стал реэкспортом SDK;
   kernel использует SDK `assertBackendId`, `assertApplicationId`,

## 12. Повторное ревью: savepoint sealing и Promise-семантика

1. **BLOCKER rejected savepoint после sealing родителя.** `active` (sealed) и
   `rolledBack` (фактический откат) разделены. Родитель не начинает rollback до
   drain tracked child-областей, поэтому rejected savepoint восстанавливает
   собственный snapshot при sealed-родителе и пропускает restore только при
   фактическом `rolledBack` предка. Добавлены unit-regression и reusable
   conformance case: nested put успевает, родитель возвращается без await
   savepoint, savepoint позже deferred reject; после `withTransaction` nested
   document отсутствует, исходные данные родителя сохранены. Прежние late-write
   case не ослаблены.
2. **MEDIUM noop catch.** Внутренний `void task.catch(() => undefined)` удалён.
   Действует стандартная JS-семантика: вызывающий обрабатывает возвращённый
   Promise. Внутренняя задача области по-прежнему дожидается через `allSettled`,
   но это не помечает внешний Promise обработанным. Добавлен тест: ignored
   operation после sealing отклоняется `TRANSACTION_CLOSED`, вызывающий ловит его
   через `await expect(...).rejects`, при прикреплённом handler
   `unhandledRejection` не возникает.
