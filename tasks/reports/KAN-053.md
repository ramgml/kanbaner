# KAN-053 — Отчёт

- Задача: `tasks/KAN-053-note-switch-performance.md`
- Ветка: `perf/kan-053-note-switch`
- Worktree: `.worktrees/kan-053-note-switch`
- Коммит: `perf(notes): ускорить переключение страниц`
- Коммит по ревью: `fix(notes): закрыть замечания к переключению страниц`

## Причина

Замер в браузере на реальной заметке «Галерея блоков»
(`note-b0a5a3ea-…`) показал, что сеть не является узким местом:

- `note.get` — 20–40 мс;
- все `attachment.get` (3 вложения, из них JPEG с base64 ~1.18 МБ) —
  ~120–170 мс суммарно.

Задержку давала синхронная работа с Markdown после получения вложений.
`AttachmentUrlCache.toEditor` раздувал `editorValue` до ~1.18 МБ data URL, после
чего `micromark` многократно парсил этот документ:

- `markdownToEditorBlocks` при создании редактора;
- `cache.toCanonical(editorValue)` и `extractAttachmentIds(...)` прямо в
  рендере `NotesView` (до четырёх парсингов на каждый ре-рендер);
- сериализации BlockNote при загрузке и технических change-событиях.

CPU-профиль перехода: ~74% сэмплов в `micromark`, включая
`locateDestination`/`replaceMarkdownImageUrls` из `plugin-notes`.

Отдельный источник задержки при уходе со страницы подтверждён стеком:

```text
setEditable
  → ProseMirror change
  → onChange
  → changeMarkdown
  → AttachmentUrlCache.toCanonical
  → replaceMarkdownImageUrls
  → micromark
```

`BlockNoteView` меняет `isEditable` при `readOnly`/`loading`, ProseMirror
эмитит change, хотя документ не менялся. Сериализация мегабайтных data URL
занимала сотни миллисекунд.

## Замер до/после

Условия: Chromium 1440×900, headless, отдельный dev-server worktree на
`127.0.0.1:3001` с копией пользовательской базы (`sqlite3 .backup`). Одна и та
же заметка «Галерея блоков», два круга «туда-обратно». Метрика — от клика по
строке дерева до `data-ready="true"` у редактора нужной заметки;

## Что сделано

- `loadNote` применяет `NoteDetails` и канонический Markdown сразу после
  `note.get`, снимает `loading` и только затем запускает загрузку содержимого
  вложений.
- `loadAttachmentUrls` догружает base64 с guard по `loadSequenceRef` и
  `selectedIdRef`: ответ прошлой страницы не применяется после быстрого
  перехода.
- При смене страницы cache сбрасывается; при повторном открытии той же
  страницы сохраняется, чтобы уже показанные data URL продолжали
  канонизироваться при сохранении.
- `AttachmentUrlCache.toEditorUrls()` отдаёт снимок `attachment://id` → data URL.
- `MarkdownNoteEditor` получил `attachmentUrls`: после загрузки вложений URL
  императивно подставляются в image-блоки и inline `inlineImage`/`linkedImage`.
  Подстановка не публикует `onChange`, не помечает документ dirty и не
  запускает autosave.
- Программная загрузка страницы, внешнее значение и подстановка вложений
  выполняются в транзакции с `addToHistory: false`: Ctrl+Z сразу после
  открытия не очищает документ и не возвращает `attachment://`.
- `onChange` игнорирует change-события без изменения ProseMirror-документа
  (`lastDocRef`). Это убирает сериализацию при lifecycle-смене `editable`.
- `referencedAttachmentIds` считается по каноническому Markdown через
  `useMemo`, а не по `editorValue` с data URL.
- Подстановка URL обходит не только абзацы и списки, но и
  `tableContent.rows[].cells[]` (ячейка `tableCell` с inline-контентом).
- Baseline сравнения хранится в каноническом виде: сериализованный документ
  перед сравнением строково канонизируется по карте вложений. Поэтому
  техническое изменение во время pending-загрузки второго изображения не даёт
  ложный `onChange`/autosave даже при уже подставленных data URL.
- Если undo/redo вернул снимок с каноническим `attachment://`, `onChange`
  обнаруживает неразрешённые URL, повторно подставляет data URL в
  транзакции без истории и только затем публикует изменение. Рекурсия
  подавлена, `lastDocRef` обновляется после подстановки.
- Ошибка вложений вынесена в отдельное состояние. Показанная страница не
  блокируется; баннер `note-attachments-error` предлагает «Повторить»,
  который повторяет только `attachment.get` для открытой страницы (без
  повторного `note.get`), с защитой от устаревших попыток и переключений.
- Домен, схема вложений, Storage Provider и persisted Markdown не изменялись.

## Тесты

Unit:

- снимок `toEditorUrls`;
- подстановка data URL в inline image и block image без `onChange`;
- повторная подстановка после внешнего значения;
- смена `editable` с уже подставленными вложениями не публикует `onChange`;
- заметка и канонический Markdown видны, пока `attachment.get` ещё висит, и
  это не помечает страницу изменённой;
- черновик, набранный до загрузки вложений, сохраняется, после догрузки
  получает data URL и не теряет текст;
- ответ вложений прошлой страницы после быстрого перехода не применяется;
- подстановка URL в изображение внутри ячейки реальной таблицы BlockNote;
- pending-загрузка второго изображения не публикует `onChange` и autosave,
  хотя первое вложение уже показано через data URL;
- undo/redo реального редактора, вернувшие канонический `attachment://`,
  повторно получают data URL без записи в историю;
- ошибка `attachment.get` показывает отдельный баннер, а «Повторить» реально
  повторяет только загрузку вложений и не перечитывает заметку.

E2E:

- `показывает страницу с большим вложением до загрузки data URL и не помечает
её изменённой`:
  - настоящее PNG-вложение ~1 МБ генерируется в тесте без внешних зависимостей;
  - `attachment.get` удерживается через `page.route`;
  - заголовок, текст и «Сохранено» видны до release, `note.update` не
    отправляется;
  - после release появляется `data:image/png`, число блоков не меняется,
    autosave не запускается;
  - после reload сохраняются текст, все блоки и изображение;
  - Ctrl+Z сразу после открытия не ломает изображение и не очищает документ.
- `быстро переключает страницы с вложениями: побеждает последняя`:
  два перехода в одном task, побеждает последняя страница с корректным
  текстом и загруженным изображением.
- `повторяет загрузку вложений после сетевой ошибки, не перечитывая страницу`:
  первый `attachment.get` обрывается через `page.route`, страница и текст
  остаются видимыми, баннер показывает ошибку; кнопка «Повторить» загружает
  вложение, убирает баннер и не запускает autosave.

Регрессионность проверена: при временно откаченных исходниках (тесты оставлены)
E2E-тест «показывает страницу с большим вложением…» падал — заголовок оставался
у промежуточной страницы, потому что загрузка ждала удержанные вложения.
Focused-тесты ревью также падают на исходниках предыдущего коммита:
изображение в ячейке таблицы остаётся `attachment://`, undo возвращает
канонический URL без повторной подстановки, pending-загрузка второго
изображения публикует ложный `onChange`, а кнопки retry нет вовсе.
После восстановления исправлений все тесты зелёные.

Жёстких timing-порогов в тестах нет: сценарии проверяют порядок «UI до
вложений», отсутствие autosave, сохранность блоков и последовательность
переходов; таймауты Playwright — обычные щедрые ожидания действий.

## Ограничения и риски

- В дереве редактора после подстановки по-прежнему лежат data URL вложений.
  Поэтому редактирование и сериализация очень большой страницы остаются
  такими же дорогими, как раньше; устранён именно повторный парсинг при
  открытии/переключении. Отдельный шаг — перейти на blob URL и для редактора.
- Все вложения по-прежнему загружаются параллельно после показа страницы
  (`Promise.all`), как и до изменения. Для 40 вложений по 5 МБ это может быть
  заметно по памяти; доменный лимит не менялся.
- При ошибке загрузки вложений страница остаётся открытой, показывается
  отдельный баннер с кнопкой «Повторить». Частично загруженные вложения не
  применяются: retry перезапрашивает весь набор, чтобы не оставить
  несогласованную карту URL.
- Программная загрузка страницы теперь не попадает в undo-историю. Это
  намеренно: раньше Ctrl+Z после открытия мог очистить документ или вернуть
  сломанный `attachment://`.
- Замеры выполнены на dev-server (React dev overhead); абсолютные значения в
  production ниже, но соотношение до/после и устранённый bottleneck те же.
