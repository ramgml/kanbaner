# Задачи Kanbaner

Локальный Markdown-трекер конкретных задач разработки.

## 1. Роль каталога

- `specs/` содержит устойчивые продуктовые и архитектурные решения.
- `specs/roadmap.md` задаёт крупные этапы.
- `specs/development-workflow.md` задаёт ветки, версии и релизы.
- `tasks/` содержит выполнимые задачи, зависимости, владение файлами и результаты.
- Git worktree используется для реализации, но не является трекером.

Не дублируй в задачах содержание спецификаций. Ссылайся на них.

## 2. Файлы задач

Один файл — одна задача:

```text
tasks/KAN-001-repository-scaffold.md
```

Правила:

- ID имеет формат `KAN-NNN`.
- ID назначает только оркестратор.
- ID не переиспользуется.
- Имя файла не меняется при изменении заголовка.
- Новая задача создаётся по `TEMPLATE.md`.
- Статус хранится в frontmatter, а не в имени каталога.
- Задача должна быть достаточно самостоятельной для выполнения в отдельном worktree.

## 3. Frontmatter

| Поле | Значение |
|---|---|
| `id` | Неизменяемый ID задачи |
| `title` | Краткое название |
| `status` | Текущий статус |
| `stage` | Этап roadmap |
| `priority` | `high`, `medium` или `low` |
| `owner` | Агент или `unassigned` |
| `blocked_by` | Список ID незавершённых зависимостей |
| `branch` | Ветка после назначения |
| `worktree` | Путь к worktree после назначения |
| `created` | Дата создания |
| `updated` | Дата последнего изменения |
| `specs` | Релевантные спецификации |

## 4. Статусы

```text
backlog → ready → in_progress → review → done
                    ↘ blocked
```

- `backlog` — задача сформулирована, но ещё не готова к запуску.
- `ready` — есть объём, владение файлами, зависимости и критерии приёмки.
- `in_progress` — назначен owner и создан worktree.
- `review` — worker закоммитил результат и прогнал проверки.
- `done` — результат смержен в `dev`, проверки на `dev` зелёные. Релиз в `main` не требуется для `done`.
- `blocked` — выполнение невозможно; причина указана в журнале.
- `cancelled` — задача отменена; файл сохраняется для истории.

Коммит worker-а не переводит задачу в `done`.

## 5. Готовность задачи

Задача может перейти в `ready`, только если:

- цель и ожидаемый результат понятны;
- перечислены разрешённые и запрещённые файлы;
- определены общие файлы и их владелец;
- перечислены зависимости;
- указаны ссылки на спецификации;
- есть проверяемые критерии приёмки;
- известна команда проверок или способ её определить.

Если задачу нельзя выполнить независимо, объедини её с пересекающейся задачей.

## 6. Владение и параллельная работа

- У каждого файла один владелец.
- Общие контракты, миграции, корневой `package.json`, lock-файл и конфигурация тестов относятся к одной задаче.
- Если две задачи неизбежно меняют один файл, они выполняются последовательно.
- Только оркестратор меняет `status`, `owner`, `branch`, `worktree` и `blocked_by`.
- Worker не редактирует файл задачи в параллельном режиме.
- Worker создаёт отчёт `tasks/reports/KAN-NNN.md`.
- Worker не назначает себе задачу и не выдаёт новые ID.
- Новые задачи, найденные worker-ом, описываются в отчёте; ID выдаёт оркестратор.
- Ветки `feat/*` и `fix/*` создаются от `dev`.
- Ветки `release/*` и `hotfix/*` создаёт только оркестратор.
- `CHANGELOG.md` редактирует только оркестратор в release-ветке.
- Перед запуском worker-а оркестратор фиксирует `in_progress` в основном checkout.

Рекомендуемое соответствие:

```text
task:    KAN-003
branch:  feat/kan-003-plugin-runtime
worktree: .worktrees/kan-003-plugin-runtime
report:  tasks/reports/KAN-003.md
```

## 7. Порядок выполнения

1. Оркестратор выбирает задачу со статусом `ready`.
2. Проверяет, что все `blocked_by` закрыты.
3. Назначает `owner`, `branch`, `worktree` и ставит `in_progress`.
4. Передаёт worker-у самодостаточный бриф.
5. Worker пишет код только в разрешённых файлах.
6. Worker прогоняет проверки и коммитит изменения.
7. Worker создаёт отчёт и сообщает о результате.
8. Оркестратор переводит задачу в `review`.
9. Выполняется интеграция в `dev` и проверка на `dev`.
10. Оркестратор заполняет `Итог` и ставит `done`.

При блокировке:

1. Причина записывается в `Журнал`.
2. Задача переводится в `blocked`.
3. Указывается, какое решение или изменение зависимости требуется.

## 8. Завершение

Задача считается завершённой, когда:

- критерии приёмки выполнены;
- отчёт содержит коммит и результаты проверок;
- изменения смержены в `dev`;
- проверки на `dev` зелёные;
- документация обновлена;
- итог задачи заполнен;
- worktree удалён, если он больше не нужен.

## 9. Поиск задач

Готовые к запуску задачи:

```bash
rg -l '^status: ready$' tasks/KAN-*.md
```

Активные задачи:

```bash
rg -n '^status: in_progress$' tasks/KAN-*.md
```

Задачи по зависимости:

```bash
rg -n 'KAN-003' tasks/KAN-*.md
```

Постоянный `BOARD.md` вручную не поддерживается. При необходимости его можно генерировать из frontmatter.
