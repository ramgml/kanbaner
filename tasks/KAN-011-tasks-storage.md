# KAN-011 — Хранение задач и инварианты

## Цель

Реализовать контракт `TasksStore` из KAN-010 поверх namespaced
`PluginDocumentStore` и обеспечить все доменные инварианты: версии,
позиции, подзадачи, каскады, теги, UTC, пагинацию и транзакционность.

Задача не меняет Storage Provider и не добавляет SQL в плагин. Хранение
физически остаётся деталью провайдера; логически плагин использует коллекции
`projects` и `tasks` в своём namespace.

## Результат

- `createTasksStore` реализует `TasksStore` и работает на in-memory и SQLite
  провайдерах без ветвлений по backend.
- Все операции асинхронны, изменяющие операции выполняются в транзакции
  плагина и поддерживают `expectedVersion`.
- Позиции уникальны и непрерывны в пределах области сортировки.
- Удаление проекта и задачи каскадно удаляет связанные данные, а вызывающая
  сторона получает `ResourceRef` удалённых сущностей для очистки поиска.
- Повторный запуск и конкурентные изменения не теряют данные.

## Объём работ

- [ ] Реализовать `createTasksStore({ storage, idFactory, now })` с
      коллекциями `projects` и `tasks`.
- [ ] Для проекта: создание, чтение, список, обновление, удаление.
- [ ] Для задачи: создание, чтение, список, обновление, перемещение,
      завершение и удаление.
- [ ] Обеспечить оптимистичную блокировку:
  - создание с `expectedVersion = 0`;
  - изменение и удаление с обязательным `expectedVersion`;
  - при несовпадении возвращать `VERSION_CONFLICT` с текущей версией;
  - не перезаписывать документ при конфликте.
- [ ] Обеспечить уникальность и стабильный порядок `position` в области
      `(projectId, status)`:
  - вставка в конец или в указанную позицию;
  - сдвиг соседей в одной транзакции;
  - удаление закрывает разрыв;
  - перемещение между статусами и позициями атомарно;
  - непрерывность `0…N-1` не требуется: допустимы позиции с шагом, если
    уникальность и порядок сохранены.
- [ ] Реализовать правила подзадач:
  - родитель существует и принадлежит тому же проекту;
  - родитель не является подзадачей;
  - удаление родителя удаляет его подзадачи;
  - перенос подзадачи в другой проект запрещён.
- [ ] Реализовать теги: нормализация из KAN-010, хранение в документе задачи,
      фильтрация по тегу в Store.
- [ ] Хранить все временные значения в UTC через `currentUtcTimestamp` или
      инъекцию `now`; ID генерировать до записи через `idFactory`.
- [ ] Реализовать `listTasks` с фильтрами, сортировкой и пагинацией:
  - использовать `indexedFields` для точных фильтров;
  - сортировать в Store по `position`, `dueAt`, `title`, `createdAt`,
    `updatedAt`;
  - обеспечить стабильный порядок при равных значениях через `id`;
  - возвращать `items`, `total`, `nextOffset`;
  - ограничить `limit` диапазоном 1…200.
- [ ] Реализовать каскадное удаление:
  - `project.delete` удаляет все задачи проекта;
  - `task.delete` удаляет подзадачи;
  - Store возвращает `deletedResourceRefs` и `deletedTaskIds`.
- [ ] Сериализовать конкурирующие изменения средствами транзакций провайдера;
      не использовать глобальные mutable-очереди.
- [ ] Реализовать переиспользуемый `createTasksStoreConformanceSuite` и
      прогнать его на четырёх вариантах: in-memory, delayed in-memory, SQLite,
      delayed SQLite.
- [ ] Драйверы conformance разместить в разрешённом
      `tests/integration/tasks-store-*.test.ts`; пакет не получает
      production-зависимость от `@kanbaner/kernel` или
      `@kanbaner/storage-sqlite`. Если тесты остаются внутри пакета,
      разрешены только devDependencies и только для `*.test.ts`.
- [ ] Добавить тесты:
  - CAS и `VERSION_CONFLICT`;
  - откат при rejected Promise внутри транзакции;
  - конкурентные перемещения и вставки;
  - уникальность позиций после серии операций;
  - подзадача второго уровня и чужой проект;
  - каскадное удаление и возвращённые ссылки;
  - пагинация без дублей и пропусков;
  - UTC и app-generated ID;
  - работа на delayed-провайдере без синхронных предположений.
- [ ] Экспортировать Store из `src/index.ts`, а conformance suite — через
      subpath `@kanbaner/plugin-tasks/testing`, чтобы тестовые утилиты не
      попадали в production entrypoint.

## Контракты и зависимости

- Опирается на `TasksStore`, модель и валидаторы KAN-010.
- Использует `PluginStorage` / `PluginDocumentStore` из
  `@kanbaner/plugin-sdk`.
- Не зависит от `kanbaner.tasks` activation, UI и поискового плагина.
- Conformance suite публикуется через `@kanbaner/plugin-tasks/testing`.
- Блокирует KAN-012.

## Критерии приёмки

- [ ] Один и тот же Store проходит conformance на in-memory и SQLite,
      включая delayed-варианты.
- [ ] Позиция никогда не дублируется в области `(projectId, status)` и даёт
      стабильный порядок.
- [ ] Конфликт версий не меняет документ и возвращает актуальную версию.
- [ ] Подзадача второго уровня и перенос между проектами отклоняются.
- [ ] Удаление проекта и родительской задачи каскадно очищает задачи.
- [ ] В доменном коде нет SQL, `PRAGMA`, имён таблиц, драйвера БД и
      синхронных методов.
- [ ] Время хранится в UTC, ID создаются до записи.
- [ ] Пагинация стабильна при одинаковых значениях сортировки.
- [ ] Тесты покрывают основной, ошибочный и конкурентный сценарии.

## Риски

- Сортировка и фильтрация в памяти могут стать узким местом на больших
  объёмах. Смягчение: `TasksStore` скрывает реализацию; позже можно добавить
  специализированный store.
- Логическая уникальность позиций зависит от транзакций провайдера.
  Смягчение: конкурентные тесты и отказ от глобальных очередей.
- Каскадное удаление большого проекта выполняется в одной транзакции.
  Смягчение: операция атомарна; жёсткий лимит задач на проект не вводится,
  а размер проекта остаётся ответственностью пользователя.
